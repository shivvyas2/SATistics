Chapter fifteen

15Deploying and operating

One repository becomes two Vercel projects. The project called satistics builds frontend/ and serves https://www.satistic.tech; the project called backend builds backend/ as a single Python function and serves https://api.satistic.tech. Both deploy on every push to main. The database is a Supabase project that neither deploy touches: schema changes are SQL you run by hand.

This chapter describes how each project is configured, which variables each one needs, why the API lives on a custom domain, how CORS and search-engine files are set up, how to change the schema and roll back a bad deploy, and what the other deploy files in backend/ are. It ends with a checklist to run after any deploy that touches configuration. Setting up your own copy uses the same steps with your own domains and keys.

The root directory is set in each project's settings, not in a file. There used to be a vercel.json at the repository root with a rootDirectory field; Vercel rejected the field and every backend build failed until it was removed (commit "Fix backend Vercel deployment"). Do not add one back. Each project reads only the vercel.json inside its own root.

Both projects use Vercel's Git integration. A push to main becomes production in both; a push to any other branch makes preview deployments. GitHub Actions (.github/workflows/ci.yml) runs lint, typecheck, build and a backend import check on the same push, but nothing makes Vercel wait for CI. A red CI run does not stop a deploy, which is why CONTRIBUTING.md says nobody commits to main directly.

15.2The backend on Vercel

The backend is one Python serverless function. Vercel's Python runtime installs backend/requirements.txt, finds backend/api/index.py, and serves the ASGI object named app that the file exposes. The file is four lines of real code: 

# backend/api/index.py
backend_dir = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
if backend_dir not in sys.path:
    sys.path.insert(0, backend_dir)

from src.main import app  # noqa: E402,F401

It puts backend/ on the import path so from src.api import ... resolves exactly as it does locally, then re-exports the FastAPI app. There is no adapter such as Mangum; the runtime speaks ASGI directly. backend/vercel.json sends every path to that one function: 

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/api/index" }
  ]
}

The rewrite changes which function runs, not the path FastAPI sees, so /api/health/ still matches the health router. The file sets no maxDuration or memory, so the platform defaults apply. Question generation that calls the College Board bank, a web search and a model in sequence is the slowest request; if it starts timing out, a functions block in this file is the place to raise the limit.

backend/.vercelignore keeps the upload small and secret-free. It excludes .env and .env.*, venv/, caches, the alternative deploy files (Dockerfile, fly.toml, railway.json, render.yaml), every *.sh script, and the whole database/ folder. The SQL never ships, because nothing at runtime reads it.

Serverless has two consequences worth knowing. The in-memory caches (the 24-hour video cache in src/services/videos.py and the College Board index cache in src/services/question_sources.py) live per warm instance and vanish on a cold start. And Database.get_client() keeps one Supabase client per instance, shared by every request that instance serves.

15.3The frontend on Vercel

frontend/vercel.json declares the Next.js framework with npm install, npm run build and an output directory of .next. It also contains a rewrite that is left over from an earlier hosting plan: 

"rewrites": [
  {
    "source": "/api/:path*",
    "destination": "https://your-backend-url.railway.app/api/:path*"
  }
]

The destination is a placeholder that does not resolve. Nothing depends on it, because the browser calls the API by its full URL from NEXT_PUBLIC_API_URL, never through a relative /api path, and frontend/middleware.ts skips /api paths. A request to www.satistic.tech/api/... fails. Removing the block, or pointing it at https://api.satistic.tech, is a safe cleanup.

frontend/next.config.js sets reactStrictMode, allows remote images from one host for the developer page, sets output: 'standalone' (which Vercel ignores; it matters only for self-hosting in a container), and copies NEXT_PUBLIC_API_URL into the build's env with a default of http://localhost:8000.

The API URL is baked into the build NEXT_PUBLIC_API_URL is inlined into the JavaScript bundle at build time. Changing it in the Vercel dashboard does nothing until the frontend is redeployed. If it is missing from the project, the build succeeds and production quietly calls http://localhost:8000, which shows up as every API call failing in users' browsers.

frontend/.vercelignore excludes .env.local, .env.*.local, node_modules/, .next/, .vercel/ and log files. frontend/deploy.sh builds and runs npx vercel --prod by hand; with the Git integration you do not need it, and its reminder to set Supabase variables on the frontend is out of date (see 15.4).

The service-role key must be under one of the two names the backend reads, SUPABASE_SERVICE_ROLE_KEY or SUPABASE_SERVICE_KEY. If neither is set, the client silently falls back to the anon key, Row Level Security rejects the backend's writes, and saving a score fails. That exact failure is why SUPABASE_SERVICE_KEY was added as a fallback name. Backend variables take effect on the next deployment, so redeploy after changing one.

15.5Domains, CORS and deployment protection

Both domains are added in each project's Settings, Domains, with DNS records at the registrar pointing at Vercel. The site's canonical host is www.satistic.tech; it is SITE_URL in frontend/lib/site.ts.

Why the API has its own domain. Vercel's deployment protection puts a Vercel login in front of generated deployment URLs (the *.vercel.app hosts). A browser fetch from the site to such a URL gets a 401 and a login page instead of JSON, and the CORS preflight fails with it, so the site looks broken while the API is fine. A custom production domain is not covered by standard protection, so api.satistic.tech is reachable by every browser while the generated URLs stay private. Point NEXT_PUBLIC_API_URL at the custom domain, never at a vercel.app URL.

CORS. backend/src/main.py builds the allow list once, at import: 

allowed_origins = os.getenv("ALLOWED_ORIGINS", "").split(",") if os.getenv("ALLOWED_ORIGINS") else []
default_origins = [
    "http://localhost:3000",
    "http://localhost:3001",
    "http://127.0.0.1:3000",
    "http://127.0.0.1:3001",
]
allowed_origins = [origin for origin in allowed_origins + default_origins if origin]

The middleware allows credentials, the methods GET, POST, PUT, DELETE, OPTIONS, PATCH and HEAD, any header, and caches a preflight for 3600 seconds. Matching is exact: https://satistic.tech and https://www.satistic.tech are different origins, and the split does not trim spaces, so write the list with commas only. A frontend preview deployment has its own origin, which is not on the list, so previews can load pages but their API calls to production are blocked. Test API changes locally, not on previews.

15.6Changing the database

There is no migration runner. Schema lives in SQL files under backend/database/, and a change reaches production when someone pastes it into the Supabase SQL Editor for the production project. CONTRIBUTING.md sets the rule: a schema change is a new SQL file, and the same change is folded into reset.sql so a fresh project gets the whole schema in one run. Every new table gets RLS enabled and policies, even though the backend uses the service-role key.

Order matters because the two sides deploy separately:

  1. Write the change additively: CREATE TABLE IF NOT EXISTS, ADD COLUMN with a default, and DROP POLICY IF EXISTS before CREATE POLICY, so the file can be rerun.
  2. Run it on a development project and exercise the code against it.
  3. Run it on production before merging code that reads the new column or table.
  4. Merge. The new backend deploys against a schema that already fits it.
  5. Remove old columns only in a later change, after no deployed code reads them.

A new project gets the schema from two files, run in order: reset.sql, then add_materials.sql, which creates materials and custom_questions. Never run reset.sql on production. It drops the core tables and deletes every user in auth.users. Chapter 13 lists the tables and policies.

15.7Search engines

Three files in the frontend describe the site to crawlers, and all of them build URLs from SITE_URL in frontend/lib/site.ts:

  • frontend/app/sitemap.ts lists four public URLs: the home page, /developer, /signup and /login, with lastModified set to build time.
  • frontend/app/robots.ts allows /, disallows /dashboard, /games, /learn, /materials, /mock, /profile and /stats, and points at /sitemap.xml.
  • frontend/app/layout.tsx sets metadataBase, the title template %s | SATistics, the description and application name from lib/site.ts, and renders JSON-LD through the jsonLd helper, which escapes < so the data cannot close the script tag.

The robots disallow list matches protectedPrefixes in frontend/middleware.ts route for route. Keep the two lists in step when you add a signed-in route. If you run your own copy on another domain, SITE_URL is the one value to change.

15.8Rolling back

Every deployment Vercel has built stays available. To undo a bad release, open the project's Deployments tab, find the last good production deployment, and use Instant Rollback (or "Promote to Production"). The CLI does the same with vercel rollback from a directory linked to the project. The switch is immediate because nothing is rebuilt.

Three things to keep in mind:

  • The projects roll back separately. If a change touched both the API and the client, decide whether the old frontend works with the new backend before rolling back only one.
  • An instant rollback keeps the old build's inlined values. A frontend deployment carries the NEXT_PUBLIC_API_URL it was built with.
  • The database does not roll back. Nothing reverses a SQL change. This is why schema changes are additive and run first.

After a rollback, fix forward on a branch: git revert the bad commit in a pull request, so main matches what is serving again and the next push does not reintroduce the bug.

15.10Operations checklist

Run this after a deploy that changes configuration, domains, dependencies or schema.

  1. curl https://api.satistic.tech/api/health/ returns "status":"healthy".
  2. curl https://api.satistic.tech/api/health/supabase returns "supabase":"connected". If it says unhealthy, read the error field: a missing table means SQL was not run, an auth error means a wrong key.
  3. A CORS preflight from the site origin succeeds: 
    curl -si -X OPTIONS https://api.satistic.tech/api/auth/login \
  -H "Origin: https://www.satistic.tech" \
  -H "Access-Control-Request-Method: POST" | grep -i access-control-allow-origin
  4. Load https://www.satistic.tech, log in, and check in the browser's network tab that requests go to api.satistic.tech, not localhost.
  5. Play one round and confirm it appears on /stats.
  6. Open one lesson and confirm videos load.
  7. https://www.satistic.tech/sitemap.xml and /robots.txt show the production host.
  8. In the backend project's runtime logs, look for Unhandled exception lines, which global_exception_handler prints with a traceback before returning a generic 500.
What a green deployment does not tell you Vercel marks a deployment ready when it builds. It does not check that the environment variables are present, that the API URL was right at build time, or that the database has the tables the code queries. Each of those fails only at request time, in a user's browser. The checklist above is how you find out first.

15.11Study notes

Read in this order

  1. backend/api/index.py and backend/vercel.json, the whole backend deploy.
  2. backend/.vercelignore, for what never ships.
  3. backend/src/main.py, the CORS block and the exception handler.
  4. frontend/next.config.js and frontend/vercel.json, including the stale rewrite.
  5. frontend/lib/site.ts, app/sitemap.ts, app/robots.ts and the metadata in app/layout.tsx.
  6. .github/workflows/ci.yml, for what runs beside each deploy.
  7. backend/Dockerfile, if you plan to host the API elsewhere.

Check yourself

You change NEXT_PUBLIC_API_URL in the dashboard. Why does production still call the old API?

The value is inlined at build time. The frontend has to be redeployed.

Why does the site call api.satistic.tech and not the backend's vercel.app URL?

Deployment protection puts a Vercel login in front of generated URLs, so browser calls get a 401 page. The custom production domain is not protected.

Saving scores fails in production with a row-level security error. What is the likely cause?

Neither SUPABASE_SERVICE_ROLE_KEY nor SUPABASE_SERVICE_KEY is set, so the client fell back to the anon key.

A frontend preview deployment loads but every API call fails. Is the backend down?

Probably not. The preview's origin is not in ALLOWED_ORIGINS, so CORS blocks it.

You rolled back the backend after a release that added a column. What did not roll back?

The database. SQL changes are not reversed, which is why they must be additive and applied before the code that needs them.
