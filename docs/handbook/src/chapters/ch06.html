Chapter six

6Exams, courses and practice settings

Every question in SATistics belongs to one exam and one section. That pair, plus a question count, is the only setting a player chooses before a game. This chapter covers where the pair is defined, how it is stored, how it reaches the games and the backend, and what a question looks like once it arrives. It ends with a checklist for adding an exam or a section.

6.1Intent

The product trains for two tests, the Digital SAT and the GRE, and each has a quantitative and a verbal section. Rather than build a separate game per test, the app keeps one small model of "what am I practising" and threads it through everything: the game setup screen, the question loader, the timer, the offline bank, the learning hub's courses and the mock exam. A game never knows which exam it is running; it receives questions and a number of seconds per question.

The model is deliberately thin. It is a pair of string ids, a question count and a table of real-exam pacing. There is no database row for it: the choice lives in the browser's localStorage, under one key, and the backend is told the exam and section as query parameters on every question request. The profile's exam field, covered with profiles, is a separate thing: it sets the target score scale and is not read by the question loader.

The frontend and backend each keep their own EXAMS table. They are not generated from one another and they hold different facts: the frontend's has display names and pacing, the backend's has the names used in prompts and search queries and the number of answer choices.

6.3Model

Exam, section and pace

// frontend/lib/exam.ts
export type ExamId = 'sat' | 'gre'
export type SectionId = 'quant' | 'verbal'
export type Pace = 'quick' | 'deep'

export interface ExamPrefs {
  exam: ExamId
  section: SectionId
  questionCount: number
}

SectionId uses the GRE's vocabulary for both tests. On the SAT, quant means Math and verbal means Reading and Writing. The display name comes from EXAMS, never from the id.

Pace is not a player setting. It is a property of the game: gamePace returns 'deep' for any id in DEEP_GAMES, which today holds only 'squid-game', and 'quick' for everything else. Quick games want short questions that can be read while something is moving on screen; the deep game wants passages and multi-step problems. Chapter 7 shows how each question source honours it.

The pacing table

ExamSection idNamepacingsecondsPerQuestion

secondsPerQuestion is the official section length divided by its question count, rounded down (35 minutes over 22 questions is 95.45 seconds). It is used where the app wants the real exam's pace: the deep game's per-question timer and the mock exam's single clock. Quick games ignore it and use QUICK_SECONDS_PER_QUESTION, which is 35.

QUESTION_COUNTS is [6, 10, 20], the three choices on the setup screen. The default preferences are { exam: 'sat', section: 'quant', questionCount: 10 }.

Storage

getExamPrefs reads the JSON under the localStorage key exam_prefs and validates each field on the way out: an exam that is not a key of EXAMS, a section that is neither 'quant' nor 'verbal', or a count not in QUESTION_COUNTS falls back to the default for that field alone. On the server (typeof window === 'undefined') or on a parse error it returns the defaults. setExamPrefs writes the whole object and swallows storage errors. Neither function touches the backend, so preferences are per browser, not per account.

The SAT topic strings are the College Board's own domain names. They matter because the official question bank reports a question's topic as its primary_class_cd_desc, which uses the same strings, so topic statistics from games line up with course topics without a mapping table. The offline bank uses the same names for its topic fields. courseFor(exam, section) finds the matching course and falls back to COURSES[0], SAT Math, if none matches. Besides the setup screen, the landing page, the dashboard, the learning hub and frontend/lib/lessons.ts import this file.

A question

The question shape is defined twice, once per language, and the two are kept in step by hand.

FieldTypeMeaning
idintStable per source, see chapter 7 for how each source makes it
questionstrFull plain text, passage first if there is one
optionslist of strPlain-text choices, 2 to 5
correctAnswerint0-based index into options
topic, difficulty, explanationstrDifficulty is easy, medium or hard
exam, section, skilloptional strSkill is the fine-grained College Board skill
passage, stemoptional strThe passage and the question without it
questionHtml, passageHtml, optionsHtml, explanationHtmloptionalSanitized HTML and MathML, only on official questions
source, sourceName, sourceUrloptional strWhere the question came from

The plain and rich forms exist side by side because the games need both. Canvas games draw text themselves and can only use question and options. The React overlays and the mock exam render HTML through QuestionContent and fall back to the plain text when no HTML is present. question always carries the passage too, so a game that shows only one string still shows everything; renderers that have room use passage and stem separately.

source takes five values in practice: official (College Board), web (copied from a practice page), ai (written by the model), custom (the user's own material, chapter 12) and practice (the offline bank, set only in the browser). The comment in schemas.py lists three of them and the comment in SATQuestion lists four; neither mentions custom. The field is a free string in both, so nothing breaks.

6.4The server side

# backend/src/services/question_sources.py
EXAMS = {
    "sat": {
        "name": "SAT",
        "sections": {
            "quant": {"name": "Math", "option_count": 4},
            "verbal": {"name": "Reading and Writing", "option_count": 4},
        },
    },
    "gre": {
        "name": "GRE",
        "sections": {
            "quant": {"name": "Quantitative Reasoning", "option_count": 5},
            "verbal": {"name": "Verbal Reasoning", "option_count": 5},
        },
    },
}

section_label(exam, section) joins the two names, giving strings like "GRE Quantitative Reasoning". That label goes into the LLM prompts, the DuckDuckGo queries and the material parser's prompt. option_count is only read by the agent's prompt ("Single-answer multiple choice with 5 options"). The lesson-video search in backend/src/services/videos.py also reads the names from this table.

The names differ from the frontend's on purpose: the backend uses the official long names because they make better search queries. Do not "fix" one to match the other without checking what reads it.

Validation happens at the edges. GET /api/questions declares exam: Literal["sat", "gre"] and section: Literal["quant", "verbal"], so FastAPI rejects anything else with a 422 before any code runs. POST /api/materials does the same with form fields, and GET /api/learn/videos uses a regex pattern ^(sat|gre)$. In the database, materials.exam and profiles.exam carry a CHECK (exam IN ('sat', 'gre')). The response model is QuestionResponse: a list of Question and a total.

6.5The client

The setup screen at /games/[gameId]/select is the only place a player edits the preferences for games. It is a client component. Because preferences live in localStorage, it renders a pulsing placeholder on first paint and loads them in a useEffect, which avoids a hydration mismatch between the server render (defaults) and the browser (saved values).

It shows three rows of toggle buttons: exam (from Object.keys(EXAMS)), section (from the chosen exam's sections) and question count (from QUESTION_COUNTS), each with aria-pressed. Under the counts it prints the real exam's pacing string, and under that the topic chips from courseFor(prefs.exam, prefs.section).topics. Every click goes through updatePrefs, which merges the change, sets state and calls setExamPrefs at once. There is no save button. "Start game" is a plain link to /games/[gameId]; it carries no parameters, because the game page reads the preferences itself.

An unknown gameId (not in games from frontend/lib/games.ts) renders a "That game doesn't exist" card with a link back to /games.

Subway Surfers and Squid Game fetch twice the count so their difficulty can adapt as the run goes, then cap the run at questionCount. Pac-Man, Carnival and Whack-a-Mole ignore the count setting. Every container reads getExamPrefs() on mount and the loader in frontend/lib/api/questions.ts reads it again to build the request, so the exam and section always come from storage, never from props.

6.6How it works

  1. The player opens /games/squid-game/select. The effect calls getExamPrefs(); say it returns GRE, verbal, 10.
  2. The screen shows "Real exam pace: 12 questions in 18 min" and the chips Text Completion, Sentence Equivalence, Reading Comprehension.
  3. The player taps 20. setExamPrefs writes {"exam":"gre","section":"verbal","questionCount":20} to exam_prefs.
  4. "Start game" navigates to /games/squid-game. SquidGameContainer reads the preferences again and calls fetchAIQuestions(40, undefined, 'deep').
  5. fetchAIQuestions reads the preferences a third time and requests /api/questions/?use_agent=true&limit=40&use_web_search=true&exam=gre&section=verbal&pace=deep.
  6. The questions come back (chapter 7). The container builds the game with questionCount: 20 and secondsPerQuestion: 90, from EXAMS.gre.sections.verbal.

The mock exam (chapter 12) has its own exam and section picker, and before it loads questions it calls setExamPrefs({ ...getExamPrefs(), exam, section }), because the loader only reads the section from storage. A side effect is that choosing a mock exam also changes the section the next game will use.

6.7Adding an exam or a section

There is no single registry, so a new exam touches both halves of the stack. In order:

  1. frontend/lib/exam.ts: extend ExamId (or SectionId) and add the entry to EXAMS with a real pacing string and secondsPerQuestion. If you add a section, update the hand-written check in getExamPrefs, which accepts only 'verbal' and 'quant'.
  2. frontend/lib/courses.ts: add a Course per section, with the official domain names as topics.
  3. frontend/lib/questionBank.ts: add a bank array per section to BANK. The type is Record<ExamId, Record<SectionId, ...>>, so TypeScript will refuse to compile until you do. Include all three difficulties so both paces have something left after filtering.
  4. frontend/app/mock/page.tsx: MODULE_QUESTIONS and SCORE_RANGE are also keyed by ExamId. The rounding step and the source blurb test exam === 'sat'.
  5. frontend/lib/profile.ts: SCORE_RANGES, and the copy in frontend/components/profile/ProfileFields.tsx.
  6. backend/src/services/question_sources.py: add the entry to EXAMS with names suitable for search and an option_count.
  7. backend/src/api/questions.py and backend/src/api/materials.py: widen the Literal types. backend/src/api/learn.py: widen the regex. backend/src/models/schemas.py: widen Profile.exam and its target-score validator.
  8. SQL: the CHECK constraints in add_materials.sql, add_profiles.sql and reset.sql need a new migration that drops and recreates them.
  9. backend/src/services/agent.py: only SAT has an official source (if exam == "sat"). A new exam gets web and AI questions only, so it needs OPENROUTER_API_KEY set, or it falls through to the offline bank.
Check with grep. Before opening a pull request, search both trees for 'sat', "gre", Record<ExamId and Literal["sat". Every hit is a place that enumerates exams.

6.8Edge cases and tests

  • Private windows. If localStorage throws, the getter returns defaults and the setter is a no-op, so the setup screen works but forgets every change.
  • Stale values. A stored count of 15 from an older version falls back to 10 without touching the stored exam or section.
  • Two tabs. There is no storage event listener. A tab that is already open keeps the preferences it read on mount.
  • Name drift. The frontend says "Reading & Writing" and "Quantitative"; the backend says "Reading and Writing" and "Quantitative Reasoning". This is harmless but it means a label from one side should never be compared to the other.
  • Profile versus practice. A user whose profile says GRE can practise SAT. Nothing reconciles the two.

There are no automated tests for this code. The frontend package.json has no test script and the backend has no test directory. The validation in getExamPrefs and the hand-kept parity between SATQuestion and Question are the first things worth pinning.

Check yourself

Where does the backend learn which exam a player is practising?

From the exam and section query parameters on each GET /api/questions call, which fetchAIQuestions fills from localStorage. Nothing is stored server side.

Why does the select page render a placeholder before showing the options?

The preferences are only readable in the browser. Loading them in an effect keeps the server render and the first client render identical.

A quick game and the deep game both run GRE Quant. How long does each give per question?

The quick game gives QUICK_SECONDS_PER_QUESTION, 35 seconds. Squid Game gives the section's secondsPerQuestion, 105 seconds.

Why can SAT topic statistics be matched to course topics without a mapping?

Official questions take their topic from the College Board's domain description, and COURSES uses those same domain names.

You add a third section. Which frontend function silently drops it if you forget it?

getExamPrefs, which only accepts 'verbal' or 'quant' and otherwise returns the default section.
