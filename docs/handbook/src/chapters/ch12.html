Chapter twelve

12Mock exams and your own material

Two features sit beside the games. The mock exam is a timed section in test-day format: one clock, no feedback until the end, a score report after. "My material" lets a student upload a practice test or notes, review the questions found in it, and approve the ones that should appear in their games and mock exams. Both reuse the question engine of chapter 7 rather than adding their own.

12.1Intent

Games are good for repetition, but a student also needs to feel the real exam's pace and to see an honest score afterwards. The mock exam gives them that with the same questions the games use. It lives entirely in the browser: one page, three screens (setup, exam, results), and a single call to save the result alongside game sessions so it feeds statistics and weak topics.

Students also have their own material: a teacher's handout, a practice test PDF, class notes. The materials feature turns that into questions in the standard game format. The design rule is that nothing from an upload reaches a game until the student has looked at it. Every question starts as pending, and a question cannot be approved without a correct answer.

12.3Model

Two tables

-- backend/database/add_materials.sql (abridged)
CREATE TABLE IF NOT EXISTS materials (
  id UUID DEFAULT gen_random_uuid() PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  exam TEXT NOT NULL CHECK (exam IN ('sat', 'gre')),
  section TEXT NOT NULL CHECK (section IN ('quant', 'verbal')),
  created_at TIMESTAMP WITH TIME ZONE ...
);

CREATE TABLE IF NOT EXISTS custom_questions (
  id BIGSERIAL PRIMARY KEY,
  material_id UUID NOT NULL REFERENCES materials(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  exam TEXT NOT NULL,
  section TEXT NOT NULL,
  question TEXT NOT NULL,
  passage TEXT NOT NULL DEFAULT '',
  options JSONB NOT NULL,
  correct_answer INTEGER,               -- NULL until found or picked
  topic TEXT NOT NULL DEFAULT 'My material',
  difficulty TEXT NOT NULL DEFAULT 'medium',
  explanation TEXT NOT NULL DEFAULT '',
  origin TEXT ... CHECK (origin IN ('extracted', 'generated')),
  status TEXT ... DEFAULT 'pending' CHECK (status IN ('pending', 'approved')),
  created_at ...
);

A material is a name, an owner, an exam and a section. It holds no text and no file: the upload is read once, turned into rows in custom_questions, and discarded. There is no storage bucket. If the parser misses a question, the only way to get it is to upload again.

Three indexes support the reads: by materials.user_id, by custom_questions.material_id, and a compound one on (user_id, exam, section, status), which is exactly the filter load_custom_questions uses. Both tables have RLS enabled with an owner-only policy for all operations.

Ownership is enforced in Python. The backend's Database.get_client prefers SUPABASE_SERVICE_ROLE_KEY, which bypasses RLS. Every query in materials.py therefore filters by user_id itself, and _own_material returns 404 for a material that is not the caller's. The RLS policies are a backstop. If the backend ever ran with only the anon key, the inserts would fail, because auth.uid() would be null.

Client types

frontend/lib/materials.ts mirrors the rows. Material adds two optional counts the list route computes, question_count and approved_count. CustomQuestion has correct_answer: number | null, origin: 'extracted' | 'generated' and status: 'pending' | 'approved'. It omits topic and difficulty, which the page never shows.

Every route depends on get_current_user, so all of them require a valid bearer token. The router is mounted at /api/materials in backend/src/main.py.

Upload

upload_material takes form fields exam and section (both Literal), name, text, generate and an optional file. If a file is present it reads all of it, checks the size, and replaces text with extract_text(filename, content); pasted text is ignored in that case. An empty name falls back to the file name, and later to "Untitled material". Then:

  1. Text shorter than 40 characters after trimming is a 400 that suggests the PDF is scanned.
  2. parse_questions(text) runs the rule-based parser.
  3. If generate is set or the parser found nothing, questions_from_llm runs too.
  4. merge_questions keeps every parsed question and adds model questions whose first 60 normalized characters are new.
  5. No questions at all is a 422 that explains the numbered format.
  6. One materials row is inserted, then all questions in one insert, each with the material's exam and section, topic defaulting to "My material" and difficulty to medium. The response is the material and the saved rows.

Reading files

extract_text treats a file as PDF if its name ends in .pdf or its first five bytes are %PDF-, and reads it with pypdf's PdfReader, joining each page's extract_text(). There is no OCR, so a scanned PDF yields little or no text. Anything else is decoded as UTF-8 with errors="replace". The file input in the browser accepts .pdf, .txt, .md, application/pdf and text/plain, but the server does not check the type: a Word document would be decoded as noise and most likely fail with "No questions found".

The parser

parse_questions reads line by line with five regular expressions.

PatternMatches
QUESTION_START1., 12), 3: or Question 4. followed by text; up to three digits
OPTION_STARTA), b., (C) followed by text; letters A to E
ANSWER_LINEAnswer: C, Correct answer is (B)
EXPLANATION_LINEExplanation:, Solution:, Rationale:
ANSWER_KEY_HEADINGA line that is just Answer Key or Answers

An answer key heading ends the questions: everything after it is scanned with ANSWER_KEY_ENTRY for pairs like 1. C or 2-D. Options must arrive in order (A, then B, then C), so a line that happens to start with a later letter, such as "C. Smith wrote", is not taken as a choice. A new numbered line starts a new question only once the current one has options, so a numbered list inside a stem stays part of it. Continuation lines join the stem, the last option or the explanation, depending on what came last. A question survives with two to five options. Its answer comes from its own answer line, else the key, else it is None. Parsed questions are origin: "extracted" and have no topic or difficulty.

The model

questions_from_llm imports the agent's get_llm_client lazily, so the parser still works where the agent's dependencies are missing, and returns an empty list when OPENROUTER_API_KEY is not set. It splits the text into 12,000-character chunks, keeps the first four, and sends them in parallel with temperature 0.3. The prompt asks the model to extract every multiple-choice question exactly, to give correctAnswer only when the material states it, and, with generate, to write up to eight original questions per chunk with fromMaterial: false.

_normalize_llm_question applies the same honesty test as the question engine: a question counts as extracted only if the model said so and the first 50 normalized characters of its stem appear in the chunk. A generated question without a valid answer is dropped, because it cannot be reviewed into shape. An extracted one without an answer is kept with correctAnswer: None.

Review

QuestionUpdate accepts question, options, correct_answer, explanation and status. update_question merges the change over the stored row and rejects an answer outside the options (400) and an approval without an answer (400). approve_all approves the rows with an answer and returns approved and needs_answer counts. delete_material deletes the questions and then the material; the foreign key cascade would do the first step anyway.

12.5The client

The materials page

/materials starts from the exam and section in getExamPrefs() and loads the list. The form has exam and section toggles, a file input, a textarea whose placeholder shows the expected format, a name, and a checkbox "Also write new questions from this material" that sets generate. apiClient.uploadMaterial builds a FormData and calls fetch directly, so the browser sets the multipart boundary; the generic request helper would force a JSON content type.

After an upload the new material opens in the review pane. Each question is a QuestionReview card with a "Needs review" or "In your games" chip, a "Written by AI" chip for generated questions, and its choices as buttons. Tapping a choice sets correct_answer. "Approve for games" is disabled until an answer exists and toggles to "Take out of games". "Approve all with answers" calls the bulk route. The page only edits the answer and status; editing text through the API is possible but has no UI.

The mock exam page

/mock holds three components behind one state machine in MockExamPage.

Setup picks exam, section and a length. questionCount turns the length into a number from MODULE_QUESTIONS, the real module sizes:

SectionQuick checkOne moduleFull section
SAT Math102244
SAT Reading & Writing102754
GRE Quantitative101224
GRE Verbal101224

The time shown is the count times the section's secondsPerQuestion from chapter 6, in whole minutes. "Start the clock" saves the exam and section to the preferences and calls fetchAIQuestions(count) with no pace, so the engine applies no length filter and includes the user's approved custom questions.

Exam renders full screen, outside the dashboard layout. One clock, computed from Date.now() every 500 ms, counts down questions.length * secondsPerQuestion; at zero it finishes with whatever is answered, read through a ref so the timer sees the latest answers. The clock turns coral under five minutes or 15 percent of the total, whichever is smaller, and can be hidden. Questions with a passage use a two-column layout. The player can mark a question for review, jump through a navigator grid that marks answered, unanswered and flagged questions, open the Calculator on quant sections, and finish early through a confirmation that counts unanswered questions. Nothing is graded until the end.

Results shows correct count, accuracy, time used and an estimated score: a straight line across SCORE_RANGE (200 to 800 for an SAT section, 130 to 170 for a GRE section), rounded to 10 on the SAT and 1 on the GRE. The page says plainly that real scores are equated and this is only a marker. Below that are topics sorted weakest first and every question in a <details> element with the correct answer, the player's answer and the explanation.

On finish, finish also builds a GameAnalytics object and calls apiClient.saveScore('mock-exam', ...): score is correct answers times 100, each attempt gets the average time per question in milliseconds, and the longest correct streak goes in streakInfo. Errors are logged, not shown. The type is imported from frontend/games/whackamole/types, a leftover of where the shape was first written.

12.6How it works

  1. A student pastes a ten-question worksheet with an "Answer Key" at the end and leaves the checkbox off.
  2. parse_questions finds ten questions and takes their answers from the key. The model is not called.
  3. Ten pending rows are saved. The page opens them; the student clicks "Approve all with answers".
  4. The next time a signed-in game or mock exam for that exam and section asks for questions, load_custom_questions returns up to half the requested limit from these rows, each with source: 'custom' and sourceName set to the material's name, so the question panel shows "From" and the material name.

With no OPENROUTER_API_KEY, step 2 is all there is: the checkbox does nothing and unnumbered notes produce a 422. Custom questions still appear in the GRE when no other source is available, which makes them the main way to get real GRE questions into a keyless setup.

12.7Edge cases and tests

  • Pasted text is not capped. MAX_TEXT_CHARS applies only inside extract_text; a large paste goes to the parser in full.
  • The whole file is read before the size check. On Vercel the platform limit stops oversized bodies first; elsewhere the server holds the bytes in memory.
  • Only the first 48,000 characters reach the model. The parser sees up to 400,000.
  • Unhandled rejections. On the materials page, delete question, approve all and delete material have no try; a failure shows nothing to the user.
  • The file input is not cleared. After an upload setFile(null) resets state, but the uncontrolled input still shows the old file name.
  • Unreachable mock error. The mock page shows an error when no questions load, but fetchAIQuestions always falls back to the bank, which is never empty. With the backend down, a 54-question full section silently becomes a 9-question exam, with the clock scaled to match.
  • The SAT blurb overstates. Setup says SAT questions are official ones. Custom questions and, when the College Board falls short, model questions can be mixed in.
  • Mock exams change game settings. Starting one writes its exam and section to exam_prefs.
  • No resume. Exam state is React state; a reload loses the attempt.
  • Delete is idempotent. DELETE /api/materials/questions/{question_id} returns success for an id that does not exist.

There are no automated tests. parse_questions is the obvious first target: it is a pure function with many formats to pin, including answer keys, out-of-order letters and multi-line options.

Check yourself

Where is the uploaded PDF stored?

Nowhere. It is read in memory, turned into custom_questions rows and discarded. The materials row holds only a name, owner, exam and section.

When is the model called during an upload?

When generate is true, or when the parser found no questions, and only if OPENROUTER_API_KEY is set.

Why can a generated question never be saved without an answer, while an extracted one can?

An extracted question's answer may be in the student's head or answer sheet, so review can supply it. A generated question with no answer has nothing to check against, so _normalize_llm_question drops it.

How does the mock exam's clock length follow from the exam?

It is the number of questions actually loaded times the section's secondsPerQuestion, so a shorter set gets a shorter clock.

The backend uses the service role key. What stops one user reading another's material?

The routes filter every query by the caller's user_id and _own_material 404s on foreign ids. RLS would only apply to a client using a user's own token or the anon key.
