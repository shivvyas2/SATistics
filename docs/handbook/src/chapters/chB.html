Appendix B

BDecisions

This is a log of the design and engineering decisions that can be read off the code. Each entry gives the decision, the reason (from a comment in the code where there is one), and the consequence a contributor lives with. None of them is sacred. If you change one, change the entry too.

B.1A separate FastAPI backend

Decision. All data access and every outside call runs in a Python FastAPI app in backend/, deployed as its own Vercel project. The Next.js app has no API routes.

Reason. The question pipeline is Python: the openai client for OpenRouter, ddgs for DuckDuckGo, pypdf for uploads, and httpx for the College Board and YouTube. Keeping secrets and slow work off the browser and out of the page server keeps the frontend a static-ish client.

Consequence. Two deploys, two sets of environment variables, and CORS: ALLOWED_ORIGINS must name the frontend's origin. The frontend must be built with NEXT_PUBLIC_API_URL pointing at the backend. A change that spans both needs both deployed.

B.2Supabase for auth and data, behind the backend

Decision. Supabase provides Auth and Postgres. Only the backend talks to it, through one client built by Database.get_client, which prefers SUPABASE_SERVICE_ROLE_KEY.

Reason. One client with full rights is simple: no per-request client, no RLS to reason about in each query. The comment in utils/database.py says it plainly: the "service role key bypasses RLS".

Consequence. The RLS policies in backend/database/*.sql are defence in depth only. Isolation between users depends on every query filtering on user_id. The frontend's @supabase/ssr and @supabase/supabase-js dependencies are unused.

B.3A bearer token in localStorage and a cookie

Decision. The Supabase access token is returned by /api/auth/login, stored by ApiClient.setToken under auth_token in localStorage and a seven-day cookie, and sent as Authorization: Bearer. middleware.ts checks only that the cookie exists. AuthService.get_user decodes the JWT without verifying its signature and checks exp.

Reason. The cookie exists so the edge middleware can redirect signed-out visitors before a page renders; the comment in setToken says "Also set cookie for middleware auth check". Decoding without a network call keeps every request fast.

Consequence. No refresh: when the token expires, calls fail with 401 until the student logs in again. And because the signature is not checked while the backend holds the service-role key, a forged token is trusted. Verifying the JWT is the most important open fix in the codebase.

B.4Official questions first, then the LLM, then an offline bank

Decision. ExamLearningAgent.generate_questions takes SAT questions from the College Board Educator Question Bank (CollegeBoardSource). Any shortfall, and every GRE question, comes from one LLM call that is given up to four web pages of practice questions (WebQuestionSource.find_pages) and told to extract real questions first and write the rest. If the backend returns nothing, fetchAIQuestions falls back to getBankQuestions in frontend/lib/questionBank.ts.

Reason. The landing page promises questions "Drafted in the real format" and "Checked against the web". An LLM alone invents plausible but wrong questions; real sources fix that where they exist. The offline bank means a game always starts, even with no API key.

Consequence. A question is labelled web only if the first 50 normalized characters of its stem or passage appear on the cited page (_normalize_llm_question); otherwise it is ai. Every question carries source, sourceName and sourceUrl so the UI can say where it came from. One LLM call is capped at MAX_LLM_QUESTIONS (25). The offline bank is small: nine questions per section, 36 in all.

B.5Question length matched to the game

Decision. Games have a pace. gamePace marks squid-game as deep and every other game as quick, and the backend filters with is_quick_question and _fits_pace.

Reason. The comment in question_sources.py: "Fast games need questions that can be read and answered in seconds; slow games take the long passages and multi-step problems."

Consequence. Quick games never see reading passages, so verbal practice in them is limited to short skills (QUICK_SKILLS). The College Board fetch oversamples five times for quick games because so many candidates are dropped.

B.6Weak topics decided per game, by fixed thresholds

Decision. GameService._update_user_stats marks a topic weak below 50 percent accuracy in the game just played and strong at 80 percent or more, and moves topics between the two lists.

Reason. The comment: "A topic moves between the lists as the player improves or slips."

Consequence. One bad game makes a topic weak, and one good game clears it. Topics in neither range keep whatever label they had. The dashboard and the agent both read these lists.

B.7Lessons as static content

Decision. The fifteen lessons are TypeScript constants in frontend/lib/lessons.ts, one per topic in COURSES, each with ideas, a worked example, traps and a quick check.

Reason. Lessons must be right, and they change rarely. Static content is reviewed in a pull request, costs nothing to serve, and needs no backend.

Consequence. Editing a lesson is a code change and a deploy. A new topic in COURSES needs a lesson in the matching array, or it has none.

B.8A video provider chain with a one-day cache

Decision. videos.py tries the YouTube Data API (YOUTUBE_API_KEY), then Serper (SERPER_API_KEY), then DuckDuckGo; the first provider with results wins. Results are cached in memory for CACHE_TTL_SECONDS (24 hours), ranked toward trusted channels and 3 to 25 minute lengths, with up to GREGMAT_SLOTS (3) GregMat videos first.

Reason. DuckDuckGo needs no key but rate limits; the paid providers are reliable but optional. The module docstring explains the ranking: lesson-length videos from established test-prep channels.

Consequence. With no keys set, videos still work, slowly and sometimes not at all. Only non-empty results are cached, "so a rate-limited search is retried next time". The cache is per process, so each Vercel instance warms its own.

B.9Profiles in a table, with a pending-profile flow

Decision. Profiles live in profiles, keyed by user_id, saved by an upsert in PUT /api/profile. When signup returns no session (email confirmation on), the profile is parked in localStorage as pending_profile and saved on first login.

Reason. The comment in frontend/lib/profile.ts: "When Supabase requires email confirmation, signup returns no session, so the profile can't be saved yet."

Consequence. A student who confirms and logs in on another device has no profile and is asked again. Usernames are unique; a clash is a 409, and signup or login sends the student to /profile?setup=1 rather than failing.

B.10Lesson progress in localStorage

Decision. "Mark as learned" writes to the learned_lessons key in frontend/lib/learnProgress.ts. So do exam preferences (exam_prefs) and high scores (arcade_hi_<gameId>).

Reason. The file's comment: "Kept in this browser only." It needs no table, no endpoint and no sign-in.

Consequence. Progress does not follow the student between browsers. Moving it to a table is a small, self-contained change.

B.11Mock exams saved as game sessions

Decision. app/mock/page.tsx saves results with saveScore('mock-exam', ...), in the same GameAnalytics shape as a game.

Reason. The comment: "Save it alongside game sessions so it feeds statistics and weak topics." No new table or endpoint.

Consequence. gameTitle special-cases mock-exam. Statistics mix mock exams with games.

B.12Uploaded questions need approval

Decision. Questions from uploads go into custom_questions as pending. Only approved ones are served, and they make up at most half of a game's set (limit // 2 in get_questions).

Reason. Parsed and LLM-extracted questions can have the wrong or missing answer (correct_answer is nullable). The student is the only one who can confirm them.

Consequence. Uploading has a review step. The rest of every set still comes from the agent, so the student's own material never crowds out real exam questions.

B.13A neo-brutalist and glass design system

Decision. The site's look is thick ink outlines with hard offset shadows (brutal, brutal-sm, brutal-lg in tailwind.config.js) combined with frosted glass panels, over a paper background, in a five-colour palette: paper, ink, cobalt, lime, coral.

Reason. The comment in app/globals.css: "SATistics theme: brutalist outlines with frosted glass panels". It reads as a game, not a textbook.

Consequence. Use the component classes in globals.css (.brutal, .glass, .btn) and the Tailwind tokens rather than raw colours. The in-game screens use a separate arcade skin with the Press Start 2P font from lib/arcade.ts.

B.14Game covers drawn as inline SVG

Decision. components/brand/GameCover.tsx draws each game's cover as SVG in the site palette, with a FALLBACK for unknown ids.

Reason. The file's comment: "Illustrated cover art for each game, drawn as SVG in the site palette." No image assets to license, load or keep in sync with the palette.

Consequence. A new game needs a cover entry in COVERS, written as SVG.

B.15Schema as hand-run SQL files

Decision. The schema lives in backend/database/*.sql, run by hand in the Supabase SQL editor. There is no migration tool.

Reason. Few tables, one environment, one maintainer.

Consequence. Order matters and nothing records what has been applied. reset.sql recreates the four core tables but not materials or custom_questions, so after a reset run add_materials.sql again.

B.16The backend as one Vercel Python function

Decision. backend/vercel.json rewrites every path to /api/index, and backend/api/index.py exposes the whole FastAPI app.

Reason. One deploy target for both apps, no server to run.

Consequence. In-memory caches are per instance and lost on cold starts. Long question builds (web search plus an LLM call) run inside a single function invocation. The Docker, Fly, Railway and Render configs in backend/ are left over and not used.
