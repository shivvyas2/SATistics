Chapter two

2Architecture

SATistics is three pieces: a Next.js 14 frontend that runs the pages and the games in the browser, a FastAPI backend that owns every decision touching data or an outside service, and a Supabase project that holds identity and every table. The browser never talks to Supabase. It talks to the backend with a bearer token, and the backend talks to Supabase with the service-role key. Everything else in this chapter follows from that one boundary.

This chapter is the map. It names the pieces and the outside services, lays out the repository, follows one request from a click to a database row and back, shows how the login token travels, lists where each kind of state lives, and marks the code in the tree that nothing runs, so you can ignore it. Where the code and this handbook disagree, the code is right.

2.1The three pieces

The frontend is frontend/: Next.js 14 with the App Router, React 18, TypeScript, Tailwind CSS, and Three.js for the 3D games. Almost every page is a client component ('use client'), and all data comes from the backend through one class, ApiClient in frontend/lib/api/client.ts, exported as the singleton apiClient. The only server-side code the frontend runs is frontend/middleware.ts, which checks for a cookie, plus metadata routes (app/robots.ts, app/sitemap.ts). There are no Next.js API routes.

The backend is backend/: FastAPI on Python, built in backend/src/main.py. It mounts eight routers, each in backend/src/api/, and most of them hand off to a service in backend/src/services/.

Supabase provides two things: Auth (email and password users in auth.users) and Postgres. The schema is plain SQL in backend/database/, pasted into the Supabase SQL editor by hand; there is no migration runner. schema.sql creates game_sessions, question_attempts and user_stats; add_profiles.sql adds profiles; add_materials.sql adds materials and custom_questions; reset.sql drops and recreates the first four. Every table has row level security enabled with owner-only policies, but the backend connects with the service-role key, which bypasses those policies. The backend enforces ownership itself, by filtering every query on the caller's user_id.

2.4A request, end to end

Follow one click: a signed-in student on /games/zombie/select presses play.

  1. The page. The select page has already written the student's choice of exam, section and question count with setExamPrefs. It navigates to /games/zombie. middleware.ts sees the auth_token cookie and lets it through.
  2. The game container. app/games/[gameId]/page.tsx renders GameContainer, which hands zombie to ZombieGameContainer. That component calls fetchAIQuestions(examPrefs.questionCount, undefined, gamePace(GAME_ID)).
  3. The client. fetchAIQuestions reads the prefs and calls apiClient.getAIQuestions, which builds GET /api/questions/?use_agent=true&limit=10&use_web_search=true&exam=sat&section=quant&pace=quick. The private request method prefixes NEXT_PUBLIC_API_URL, adds Authorization: Bearer <token>, and turns any non-2xx into an Error carrying the response's detail.
  4. The router. get_questions in src/api/questions.py resolves the caller with get_current_user_optional, so the route also works signed out (as a guest with an all-zero user id). It loads up to half the set from the student's approved material with load_custom_questions, then asks an ExamLearningAgent for the rest.
  5. The service. generate_questions reads the student's weak topics from user_stats and question_attempts through SupabaseAgentOps. For the SAT it calls CollegeBoardSource.fetch; any shortfall, and all GRE, goes to _questions_from_llm, which may first search the web for practice pages. Every question carries a source of official, web or ai.
  6. The response. The router validates each question against the Question model, shuffles, and returns { questions, total }. If the agent throws, the router returns just the custom questions.
  7. The fallback. Back in the browser, an error or an empty list makes fetchAIQuestions return getBankQuestions(exam, section, pace) from the offline bank. The game always starts.

When the game ends, the reverse trip is shorter. The container builds a GameAnalytics object and calls apiClient.saveScore. POST /api/games/save-score requires a user (get_current_user), and GameService.save_game_session inserts one game_sessions row, one question_attempts row per question, and updates user_stats.

Two requests skip request. uploadMaterial calls send without a JSON Content-Type so the browser can set the multipart boundary. And the backend's /api/auth/signup and /api/auth/login have explicit OPTIONS handlers in addition to the CORS middleware, which allows the origins in ALLOWED_ORIGINS plus localhost on ports 3000 and 3001.

2.5How the login token travels

There is one credential: the Supabase access token, a JWT. It is issued by Supabase, passed through the backend to the browser, kept in two places there, and sent back on every call.

  1. Issued. AuthService.login calls sign_in_with_password on a throwaway client from Database.new_auth_client() and returns the access token, the refresh token and expires_at (Unix seconds), all three carried by TokenResponse. AuthService.signup returns them only when email confirmation is off.
  2. Stored. ApiClient.setSession writes the three values to localStorage under auth_token, auth_refresh_token and auth_expires_at, and the access token to an auth_token cookie with path=/, max-age of COOKIE_MAX_AGE_SECONDS (400 days) and SameSite=Lax. The cookie only tells the middleware someone is signed in, and every refresh renews it. On construction the client reads localStorage, falling back to the cookie for the access token.
  3. Checked by Next.js. middleware.ts only checks that the cookie exists. It does not decode or validate it. Its matcher skips _next assets, images and api paths.
  4. Sent to the backend. Every call carries Authorization: Bearer. FastAPI's HTTPBearer(auto_error=False) extracts it, and get_current_user answers 401 with "Missing authorization token" or "Invalid or expired token".
  5. Verified. AuthService.get_user asks Supabase about the token with auth.get_user(token) on a dedicated client that never signs in, and returns { id, email }. A forged, expired or revoked token gets None, so 401. Accepted tokens are cached in _verified_tokens for at most VERIFIED_TOKEN_TTL (300 seconds) and never past the token's exp.
  6. Refreshed. ApiClient.send posts the refresh token to /api/auth/refresh when the access token expires within 60 seconds, and once more after a 401, then retries the call. Concurrent callers share one refresh.
  7. Cleared. logout posts to /api/auth/logout, which revokes the session in Supabase on a best-effort basis, and then always calls setSession(null), removing the keys and expiring the cookie. DashboardLayout also calls clearAccountCache.

A session ends when Supabase refuses the refresh token. The client then clears its tokens, fires SESSION_ENDED_EVENT (which clears the useAccount cache) and, on a protected path, sends the student to /login?expired=1 with a redirect back. A network failure during a refresh does not sign anyone out.

On Vercel each function instance has its own backend caches.

2.7Deployment shape

Both apps deploy to Vercel as separate projects. The backend's vercel.json rewrites every path to /api/index, and backend/api/index.py adds the backend folder to sys.path and imports app from src.main, which Vercel's Python runtime serves as ASGI. backend/.vercelignore keeps .env, the shell scripts, database/ and the other hosts' configs out of the upload. The frontend learns where the backend is from NEXT_PUBLIC_API_URL, baked in at build time by next.config.js, defaulting to http://localhost:8000. The backend must list the frontend's origin in ALLOWED_ORIGINS. Locally, start_local.sh runs both.

2.8Code that nothing runs

The repo grew out of a hackathon project and still carries pieces of earlier designs. None of the following is reached from a page or a route. Do not extend them, and do not be misled by them when reading.

  • TypeScript under backend/src/, such as index.ts, api/games.ts, config/supabase.ts and services/gameScoreService.ts. They describe a Node backend that was never built; there is no package.json in backend/ to compile them. The live equivalents are the .py files beside them.
  • Other hosts' configs: backend/Dockerfile, fly.toml, railway.json, render.yaml. Production is Vercel.
  • The rewrite in frontend/vercel.json to a placeholder Railway URL. The client calls the backend by absolute URL, so /api/* on the frontend is never requested.
  • frontend/games/GameRenderer.ts and frontend/games/mario/. GameContainer only uses the renderer for games without their own container, and the only such game, mario, is not in lib/games.ts.
  • Unused components: components/AuthButton.tsx and components/GameCard.tsx are imported nowhere.
  • Unused dependencies: @supabase/ssr and @supabase/supabase-js in frontend/package.json. The frontend never talks to Supabase.
  • Unused backend methods: ExamLearningAgent.update_performance and get_learning_insights, and the save_* and update_user_stats methods of SupabaseAgentOps they call. Scores are saved by GameService. GET /api/questions/topics and apiClient.getQuestions and getTopics have no caller, and GET /api/questions/ without use_agent=true returns an empty list.

The older architecture notes and test script that once sat at the repo root have been removed; this handbook replaces them.

  7. frontend/lib/api/questions.ts, the fallback to the offline bank.
  8. backend/database/schema.sql, add_profiles.sql, add_materials.sql.
  9. backend/vercel.json and backend/api/index.py, how it is hosted.

Check yourself

The RLS policies say users can only see their own rows. Why does that not protect the backend's queries?

Database.get_client prefers SUPABASE_SERVICE_ROLE_KEY, and the service role bypasses RLS. The backend's own .eq("user_id", ...) filters are what keep users apart, so a new query that forgets the filter leaks data.

A token expires while the student is on the dashboard. What do they see?

Usually nothing. The client refreshes the token a minute before it expires, or after a 401, and retries the call. Only if Supabase refuses the refresh token does the session end: the client signs out and sends them to /login?expired=1, which shows a "Your session ended" notice.

OpenRouter is down. Does a GRE game still start?

Yes. _questions_from_llm returns an empty list, the router returns only custom questions (possibly none), and fetchAIQuestions falls back to getBankQuestions, which has nine GRE questions per section.

Why does uploadMaterial not use the shared request method?

request always sets Content-Type: application/json. A multipart upload needs the browser to set the content type with its boundary, so it calls fetch directly with only the bearer header.
