Chapter eight

8The game framework

SATistics teaches through games, and every game is the same machine wearing a different costume: questions go in, a player answers them by doing something in a 3D scene, and an analytics object comes out. This chapter describes that machine. It covers how a game is registered, the three routes a player passes through, the container component that owns each game, the shared exam UI that every container borrows from, and how questions arrive and results leave. The one idea that shaped it is that the engine never touches React and React never touches the scene: they talk through a handful of callbacks and imperative methods.

This chapter describes the code on main at commit 9b9abf0. There is no plugin system and no game interface file. A "framework" here is a set of conventions that six games happen to follow, plus a few shared components in frontend/components/exam/ and frontend/components/arcade/. Where the games disagree with each other, this chapter says so, because the disagreements are where new contributors get caught.

8.1Intent

The first intent is that a game is practice, not a reward for practice. Answering is the gameplay: the player shoots the zombie wearing the answer, runs through the gate of the answer, stands on the pad of the answer. A question is never a modal that interrupts the game; it is the reason the game is moving.

The second intent is that every game uses the same questions and reports the same numbers. All of them fetch from one backend endpoint through lib/api/questions.ts, all of them fall back to the same offline bank, and all of them hand a GameAnalytics object to apiClient.saveScore. That is what lets the statistics pages and the "Your games" panel treat a Pac-Man round and a Squid Game round as rows in one table.

The third intent is that the exam stays visible. The newer games render the full question, passage and choices in a shared QuestionCard beside the action, pace themselves from the real exam's seconds per question, offer hints that rule out choices, and refuse to show the answer after a first miss so the question can come back later.

The split to remember is components/ versus games/. A file in frontend/games/ is an engine: plain TypeScript that owns a Three.js scene and knows nothing about React. A file in frontend/components/ is the React side: it fetches questions, constructs the engine, runs the animation frame loop and draws every piece of text on top of the canvas.

8.3Model

The registry

lib/games.ts exports games: Game[]. The Game interface lives, for historical reasons, in frontend/games/subway-surfers/types/game.ts: an id, a name, a description and a status of 'coming-soon' or 'available'. All six entries are 'available', and nothing in the app reads status. The array order is the catalogue order.

lib/gameMeta.ts holds what the catalogue actually shows. Its header comment says it is kept apart so the engine's Game type stays unchanged. Each entry in GAME_META has a display title, a genre (one of 'Action' | 'Arcade' | 'Runner' | 'Survival', listed in GENRES for the filter chips) and an answerBy sentence. gameTitle(id, fallback) resolves an id to a title and special-cases 'mock-exam', which is not a game but saves sessions under that id.

Exam preferences

lib/exam.ts defines ExamPrefs: exam ('sat' | 'gre'), section ('quant' | 'verbal') and questionCount, which must be one of QUESTION_COUNTS = [6, 10, 20]. They live in localStorage under exam_prefs; getExamPrefs() validates every field and falls back to { exam: 'sat', section: 'quant', questionCount: 10 }. EXAMS carries the real pacing per section, from 71 seconds per question for SAT Reading and Writing to 105 for GRE Quantitative. QUICK_SECONDS_PER_QUESTION is 35, the budget for the quick-fire games. gamePace(id) returns 'deep' for ids in DEEP_GAMES, which is only ['squid-game'], and 'quick' for everything else; the backend uses it to choose short questions or passage questions.

Questions and results

A question is SATQuestion from lib/api/questions.ts: an id, question, options, a zero-based correctAnswer, topic, difficulty and explanation, plus optional passage, stem, skill, sanitized HTML variants and source fields. Whack-A-Mole and Balloon Pop import an older, narrower SATQuestion from their own types.ts; it is structurally compatible, and their containers cast to the full type when they need the HTML fields.

A result is GameAnalytics, which is defined in frontend/games/whackamole/types.ts and imported from there by every other game: gameId, score, accuracy (a percentage), correctAnswers, wrongAnswers, questionAttempts (one QuestionAttempt per answer, with timeSpent in milliseconds), topicPerformance, streakInfo.maxStreak and averageResponseTime. The backend mirrors it as a Pydantic model in backend/src/models/schemas.py. The newer games also return a review list (ZombieReviewItem, RunnerReviewItem, SquidReviewItem, PacManReviewItem), all the same shape: question, selected (null on a timeout), isCorrect, timeSpent.

8.4Routes

A player passes through three pages. app/games/page.tsx is the catalogue. It filters games by a search box and a genre chip, matching against the GAME_META title and answerBy, draws each card with GameCover, and links to /games/[id]/select. Its side panel, YourGames, calls useRecentSessions(50) from lib/sessions.ts and groups saved sessions by game_id to show plays and best score.

app/games/[gameId]/select/page.tsx is setup. It loads getExamPrefs() after mount, offers buttons for exam, section and question count, writes each change straight back with setExamPrefs, lists the section's topics from courseFor, and shows the real exam pace. The "Start game" button is a plain link to /games/[id]. Nothing is passed in the URL: the play page reads the same localStorage key.

app/games/[gameId]/page.tsx is a server component. It exports generateStaticParams over games, calls notFound() for any id not in the registry, and otherwise renders a fixed, black, full-screen div containing <GameContainer game={game} />. Everything below that is a client component.

8.5How it works

Dispatch

GameContainer holds a constant OWN_CONTAINER_GAMES listing all six ids, then a chain of if (game.id === ...) early returns that render each game's own container. The early returns come after a useEffect, because React requires hooks to run in the same order on every render; the comment in the file says so. Only when the id matches none of them does the component render a bare full-screen <canvas>, and the effect constructs a GameRenderer on it.

GameRenderer and BaseGame are the original design: an abstract class with init, update(deltaTime), render(ctx) and handleInput(key), driven by a generic loop that also forwards keyboard events and draws on a 2D overlay canvas. Its init() switch knows exactly one id, 'mario', and 'mario' is not in games, so the play page returns 404 before GameContainer ever sees it. In practice the canvas branch is unreachable. Every live game takes the container path.

The container pattern

ZombieGameContainer is the cleanest example, and the newer containers follow it closely. In order:

  1. A mount effect calls getExamPrefs(), reads the local high score with getHighScore, and calls fetchAIQuestions(count, undefined, gamePace(GAME_ID)). A cancelled flag guards the setQuestions in case the page unmounts first.
  2. A second effect waits for both the canvas ref and the questions, then dynamically imports the engine module with await import('@/games/zombie/ZombieGame'). The type import at the top of the file is import type, so Three.js and the engine stay out of the page's initial bundle.
  3. It constructs the engine with the window size, the canvas, the questions and a config of { questionCount, secondsPerQuestion }, stores it in a ref, and assigns the callbacks: onHudChange, onQuestionChange, onFeedback and onGameOver. Most are passed React state setters directly.
  4. It adds resize and keydown listeners and starts a requestAnimationFrame loop that computes deltaTime, caps it at 50 ms so a background tab does not cause a jump, and calls game.update(deltaTime) then game.render().
  5. The effect's cleanup sets cancelled, cancels the frame, removes the listeners and calls game.cleanup(), which disposes geometries, materials and the renderer.

Everything the player reads is DOM, not canvas: the score bar, the question card, the hint button, the calculator, the pause menu and the results modal. The engine pushes a snapshot of its state through onHudChange, throttled to one call per HUD_UPDATE_INTERVAL_MS (100 ms) in Zombie, Subway Surfers and Squid Game, and the container renders from that snapshot. Controls flow the other way through public methods on the engine held in gameRef: start(), setPaused(), setMuted(), skipFeedback(), and per-game verbs such as shootAt, moveLane or lockIn.

A constructor that reports too early. The newer engines call emitHud(true) from their constructor, before the container has assigned onHudChange. ZombieGameContainer works around it by calling game.setMuted(false) straight after wiring the callbacks, which re-emits the HUD. The engines that load assets asynchronously (Subway Surfers, Squid Game) emit again when loading finishes, so they do not need the trick.

Getting questions

fetchAIQuestions(limit, fallbackQuestions, pace) reads the exam and section from getExamPrefs() and calls apiClient.getAIQuestions, which issues GET /api/questions/ with use_agent=true, limit, use_web_search=true, exam, section and, when given, pace. If the call throws or returns no questions, it falls back to getBankQuestions(exam, section, pace) from lib/questionBank.ts, then to fallbackQuestions. A game therefore always gets a list, though it may be short.

fetchQuestionsWithCache(gameId, limit, fallback) wraps that with a five-minute sessionStorage cache keyed ai_questions_${gameId}_${exam}_${section}. Only Whack-A-Mole and Balloon Pop use it, and both ask for 50 questions regardless of the chosen question count. The other four call fetchAIQuestions directly with a count derived from the preference: Zombie asks for questionCount, Subway Surfers and Squid Game ask for twice that so difficulty can adapt, and Pac-Man asks for a fixed 20.

Timing and pacing

Every engine that has a clock receives it from the container. Zombie and Subway Surfers get QUICK_SECONDS_PER_QUESTION; Pac-Man gets it through setQuestions(questions, QUICK_SECONDS_PER_QUESTION); Whack-A-Mole imports the same constant inside the engine for its popDuration. Squid Game, the one deep game, gets EXAMS[exam].sections[section].secondsPerQuestion, the real exam's pace. Balloon Pop has no clock at all. Engines measure time from the deltaTime the loop gives them, so a paused game's clock stops; the exception is the 2-second setTimeout that Whack-A-Mole and Balloon Pop use between questions.

Saving results

When an engine calls onGameOver, the container stores the result in state, which renders GameOverModal, and records the local high score with recordHighScore(gameId, score) (Zombie, Whack-A-Mole, Balloon Pop and Pac-Man do; Subway Surfers and Squid Game do not). It then imports apiClient lazily and calls apiClient.saveScore(gameId, analytics), which posts { gameId, analytics } to /api/games/save-score. The endpoint depends on get_current_user, so a signed-out player's save fails; every container catches the error and logs it, and the modal is unaffected.

GameIntro is the pre-game card: cover art, a kicker, a two-part title, a summary, a list of { label, text } steps, a start button and a link back to /games. GameLoading shows the cover and a progress bar; pass progress={null} for an indeterminate pulse. Zombie uses the arcade equivalents instead: ArcadeFrame wraps the screen in the Press_Start_2P pixel font from lib/arcade.ts, sets --arcade-color and lays a CRT overlay on top; ArcadeStartScreen is the attract screen with "INSERT COIN".

QuestionCard renders the header (question number, skill, difficulty), the passage, the stem and the choices through QuestionContent, which sanitizes question HTML against an allowlist of tags including MathML. Choices are buttons only when onPick is passed; none of the current games passes it, because the answer is always picked in the scene. activeOption and activeLabel highlight a tentative pick (Subway Surfers passes the current lane and "YOUR LANE"). After an answer, feedback colours the choices, and if insight is set the card hides which choice was right and shows the nudge from insightFor instead, because the question will come back.

useQuestionHints(question) resets when the question changes. The first requestHint() adds a strategyHint and returns null; each later one adds an eliminationHint and returns the option it ruled out, which the container passes to the engine (eliminateZombie, eliminateLane, eliminatePad, eliminateAnswer) so the scene drops that target. eliminationHint always leaves the right answer and one other choice standing.

useViewShift(panelRef, isActive, setViewShift) measures the question panel and tells the engine how far to offset its camera so the action stays centred in the uncovered part of the screen: half the panel's width beside it at SIDE_PANEL_MIN_WIDTH (1024 px) and wider, half its height below it otherwise. A ResizeObserver re-measures as the panel grows with each question.

PauseMenu offers Resume, Restart (a full window.location.reload()), "Change exam or section" (back to the select page) and "Exit to games". ReviewList renders each review item in a <details>; for a missed question it shows the insight and a button to reveal the answer, so the review doubles as a second try. GameOverModal takes analytics, onRestart, optional title and subtitle, and children rendered above its buttons, which is where containers put ReviewList. It accepts an emoji prop it no longer shows, kept so old callers compile.

8.7Input and assets

Keyboard and touch

Input is wired by the container, not by a shared layer. Keyboard listeners go on window and ignore e.repeat; Space and the arrow keys call preventDefault() so the page does not scroll. P and Escape pause in the four games that listen for keys; Whack-A-Mole and Balloon Pop have no keyboard input and pause only from the menu button. Number keys 1 to 5 pick an answer in Zombie and Subway Surfers. Touch uses pointer events, never touch events: Zombie aims on onPointerMove and fires on onPointerDown; Subway Surfers and Pac-Man treat a pointer drag longer than SWIPE_MIN_DISTANCE (30 and 24 px) as a swipe; Squid Game and Pac-Man draw on-screen buttons, and Squid's holdKey helper maps pointer down and up to handleInput and handleKeyRelease, so a held button behaves like a held key. Whack-A-Mole and Balloon Pop listen for click on the canvas inside the engine and raycast against their meshes, which works for taps too. Canvases that take gestures carry touch-none.

Assets

Whack-A-Mole, Balloon Pop, Zombie and Pac-Man build their scenes entirely from Three.js primitives and CanvasTexture labels; they load no files. Subway Surfers loads a glTF map from /games/subway-surfers/assets/subway_surfers_maps/scene.gltf, the FBX character from /Flying.fbx with /Falling.fbx and /Falling Flat Impact.fbx, and three MP3s from the public/ root. Squid Game loads three FBX animations and three glTF models from /games/squid-game/assets, two textures from its squid-textures folder, and audio from /games/squid-game/audio. Anything under frontend/public/ is served from the site root; anything elsewhere is not.

8.8Performance

The heavy cost is download, not frame time. frontend/public/games is about 129 MB, of which Squid Game is 124 MB: the red_guy guard model alone is 43 MB, and the squid-textures folder is 72 MB although the engine reads only two images from it. Engines are imported dynamically so none of this, nor Three.js, lands in the catalogue's bundle.

On the frame side, the newer engines are frame-rate independent: they scale motion by dt and smooth with an exponential damp(rate, dt). Zombie, Subway Surfers and Squid Game cap the renderer's pixel ratio at 2; Pac-Man passes window.devicePixelRatio uncapped. HUD callbacks are throttled to 10 per second, because each one is a React state update. The older code does not follow these rules: Pac-Man moves Pac-Man and the ghosts by a fixed step per frame and calls onHudChange on every frame; Balloon Pop moves balloons per frame and runs its pop and particle animations in their own requestAnimationFrame chains, outside the game loop and outside pause.

8.9Edge cases

  • No backend. fetchAIQuestions falls back to the offline bank, so every game still starts. Saving then fails and is logged.
  • Signed out. The game plays normally; save-score requires a user, so the session is not stored and does not appear in "Your games". The local high score still updates.
  • Restart. Every restart is window.location.reload(). For the two cached games, a reload within five minutes reuses the same questions from sessionStorage.
  • Background tab. The capped deltaTime stops a returning tab from skipping time, except in Whack-A-Mole, whose loop does not cap it, so one long frame can expire the question.
  • Five choices. LANE_COLORS and LANE_LETTERS have five entries and the newer engines build one target per option. Whack-A-Mole and Balloon Pop always build four, so a fifth choice cannot be picked.
  • Fractional averages. The backend's GameAnalytics.averageResponseTime is an int under Pydantic 2. Whack-A-Mole and Balloon Pop send an unrounded mean, which can fail validation; the other four round it.

There are no automated tests for the games or the shared exam components.

Check yourself

Why does the "Start game" link carry no query string?

The setup page writes every choice to localStorage through setExamPrefs as it is made, and the container reads it back with getExamPrefs(). The URL only names the game.

Can GameRenderer run the Mario placeholder today?

No. 'mario' is not in games, so /games/mario calls notFound() before GameContainer renders.

Why do containers import the engine with import() inside an effect?

To keep Three.js and the engine out of the page bundle and off the server. The top of the file uses import type, which is erased at compile time.

Where does a hint's elimination become visible in the scene?

requestHint() returns the ruled-out option and the container passes it to an engine method such as eliminateLane, which hides that gate. The hook only manages text and the list of eliminated options.

Why would a game's session be missing from the stats page after a good round?

The player was signed out, the backend was down, or the analytics failed validation; all three are caught and only logged in the console.
