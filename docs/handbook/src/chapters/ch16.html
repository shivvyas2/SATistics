16Contributing

A change to SATistics travels a short road: an issue, a branch, a few focused commits, a pull request that passes CI, and a merge to main that Vercel deploys within minutes. The road is short because the codebase is split by area, so most changes touch one folder of the frontend, one router of the backend, or one chapter of this book. This chapter is the map and the rules of the road.

CONTRIBUTING.md at the repository root is the short version and the one GitHub shows to new contributors. This chapter agrees with it and adds the detail: which files belong to which area, what the checks prove and what they do not, the conventions you will see in the code, and how to change this handbook. CODE_OF_CONDUCT.md sets the expectations for how we treat each other, and SECURITY.md explains how to report a vulnerability privately instead of in a public issue.

For a first change, CONTRIBUTING.md suggests work that needs no deep knowledge of the rest of the system: a lesson in frontend/lib/lessons.ts, more questions in the offline bank in frontend/lib/questionBank.ts, tests for pure functions, accessibility in game overlays, or an issue labelled good first issue.

For anything bigger than a fix, open an issue first. The repository has three issue templates in .github/ISSUE_TEMPLATE/: a bug report, a feature request, and a new game proposal that asks how the player chooses an answer and which assets (with licenses) the game will use. Agreeing on an idea is cheaper than reworking a finished pull request. A new question type, topic or exam section always starts as an issue, because SAT and GRE content must follow the official domains listed in frontend/lib/courses.ts.

16.2Branches and commits

Branch from main for every change and open a pull request. Never push to main directly: both Vercel projects deploy it to production on every push (15.1), and nothing makes the deploy wait for CI. 

git switch main
git pull
git switch -c add-pac-man-hint-button
# ...edit, check, commit...
git push -u origin add-pac-man-hint-button

Commits follow the history that is already there:

  • Small and focused. One logical change per commit. A refactor and a feature are separate commits, and usually separate pull requests.
  • Imperative subject lines that say what changed for the user: "Add hints, material uploads, arcade skin and touch support to the games", "Fix backend Vercel deployment". Not "updated files". A scope prefix such as fix(learn): or feat(games): is welcome but not required.
  • A body when the why is not obvious. Recent commits use a short bulleted body listing each user-visible change. Explain causes, not just effects: "Remove root vercel.json: its invalid rootDirectory field failed every backend build".
  • No AI co-author trailers. If a tool helped, you are still the author and the one responsible for the change.
  • No secrets, ever. Not in code, docs, fixtures or screenshots. CI runs a gitleaks scan on every pull request, but it is a net, not a plan.

16.3Checks before a pull request

Run what CI runs. .github/workflows/ci.yml has three jobs; run the first two yourself before you push. 

cd frontend
npm run lint          # next lint with next/core-web-vitals
npx tsc --noEmit      # the whole project under strict mode
npm run build         # catches server/client boundary and route errors
cd backend
pip install -r requirements.txt
uvicorn src.main:app --reload --port 8000
curl http://localhost:8000/api/health/
CI jobStepsWhat it proves
FrontendNode 22, npm ci, npm run lint, npx tsc --noEmit, npm run build with NEXT_PUBLIC_API_URL=http://localhost:8000The frontend lints, type-checks and builds
BackendPython 3.12, pip install -r requirements.txt, python -c "from src.main import app"Every module imports and every router registers
Secret scangitleaks/gitleaks-action over the full history, pull requests onlyNo key-shaped string entered the branch

Note what the backend job does not prove. Importing the app does not call a route, touch Supabase or run a query. A typo inside a handler passes CI. So for any backend change, start the server, call the route you changed (the interactive docs at /docs are the quickest way), and then click through the screens that use it, on a desktop window and at phone width.

16.4There are no tests yet

SATistics has no automated test suite. There is no test runner in frontend/package.json, no test dependency in backend/requirements.txt, and no test files. Lint, the type checker, the build and the import check are the only automated guards. Say so in your pull request instead of implying coverage that does not exist, and describe how you verified the change by hand.

Adding tests is one of the most useful contributions you can make. The best first targets are pure functions with no network or DOM, where a test is short and a regression would be silent:

  • Backend parsing and ranking. parse_questions and merge_questions in backend/src/services/material_parser.py; is_quick_question and normalize_text in question_sources.py; extract_json in agent.py; the duration parser, _mentions and _score in videos.py. pytest with plain function calls is enough.
  • Frontend logic. frontend/lib/exam.ts, frontend/lib/sessions.ts and getBankQuestions in frontend/lib/questionBank.ts. A small Vitest setup would cover these without a browser.
  • API contracts. FastAPI's TestClient against the routers with get_db and get_current_user overridden by dependency injection would test validation and auth checks without a real Supabase project.

A pull request that adds a test runner should also add it to ci.yml, so the tests keep running after the first one is merged.

16.5The pull request

.github/PULL_REQUEST_TEMPLATE.md asks for three things: what changed, why (link the issue with Closes #123), and how you verified it. Fill in all three. Before you ask for review, walk the checklist:

  • One change per pull request.
  • npm run lint, npx tsc --noEmit and npm run build pass in frontend/.
  • For backend changes, the server starts and /api/health/ responds, and you called the changed route.
  • You clicked through the affected screens on desktop and at phone width. Anything visual has a screenshot or a short recording.
  • No secrets, keys or personal data in the diff.
  • A new environment variable is read on the backend and documented with a placeholder in backend/.env.example (or frontend/.env.example, if it truly belongs in the browser, which should be rare).
  • A schema change is a new SQL file under backend/database/ and is folded into reset.sql, with RLS enabled and policies on every new table.
  • CHANGELOG.md has a line under "Unreleased" if a user would notice the change.
  • The handbook chapter for the area is updated if behaviour changed (16.8).

16.6Common changes, at a glance

Adding a game

A game is a class in its own folder under frontend/games/, a container component that mounts it, and three registrations. The steps, and the contract every game shares, are in chapter 8 and chapter 9. In outline:

  1. Open a "New game proposal" issue.
  2. Create frontend/games/<id>/. Canvas games extend BaseGame in frontend/games/BaseGame.ts, which declares init, update, render and handleInput; the 3D games use three.
  3. Add a container in frontend/components/ and a branch for it in GameContainer.tsx.
  4. Register the game in frontend/lib/games.ts and its title, genre and answerBy line in GAME_META in frontend/lib/gameMeta.ts.
  5. Get questions through frontend/lib/api/questions.ts, show them with the components in frontend/components/exam/, and save results with apiClient.saveScore. A game that builds its own question pipeline is hard to maintain.

Adding or improving a lesson

Lessons are static data. A topic must exist in a course's topics list in frontend/lib/courses.ts, and its lesson is an entry in frontend/lib/lessons.ts with a summary, ideas, a worked example, traps and a quick check, matching the Lesson interface at the top of the file. The topic name must match the topic names the question bank uses, or the lesson's practice link and videos will not line up. Chapter 10 covers the rest.

Adding an API route

  1. Add a handler to the router in backend/src/api/ that fits, or a new module with router = APIRouter() registered in backend/src/main.py with app.include_router(..., prefix="/api/<name>", tags=[...]).
  2. Declare request and response models in backend/src/models/schemas.py.
  3. Require a user with Depends(get_current_user) from src/api/auth.py, and take the database with Depends(get_db). Filter every query by current_user["id"]: the service-role client bypasses RLS, so the handler is the only thing keeping one user out of another's rows.
  4. Keep logic that is more than a query in backend/src/services/.
  5. Add a typed method to ApiClient in frontend/lib/api/client.ts.

Chapter 14 lists every existing route and its auth rule.

16.7Code style

There is no formatter configuration in the repository, so match the file you are editing. These are the conventions the code follows.

TypeScript and React

  • Strict mode. frontend/tsconfig.json sets "strict": true. Write real types; a handful of files still use any (for example the auth responses in lib/api/client.ts), and replacing them is welcome, adding more is not.
  • Path aliases. Import with @/lib/..., @/components/..., @/games/... and @/types/..., as configured in tsconfig.json, not with long relative paths.
  • App Router. Each page is frontend/app/<route>/page.tsx. Interactive pages and components start with 'use client'; keep the directive as low in the tree as you can. A new signed-in route also goes into protectedPrefixes in frontend/middleware.ts and the disallow list in frontend/app/robots.ts.
  • Components. Named function components with a Props interface above them, one main component per file, grouped by feature under components/ (exam/, learn/, brand/, arcade/). Shared data and helpers live in lib/, one concern per file.
  • Network. All API calls go through the single apiClient in lib/api/client.ts. Do not call fetch against the backend from a component.
  • Lint. ESLint extends next/core-web-vitals (frontend/.eslintrc.json).

Styling

  • Theme tokens. Use the colours in frontend/tailwind.config.js: paper, ink, mist, and cobalt, lime and coral with their soft variants. Use the shadows shadow-brutal, shadow-brutal-sm, shadow-brutal-lg and shadow-glass, and the font-display and font-serif families. Do not add raw hex values to components.
  • Component classes. Reuse the classes in frontend/app/globals.css: .btn with .btn-cobalt, .btn-ink, .btn-lime or .btn-paper, plus .brutal, .glass, .field and .chip.
  • Copy. Sentence case, plain verbs, no emoji in the interface. Chapter 4 has the full rules.

Python

  • Layers. Routers in src/api/ stay thin: validate, authorise, call a service, shape the response. Services in src/services/ hold the logic. Pydantic models live in src/models/schemas.py, and their field names are camelCase (gameId) because they mirror the TypeScript types.
  • Imports are absolute from the src package: from src.services.videos import find_topic_videos.
  • Type hints use typing (List, Dict, Optional, Literal). Keep code runnable on Python 3.9: no X | None unions and no match statements.
  • Docstrings open every module and route, in one plain sentence.
  • Blocking work such as a Supabase query or a DuckDuckGo search inside an async route runs through asyncio.to_thread, as questions.py and videos.py do.
  • Configuration comes from os.getenv with a documented default, and every new name goes into backend/.env.example.

Dead code to leave alone or remove deliberately

A few files are left over from the hackathon and are not used: the TypeScript files under backend/src/ (index.ts, config/supabase.ts, api/games.ts, services/gameScoreService.ts, types/), the frontend/games/mario/ folder, which no entry in lib/games.ts points to, and the backend/setup.sh and start.sh scripts, which call files that no longer exist. Do not build on them. Removing them is a fine pull request on its own.

16.8Updating this handbook

The handbook is part of the code. If your change alters behaviour a chapter describes, update the chapter in the same pull request. The source is in docs/handbook/src/: 

docs/handbook/
build.py             assembles index.html from src/, generates the contents
make-book.sh         runs build.py, render-pdf.sh, then render-epub.sh
render-pdf.sh        typesets the PDF in two passes for real page numbers
render-epub.sh       packs the Kindle edition with pack-epub.py
src/WRITING.md       the rules every chapter follows
src/chapters/        one HTML fragment per chapter, ch01.html to ch16.html, chA, chB
src/book.css         the stylesheet

Read src/WRITING.md before you edit. The rules that trip people up: every name, path and number must exist in the repository; no em dashes; no secrets or personal data; each chapter is well-formed XML with one root <section>, because the same fragment goes into the EPUB; and every id starts with the chapter stem. Check a chapter, then build: 

python3 -c "import xml.dom.minidom,sys; xml.dom.minidom.parseString('<div>'+open(sys.argv[1]).read()+'</div>')" docs/handbook/src/chapters/ch16.html
python3 docs/handbook/build.py      # warns on em dashes and unresolved links
./docs/handbook/make-book.sh        # index.html, PDF and EPUB

A new h3 appears in the contents automatically. A new chapter file also needs its stem added to the right part in the PARTS list at the top of build.py.

16.9Study notes

Read in this order

  1. CONTRIBUTING.md, the short form of this chapter.
  2. .github/workflows/ci.yml and .github/PULL_REQUEST_TEMPLATE.md, what runs and what you are asked.
  3. frontend/tsconfig.json, frontend/.eslintrc.json and frontend/tailwind.config.js, the rules the compiler and the design enforce.
  4. backend/src/main.py and one small router, backend/src/api/learn.py, as the pattern for a new route.
  5. frontend/lib/gameMeta.ts and frontend/components/GameContainer.tsx, where a new game is registered.
  6. docs/handbook/src/WRITING.md, before you touch a chapter.

Check yourself

CI is green on your backend pull request. What has it not checked?

Any route's behaviour. The backend job only imports src.main, so it proves modules load and routers register, nothing more. You have to start the server and call the route.

Why must a new backend query filter by current_user["id"] when every table has RLS?

The backend's client uses the service-role key, which bypasses RLS. The filter in the handler is the only boundary between users.

You add a signed-in page at /review. Which two lists change besides the page itself?

protectedPrefixes in frontend/middleware.ts and the disallow list in frontend/app/robots.ts.

Where does a schema change go?

A new SQL file under backend/database/, the same change folded into reset.sql, RLS and policies on any new table, and a note in the pull request that it must be run on production before merge.

Your chapter edit builds in the browser but stops build.py. What is the usual cause?

It is not well-formed XML: an unclosed tag, an unescaped & or <, or a void element that is not self-closed.
