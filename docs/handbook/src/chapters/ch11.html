Chapter eleven

11Dashboard, statistics and sessions

Every game and every mock exam ends the same way: the client posts one analytics object, the backend writes a session row, one row per question attempted, and an updated running total for the player. The dashboard and the statistics page are two views over those rows. This chapter follows a finished game into the database and back out onto the screen, including how the weak and strong topic lists are worked out and the places where the numbers are rougher than they look.

11.1Intent

The dashboard answers one question when you sign in: what should I do next? It names a focus topic, offers a game to practice it and a lesson to study it, and shows videos on it. Everything else on the page (the numbers, the recent sessions, the courses, the games you have not tried) supports that one suggestion.

The statistics page answers a different question: how am I doing? It shows totals, a right and wrong bar for every answer so far, an accuracy trend, the weak and strong topics, and a record per game.

The storage design behind both is deliberately simple. Raw history lives in game_sessions and question_attempts; a single user_stats row per player holds running totals so neither page has to aggregate history on every load.

11.3Model

The analytics object. Every game builds the same shape, checked on the server by GameAnalytics in schemas.py:

FieldTypeMeaning
gameIdstrThe game, repeated inside the analytics
scoreintPoints for the round
accuracyfloatPercent, 0 to 100, as the game computed it (the server ignores it)
correctAnswers, wrongAnswersintCounts for the round
questionAttemptslistquestionId, topic, difficulty, isCorrect, timeSpent (ms)
topicPerformancedictPer topic: correct, total, accuracy (percent)
streakInfodictFree-form; the server reads maxStreak
averageResponseTimeintMilliseconds

SaveScoreRequest wraps it as { gameId, analytics }. The outer gameId is the one stored.

Tables. backend/database/schema.sql creates three tables, all with row level security and all cascading from auth.users.

  • game_sessions: a uuid id, user_id, game_id, score, accuracy as DECIMAL(5, 4) (a fraction from 0 to 1), correct_answers, wrong_answers, max_streak, average_response_time and created_at. Indexed on user_id and on created_at DESC.
  • question_attempts: a uuid id, session_id (cascading from the session), question_id as an integer, topic, difficulty, is_correct, time_spent and created_at. add_user_id_to_attempts.sql adds a denormalized, not-null user_id, two indexes (user_id, and user_id, topic) and rewrites the policies to use it, so per-user topic queries skip the join.
  • user_stats: one row per user (user_id is unique) with total_games_played, total_score, total_questions_answered, total_correct, total_wrong, overall_accuracy (a fraction), favorite_game, weak_topics and strong_topics as TEXT[], and updated_at.

On the client, frontend/lib/sessions.ts declares GameSession with the same fields as GameSessionResponse, and GameRecord (gameId, plays, bestScore, lastPlayed) for the per-game rollup.

11.4The server side

Saving. POST /api/games/save-score in backend/src/api/games.py takes a SaveScoreRequest, resolves the user with get_current_user and calls GameService(db).save_game_session(user_id, game_id, analytics). A failure is a 500 with the error text; success returns { success: true, sessionId }.

save_game_session in backend/src/services/game_service.py does three things in order, each its own request to Supabase:

  1. Insert the game_sessions row. accuracy is recomputed by _accuracy as correct / (correct + wrong), or 0 when there were no answers, so the game's own percentage is never trusted. max_streak is streakInfo.get("maxStreak", 0).
  2. If there are attempts, insert all of them in one call with the new session_id and the user_id.
  3. Call _update_user_stats.

Any exception is caught and returned as { success: False, error }.

Weak and strong topics. _update_user_stats first classifies this round's topics from topicPerformance, working from the counts rather than the game's percentage (the comment notes that games report it as a percent). A topic with at least one question is weak if fewer than half were right, strong if at least 80 percent were, and neither in between.

If the player has no user_stats row yet, it inserts one with this round's totals and lists. Otherwise it adds this round to each total, recomputes overall_accuracy as total_correct / total_questions_answered, and merges the lists: 

merged_weak   = (existing_weak   - this_round_strong) | this_round_weak
merged_strong = (existing_strong - this_round_weak)   | this_round_strong

So a topic moves from weak to strong (or back) as soon as one round says so, and a topic that lands in the middle band keeps whatever label it had. The lists are sets converted to Python lists, so their order is arbitrary.

Favorite game is never computed. favorite_game exists in the table, the response model and the dashboard's types, but no code writes it, so it is always null. The dashboard falls back to the most recently played game (section 11.6). To make it real, compute the most-played game_id from game_sessions in _update_user_stats and write it with the other totals.

Reading. backend/src/api/stats.py has two routes. GET /api/stats/user returns the caller's user_stats row as UserStatsResponse, or an all-zero response with empty lists and an empty updated_at if there is no row. GET /api/stats/sessions?limit= returns the newest limit sessions (default 10), newest first, as a list of GameSessionResponse. Neither reads question_attempts.

The agent's view. SupabaseAgentOps in backend/src/services/supabase_agent_ops.py is a set of static methods over the same tables for the AI question agent in agent.py. Two are in use: get_user_performance reads user_stats and reports accuracy as a percent; get_topic_performance reads every question_attempts row for the user and aggregates total, correct, accuracy and avg_time per topic. That is the only place per-attempt history is read. The class also has save_game_session, save_question_attempts and update_user_stats, a second write path that expects a different, snake_case game_data dictionary and never updates topic lists. Their only caller, ExamLearningAgent.update_performance, is never called, so these three methods are dead code. Games save through GameService only.

11.5The client

Saving. Each game container (ZombieGameContainer, WhackAMoleGameContainer, CarnivalGameContainer, SubwaySurfersGameContainer, SquidGameContainer, PacManGameContainer) registers an onGameOver handler that shows the results screen (the four arcade-style games also record a local high score) and then calls apiClient.saveScore(gameId, analytics), logging any error to the console. The mock exam in frontend/app/mock/page.tsx builds the same object itself, with a score of 100 per correct answer and the game id 'mock-exam'. saveScore posts { gameId, analytics } to /api/games/save-score.

Reading. getUserStats() returns the stats object, or null on any error or an empty body. getRecentSessions(limit) returns an array, or [] on error. useRecentSessions(limit) in sessions.ts wraps the second in state that starts as null (loading).

recordsByGame(sessions) walks the sessions, which arrive newest first, and builds one GameRecord per game in a Map: plays counted, best score kept, and lastPlayed taken from the first (newest) session seen. Map insertion order makes the result most recently played first. timeAgo(iso) formats "just now", "n min ago", "n h ago", "yesterday" or "n days ago", rounding at each step.

11.6How it works

The dashboard, frontend/app/dashboard/page.tsx, loads the account, the stats and the last 20 sessions, and derives everything else.

  • Greeting. "Morning" before noon, "Afternoon" before 6 pm, else "Evening", plus the first word of the display name (or the email's local part). Under it, a test-day countdown if the profile has a future date, and the daily goal in minutes. An account without a profile gets a lime "Finish your profile" card.
  • The exam and its courses. The exam comes from the profile, defaulting to SAT; courses are the two COURSES for that exam.
  • Focus topics. weak_topics filtered to topics that belong to this exam's courses. focusTopic is the first of them, or the first topic of the first course (SAT Algebra, GRE Arithmetic) when there are none.
  • Next game. favorite_game if it is a known game, else the game of the most recent session, else 'whackamole'. Since favorite_game is always null today, this is in practice "the last thing you played".
  • Up next. A cobalt-soft card names the focus topic, says whether it is your weakest topic or a good place to start, and offers "Play game" and "Study the lesson". Playing calls practice(course), which stores the course's exam and section with setExamPrefs and pushes to /games/<nextGameId>/select. The game's cover fills the right side.
  • Numbers. Games played, accuracy (the stored fraction times 100) and questions answered, each with a skeleton until stats arrive.
  • Watch. RecommendedVideos asks for three videos on the focus topic through useTopicVideos and hides itself if none come back.
  • Recent sessions. Up to eight SessionCards, tinted lime-soft at 80 percent accuracy or more, white at 50 or more, coral-soft below, with right and wrong counts, best streak, an accuracy bar and the score. With no sessions, a dashed empty state links to the games.
  • The aside. The exam's courses as tiles (each starts practice), up to four focus topics with a "Practice" button, and "Haven't tried yet": up to four games whose id is not among the last 20 sessions, drawn with GameCover.

The statistics page, frontend/app/stats/page.tsx, loads stats and the last 50 sessions. Until both arrive it shows four skeleton tiles; if total_games_played is 0 (or stats failed) it shows "Nothing to show yet". Otherwise:

  • Four tiles: games played, accuracy, questions answered, and best streak, which is the maximum max_streak over the 50 loaded sessions.
  • "Every answer so far": a lime segment over a coral bar, sized by overall_accuracy, labelled with the totals.
  • AccuracyTrend, when there are at least two sessions: up to TREND_LENGTH (12) bars, oldest on the left, colored lime, cobalt or coral by the same 80 and 50 percent thresholds, each with a title naming the game.
  • Two TopicLists, "Work on these" and "Going well". Their empty hints state the rules in plain words: under half right, and at least four in five.
  • "By game" from recordsByGame, each linking to that game's select page, and the newest 15 sessions as a list.

11.7Edge cases and tests

There are no automated tests for this area. These are the behaviors to know.

  • Mock exams are sessions too. A mock exam is stored with game_id 'mock-exam'. When picking "Up next", the dashboard skips any session whose id is not in games, so a mock exam never becomes the suggested game. The stats page's "By game" card still links mock exams to /games/mock-exam/select, which renders "That game doesn't exist"; it should link to /mock instead.
  • Topic labels are jumpy. Labels come from single rounds, so one wrong answer in a topic marks it weak until a later round scores 80 percent or better on it. They are not computed from the attempt history, even though get_topic_performance could.
  • No transaction. If the attempts insert or the stats update fails after the session insert, the route returns 500 but the session row stays, and the totals miss that round. The client does not retry, so nothing is duplicated, but nothing is repaired either.
  • Lost updates. _update_user_stats reads the row, adds in Python and writes it back. Two games finishing at the same moment for one player (two tabs) can overwrite each other. A Postgres function doing the increment in one statement would fix it.
  • Silent failures. getUserStats returns null on error. The stats page then shows "Nothing to show yet"; the dashboard's number tiles keep their skeletons, because they treat null as "still loading".
  • Windows, not history. "Haven't tried yet" looks at the last 20 sessions and "Best streak" at the last 50, so a game played long ago can reappear as untried and an old streak can drop off.
  • Unbounded limit. /api/stats/sessions accepts any limit; the clients ask for 20 and 50. Add an upper bound with Query(..., le=...) if you expose it further.
  • Question ids are integers. question_attempts.question_id and QuestionAttempt.questionId are both integers; a question source with string ids must map them first or the whole save fails validation.
  • Leftovers. games.py declares an unused security = HTTPBearer(), and backend/src/api/games.ts, backend/src/services/gameScoreService.ts and backend/src/types/database.ts are TypeScript from an earlier design that the FastAPI app never loads.

To check the path by hand, finish a short game, then compare the new game_sessions row, its question_attempts and the user_stats row in the Supabase table editor against the results screen. A good unit test would call _update_user_stats with a stub client and assert the merged lists for a topic that moves from weak to strong.

Check yourself

A round has 3 Geometry questions and the player gets 2 right. Geometry was weak before. What is it after?

Still weak. Two out of three is about 67 percent, which is neither under 50 nor at least 80, so this round adds Geometry to neither list and the existing label stands.

Why does the server recompute accuracy instead of storing the game's value?

Games report accuracy as a percent while the columns hold a fraction from 0 to 1, and the counts are the source of truth. _accuracy derives it from correctAnswers and wrongAnswers.

The dashboard suggests the game you played last, not the one you play most. Why?

favorite_game is never written, so the fallback runs: the first record from recordsByGame, which is the most recent session's game.

Which endpoint reads question_attempts?

None. The stats routes read user_stats and game_sessions only; the attempts are read by SupabaseAgentOps.get_topic_performance for the question agent.

What happens to a player's totals if saveScore fails because their session ended?

Nothing is written. An expired access token alone is not enough: the client refreshes it and retries. But if the refresh token is refused, the request fails with 401 and the client signs out, so the round exists only on the results screen and in the local arcade high score.
