Chapter ten

10Learn: lessons and videos

The games test what you know; Learn teaches it. Every course topic on both exams has a short lesson: a summary, the key ideas, a worked example revealed one step at a time, the traps that cost points, and one quick check question. Beside it sits a column of YouTube lessons that the backend finds and ranks on demand. The lesson text is static TypeScript shipped with the frontend; the videos are the only part that touches the server.

10.1Intent

A student who misses three Advanced Math questions in a game should be one click from the idea they are missing. Learn is built for that. The hub opens on the exam from the student's profile, puts their weakest topic first, and marks each card "Needs work" or "Strong" from the same user_stats lists the dashboard uses. A lesson ends with "Practice in a game", which sets the exam and section and drops the student into the games list.

Lessons are written content, not data. Keeping them in frontend/lib/lessons.ts means they are reviewed like code, typed, versioned and rendered without a request. Videos are the opposite: they change, there are thousands, and a good one for "Standard English Conventions" is a search away. So the backend searches, ranks toward lesson-length videos from established prep channels, and caches the result for a day.

10.3Model

Courses. frontend/lib/courses.ts defines a Course as an exam, a section (quant or verbal), a title, a summary and a list of topics. The comment on topics matters: they are the official content domains and must match the topic names the question bank uses, because that is how weak topics from games line up with lessons. There are four courses:

Courseexam:sectionTopics
SAT Mathsat:quantAlgebra; Advanced Math; Problem-Solving and Data Analysis; Geometry and Trigonometry
SAT Reading & Writingsat:verbalInformation and Ideas; Craft and Structure; Expression of Ideas; Standard English Conventions
GRE Quantgre:quantArithmetic; Algebra; Geometry; Data Analysis
GRE Verbalgre:verbalText Completion; Sentence Equivalence; Reading Comprehension

courseFor(exam, section) finds one, falling back to the first course.

Lessons. frontend/lib/lessons.ts defines the Lesson interface: 

export interface Lesson {
  exam: ExamId
  section: SectionId
  topic: string
  summary: string
  ideas: { title: string; body: string }[]
  example: { prompt: string; steps: string[]; answer: string }
  traps: string[]
  check: { question: string; options: string[]; correctAnswer: number; explanation: string }
}

Content is written as LessonContent, which is Lesson without exam and section, in four arrays: SAT_MATH, SAT_RW, GRE_QUANT and GRE_VERBAL. BY_COURSE maps 'sat:quant' and so on to those arrays, and LESSONS is built by walking COURSES in order and stamping each piece of content with its course's exam and section. The result is 15 lessons, one per topic, in course order. Each has three or four key ideas, two to four example steps, two or three traps, and a check with four options on the SAT and five on the GRE, matching each exam's option_count in the backend. correctAnswer is a zero-based index.

Slugs. topicSlug lowercases a topic and turns every run of non-alphanumerics into one hyphen, so "Problem-Solving and Data Analysis" becomes problem-solving-and-data-analysis. lessonHref(exam, topic) builds /learn/<exam>/<slug>, and findLesson(exam, slug) reverses it by slugging every lesson's topic and comparing. "Algebra" exists on both exams; the exam segment keeps them apart.

Progress. frontend/lib/learnProgress.ts stores the set of learned lessons as a JSON array under the localStorage key learned_lessons. Ids come from lessonId(exam, topic), which is "exam:topic", for example "sat:Algebra". This progress is per browser, not per account; nothing is sent to the backend.

Videos. The Video shape is the same in schemas.py and client.ts: id, title, channel, duration (a clock string such as "12:04"), url, thumbnail, published (a date) and trusted. Nothing about videos is stored in the database.

10.4The server side

backend/src/api/learn.py is mounted at /api/learn and has one route, GET /videos. It requires a signed-in user through get_current_user and validates its query: exam must match ^(sat|gre)$, section must match ^(quant|verbal)$, topic is 2 to 80 characters and limit is 1 to 12 (default 6). It awaits find_topic_videos and returns VideoResponse; any exception becomes a 502 "Video search failed: ...".

backend/src/services/videos.py does the work in four stages.

1. Cache. The key is exam:section:topic with the topic lowercased. _cache is a module-level dict of (timestamp, ranked list); a hit younger than CACHE_TTL_SECONDS (24 hours) is sliced to limit and returned. The limit is not part of the key, so the dashboard's request for three and the lesson page's request for six share one search.

2. Queries. The exam and section display names come from EXAMS in question_sources.py. First comes a dedicated GregMat search, "GregMat GRE <topic>" for the GRE or "GregMat <topic>" for the SAT; only results whose channel is GregMat and whose title mentions the topic are kept. Then up to three general queries run in order: "<exam> <topic> lesson"; for the SAT "Khan Academy SAT <topic>", for the GRE "GRE <topic> strategy"; and "<exam> <section> <topic> explained". The loop stops early once 15 non-GregMat videos are collected. Queries run one at a time on purpose, because parallel queries get rate limited. Results are deduplicated by video id.

3. Providers. _search builds a chain and returns the first provider's non-empty result:

OrderProviderEnabled byNotes
1YouTube Data APIYOUTUBE_API_KEYsearch with videoEmbeddable=true, 15 results, then one videos call for durations and view counts. ISO durations become clock strings with _iso_to_clock.
2SerperSERPER_API_KEYPOST https://google.serper.dev/videos, 15 results. No view counts, so views are 0.
3DuckDuckGoalwaysDDGS().videos through the ddgs package, run in a thread with asyncio.to_thread. Up to 2 attempts with a 2 second backoff, since rate limiting shows up as an error rather than a status.

An httpx.HTTPError from YouTube or Serper is logged and the chain moves on. Every result passes through _video, which keeps only URLs that match the YouTube id pattern (so every result can be embedded), builds the canonical watch URL and the hqdefault.jpg thumbnail, parses the duration into minutes and marks the video trusted if its channel matches TRUSTED_CHANNELS: Khan Academy, College Board, ETS, Official GRE, GregMat, Magoosh, Scalar Learning, Princeton Review, Kaplan, PrepScholar, Supertutor, 1600.io and Target Test Prep. Single-word names must match a whole word of the channel; multi-word names match as substrings.

4. Ranking. _score adds:

  • 3 for a trusted channel;
  • 2 for a length of 3 to 25 minutes (fits in a study session), 0.5 for anything else up to 60 minutes, and minus 2 for longer (multi-hour livestreams); no change if the duration is unknown;
  • log10(views) / 3, so a million views is worth 2.

The list is sorted by score, then up to GREGMAT_SLOTS (3) GregMat videos that mention the topic are moved to the front. Only a non-empty result is cached, so a rate-limited search is retried on the next request rather than remembered as "nothing found".

10.5The client

The hub. frontend/app/learn/page.tsx renders inside DashboardLayout. It sets the exam from the profile once the account loads (SAT if there is none), and the SAT and GRE chips switch it with aria-pressed. It fetches getUserStats() for weak and strong topics and reads useLearned(). A lime progress bar shows "n of m learned" for the current exam.

FeaturedLesson picks, in order, the first lesson whose topic is weak, the first lesson not yet learned, or the first lesson. It renders a cobalt card with "Recommended: your weakest topic" or "Recommended next", an "Open lesson" button and, on the right, the single best video for that topic from useTopicVideos(..., 1). Below it, each course for the exam gets a heading and a grid of lesson cards with the summary, the number of key ideas and badges for "Needs work", "Strong" and "Learned".

The lesson. LessonPage resolves the lesson with findLesson from the route params and shows "That lesson doesn't exist." for an unknown slug. Otherwise it renders LessonView, keyed by the lesson id so all local state resets when you follow "Next". The article has six parts: a back link to the course, the title and summary; key ideas as glass cards; the worked example; the traps on coral-soft; the QuickCheck on cobalt-soft; and a footer with "Mark as learned", "Practice in a game" and a "Next: topic" link to the following lesson in the same course.

The worked example starts with one step visible. The button reads "Show next step" until all steps are shown, then "Show answer", and the answer replaces the button in a lime box. "Practice in a game" calls setExamPrefs with the lesson's exam and section, then pushes to /games.

VideoPanel is passed to the shell as its aside, and rendered again inline with xl:hidden so narrow screens still get it. It shows a skeleton while loading, VideosUnavailable if there is nothing, or the selected video with its title, VideoMeta and a list of the others as VideoRows. Picking another video sets started, so the new one plays immediately. A "Wider"/"Narrow" toggle widens the aside from 320 px to 440 or 560 px; the choice is remembered in localStorage under lesson_video_wide.

Video components. frontend/components/learn/Videos.tsx holds useTopicVideos(exam, section, topic, limit), which returns { videos, failed } where videos is null while loading. It keeps a module-level Map from exam:section:topic:limit to the request promise, so revisiting a lesson in the same visit costs nothing, and deletes a failed promise so the next visit retries. VideoPlayer shows the thumbnail with a lime play button and swaps in a youtube-nocookie.com embed with autoplay=1&rel=0 when clicked; no YouTube code loads until then. VideoMeta prints the channel, a "Prep channel" badge for trusted ones and the duration. VideosUnavailable says either "Video search is unavailable right now." or "No lesson videos found for this topic yet." and links to a YouTube search built by youtubeSearchUrl.

The quick check. QuickCheck takes a lesson's check. Options are lettered A to E. Once one is picked, all are disabled, the correct one turns lime with a check mark, a wrong pick turns coral, and the rest fade. "Correct." or "Not quite." and the explanation appear in a polite live region, with "Try again" to reset. The result is not recorded anywhere.

10.6How it works

A student with SAT on their profile who missed most Advanced Math questions in their last game opens /learn. The hub sets the exam to SAT, the stats call returns weak_topics containing "Advanced Math", and FeaturedLesson features it as their weakest topic. Its video hook asks /api/learn/videos?exam=sat&section=quant&topic=Advanced%20Math&limit=1.

On a cold cache the backend runs the GregMat query and up to three general queries through the provider chain, ranks every candidate it found, caches the list and returns the top one. The student opens the lesson. VideoPanel asks for six; the client has no entry for limit 6, so it calls the server, which answers from its cache instantly. The student steps through the example, answers the check, presses "Mark as learned" (now "sat:Advanced Math" is in localStorage) and then "Practice in a game", which leaves their exam prefs on SAT Math.

10.7How to add or edit a lesson

  1. Editing text is a change to the right array in frontend/lib/lessons.ts. Aim for four ideas and three short traps, keep the SAT at four options and the GRE at five, and make sure check.correctAnswer is the zero-based index of the right option. Use real typographic characters (the file already uses −, ×, ² and curly quotes) rather than markup; the fields render as plain text.
  2. Adding a topic to an existing course takes two edits. Add the topic name to that course's topics in frontend/lib/courses.ts, spelled exactly as the question bank spells it, so weak-topic matching and the dashboard's focus topics work. Then add a LessonContent object with the same topic to the course's array in lessons.ts. Its position in the array is its position in the course and decides what "Next" points to.
  3. Check the slug. Run the topic through topicSlug in your head: it must be unique within the exam. Two topics that differ only in punctuation would collide.
  4. Adding a course means a new COURSES entry, a new content array and a new BY_COURSE key of the form exam:section. A course with no BY_COURSE entry produces no lessons but still shows its heading on the hub with an empty grid. A new section also needs the backend's section pattern in learn.py and an entry in EXAMS in question_sources.py.
  5. Check the videos. Open the lesson and look at what the search returns. If the results are poor, the levers are the query templates and TRUSTED_CHANNELS in videos.py, not the lesson. Restart the backend to clear its cache.
  6. Run npm run type-check in frontend/. The Lesson type catches missing fields; it does not catch a wrong correctAnswer, so read the check once more.

10.8Edge cases and tests

  • No keys configured. With neither YOUTUBE_API_KEY nor SERPER_API_KEY, every search goes to DuckDuckGo, which rate limits. A cold lesson can then take several seconds (up to four searches, each with a possible 2 second backoff) and may return nothing; the panel says no videos were found and offers the YouTube search link. Nothing is cached, so the next visit tries again.
  • Serverless cache. _cache lives in process memory with no size bound. On a serverless deployment each instance has its own and loses it on a cold start, so the one-day TTL is a ceiling, not a promise.
  • Learned is per browser. Clearing site data or switching devices resets it, and two people on one browser share it.
  • Hub counts. Each course heading shows course.topics.length while the grid shows the lessons that exist for that section. They agree today because every topic has a lesson; if they ever diverge, the count will be wrong.
  • Weak topics across exams. Status badges match by topic name only. A weak "Algebra" from GRE games will also mark the SAT Algebra lesson as "Needs work".
  • Answer position. Nine of the 15 quick checks have option A as the answer. A student who notices will stop reading the options. When you write or edit a check, vary the position.
  • Unknown slug. /learn/sat/nope renders the not-found card inside the shell; it does not return a 404 status.

There are no automated tests. topicSlug, findLesson, _score, _iso_to_clock, _duration_minutes and _mentions are pure functions and the obvious first candidates.

Check yourself

Why is the video cache key on the server free of limit while the client's includes it?

The server caches the whole ranked list and slices it per request, so every limit can share one search. The client caches request promises, and a promise for one video cannot answer a request for six.

Why are the general queries run one after another instead of with asyncio.gather?

The free providers rate limit bursts. The comment in find_topic_videos says so, and serial queries also let the loop stop early once it has 15 non-GregMat videos.

What must be true of a new topic name for the dashboard to recommend its lesson?

It must appear in the course's topics and match, character for character, the topic the games report in question_attempts, since weak_topics comes from those reports.

A DuckDuckGo search hits a rate limit. What does the student see, and when is the search tried again?

The provider returns an empty list, the endpoint returns no videos, and the panel shows "No lesson videos found for this topic yet." with a YouTube search link. The empty result is not cached, so the next request searches again.

Where is "Mark as learned" stored, and what is its id for GRE Geometry?

In localStorage under learned_lessons, as "gre:Geometry".
