SATistics

Engineering Handbook

Shiv Vyas and contributors · Revision A

SATistics is SAT and GRE practice that plays like an arcade. Real-format exam questions ride inside six games, every topic has a lesson with a worked example and recommended videos, and a dashboard points each student at the topic they miss most. It is a Next.js frontend and a FastAPI backend on one Supabase project, deployed on Vercel, with an LLM and web search behind the question engine. This handbook is the single reference for how it is built, why it is built that way, and how to change it. It is written for contributors: pick the part of the app you want to work on, read its chapter, and every chapter ends with a reading order through the code and questions to check yourself against.

Chapter one

1What SATistics is

SATistics is a practice site for the SAT and the GRE that hides real-format exam questions inside arcade games. You shoot the zombie wearing the right answer, run through the right gate, pop the right balloon. Around the games sit short concept lessons with videos, a timed mock exam, a profile with a target score and a test date, and a page for turning your own study material into questions. The one idea that shapes it is that every answer you give is recorded by topic, and the topics you miss are the ones that come back.

This chapter describes the product as the code on main builds it. It is the map a new contributor needs before reading any code: who the site is for, what a session looks like, which exams and sections it covers, which screen lives at which route, and what it deliberately does not do. Chapter 2 takes the same product apart into its frontend, backend and database. The repository still carries an earlier name in places: the FastAPI title in backend/src/main.py is "NYU Hacks Arcade API", and the root README.md is headed "NYU Hacks Arcade". The product name, set in frontend/lib/site.ts as SITE_NAME, is SATistics, served at https://www.satistic.tech.

1.1The product in one paragraph

SITE_DESCRIPTION in frontend/lib/site.ts says it plainly: "Train for the SAT and GRE with arcade games built on real-format questions, concept lessons and videos." Each part of that sentence is a feature with its own code.

  • Arcade games. Six playable games, listed in frontend/lib/games.ts: Zombie Apocalypse, Whack-A-Mole, Balloon Pop (id carnival), Subway Surfers, Squid Game and Pac-Man. Each one asks exam questions as part of play, and the way you answer is the game's own mechanic. GAME_META in frontend/lib/gameMeta.ts records that mechanic for each game as answerBy, for example "Switch lanes and run through the right gate".
  • Real-format questions. SAT questions come first from the College Board Educator Question Bank, fetched live by CollegeBoardSource in backend/src/services/question_sources.py. Anything missing, and all GRE questions, come from an LLM that is handed web pages of practice questions to extract from and writes the rest in the official style. If the backend cannot answer at all, the browser falls back to an offline set of 36 questions in frontend/lib/questionBank.ts.
  • Concept lessons and videos. Fifteen lessons, one per course topic, written as static content in frontend/lib/lessons.ts. Each has key ideas, a worked example, the traps that cost points and a one-question quick check. Beside each lesson the backend finds YouTube videos for the topic.
  • Profiles with goals. A display name, a username, the exam, a target score, a test date, daily minutes and an avatar colour, stored in the profiles table.
  • A dashboard that greets you, counts down to your test date, suggests a game and a focus topic, and shows your recent sessions.
  • Mock exams. A timed section in test-day format at /mock, with no feedback until the end and a score report afterwards.
  • Your own material. Upload a PDF or text file, or paste text, and the backend pulls the multiple-choice questions out of it (and can write new ones from it). Questions you approve are mixed into your games.

1.2Who it is for

The person the code is written for is a student preparing for one of two exams, who finds a question bank dull and will play a game for longer than they would sit through a worksheet. The landing page, frontend/app/page.tsx, makes the pitch: "Every zombie, mole and balloon carries a real-format exam question. Answer right to win, and your weak topics come back until they aren't."

Two assumptions follow from that. First, the student is studying for a specific exam on a specific date, so signup asks for both and the dashboard counts down to the date. Second, the student will not configure much. Exam, section and question count are remembered per browser in the exam_prefs localStorage key, defaulting to SAT, quant and ten questions (DEFAULT_PREFS in frontend/lib/exam.ts), and every route into a game (the dashboard's course cards, a lesson's practice button) sets those preferences for you before it navigates.

The site is free. The structured data in frontend/app/layout.tsx declares an Offer with price 0, and there is no payment code anywhere in the repo.

1.3The core loop: learn, play, review

A session goes round a loop. You read a lesson on a topic. You play a game whose questions lean toward the topics you are weak in. At the end of the game you review every question with your answer and the explanation. The game's analytics go to the backend, which updates your weak and strong topics, and those topics decide what the dashboard suggests you learn next and which questions the next game leans on.

Each arrow is real code. A lesson's practice button calls setExamPrefs with the lesson's exam and section and pushes /games. Each game container fetches questions through fetchAIQuestions or fetchQuestionsWithCache in frontend/lib/api/questions.ts, and when the game ends it calls apiClient.saveScore. GameService._update_user_stats in backend/src/services/game_service.py marks a topic weak below 50 percent accuracy in that game and strong at 80 percent or above, and moves topics between the two lists as the student improves or slips. The dashboard reads weak_topics, keeps the ones in the current exam's courses, and offers the first as the focus. The question agent reads the same table and asks for about half of each difficulty band from weak topics.

Review happens inside the game screen. components/exam/ReviewList.tsx lists every question with the player's answer; wrong answers keep the right one hidden until the player asks, "so the review can be used to retry". During play, frontend/lib/hints.ts offers a strategy hint matched to the question's skill or wording, and can rule out a wrong choice without naming the right one.

1.4Exams, sections and courses

Two exams, two sections each, one course per section. The types are in frontend/lib/exam.ts: ExamId is 'sat' | 'gre' and SectionId is 'quant' | 'verbal'. The section names and pacing come from the EXAMS table; the courses and their topics come from COURSES in frontend/lib/courses.ts.

Games also have a pace. gamePace returns 'deep' for squid-game and 'quick' for everything else. Squid Game, where the player freezes on red light and has time to think, takes passages and multi-step problems, with a calculator for math.

Profile score targets use the real scales: SCORE_RANGES in frontend/lib/profile.ts sets 400 to 1600 in steps of 10 for the SAT and 260 to 340 for the GRE (verbal plus quant).

The mock exam

The mock exam is the one place the product drops the game. MODULE_QUESTIONS in app/mock/page.tsx holds the real module sizes (SAT 22 and 27, GRE 12 and 12). The clock is the question count times the section's secondsPerQuestion. Questions come from the same fetchAIQuestions the games use. When it finishes, the result is saved through the same saveScore call with the game id mock-exam, "so it feeds statistics and weak topics". The results page gives a rough scaled estimate using SCORE_RANGE: 200 to 800 per SAT section, 130 to 170 per GRE section.

Your own material

The materials page posts a file (4 MB at most, enforced on both sides as MAX_FILE_BYTES and MAX_UPLOAD_BYTES) or pasted text to POST /api/materials. The backend parses numbered questions with lettered choices and an answer line or answer key. If the parser finds nothing, or the student ticked the option to write questions, the LLM reads the material too. Every question starts as pending; a question with no answer shows "No answer was found. Pick the correct one". Only approved questions reach games, where they can make up to half of a set.

1.6What happens on first visit

A new visitor lands on /, clicks "Start free" and goes to /signup. The form asks for an email and a password of at least six characters, then the profile. createAccount calls apiClient.signup and, before anything else, copies the chosen exam into the saved preferences, so the first game is on the right exam.

What happens next depends on a Supabase setting. If email confirmation is off, signup returns an access token, the profile is saved at once with PUT /api/profile, and the student lands on /dashboard. If it is on, there is no session yet, so the profile cannot be saved. savePendingProfile parks it in localStorage under pending_profile, keyed to the lower-cased email, and the page tells the student to confirm their email. On their first login, takePendingProfile finds it, the login page saves it, and the key is removed. If saving fails either way (a taken username returns 409), the student is sent to /profile?setup=1 with the error as a notice, rather than failing the signup.

1.7What is out of scope

Knowing what the product does not do saves a contributor from looking for it.

  • No other exams. ExamId is two values and the backend's queries validate ^(sat|gre)$. There is no ACT, LSAT or GMAT.
  • No free-response or figure questions. CollegeBoardSource._normalize keeps only mcq items and drops any whose stem, stimulus or options contain a figure. The LLM prompt says "Skip anything that needs a figure, chart, or image". GRE numeric entry and multi-select types are not produced.
  • No official scoring. The mock exam's scaled score is a linear estimate and the page calls it rough. There is no adaptive second module.
  • No social features. Usernames are unique, but nothing shows another user's profile, scores or a leaderboard. High scores are per browser, in arcade_hi_<gameId> localStorage keys.
  • No lesson authoring. Lessons are TypeScript constants. There is no editor, no CMS and no LLM in the lesson path.
  • No synced lesson progress. "Mark as learned" is stored in the learned_lessons localStorage key. It does not follow the student to another browser.
  • No payments, no admin console, no email of its own. Confirmation emails, if enabled, are sent by Supabase Auth.
  • No mobile app. The site supports touch in the games, but there is only the web client.
A game that exists but cannot be played frontend/games/mario/MarioGame.ts and the GameRenderer that constructs it are still in the tree, and the README still lists Mario. But mario is not in games in frontend/lib/games.ts, so /games/mario returns notFound(). Treat it as dead code. Chapter 2 lists the rest.

Check yourself

A student finishes a mock exam with poor results on Geometry. Where will that show up?

The mock page calls saveScore('mock-exam', ...), so the attempt lands in game_sessions and question_attempts, and _update_user_stats adds Geometry to weak_topics if accuracy was under 50 percent. The dashboard will offer it as the focus topic (if it is in the current exam's courses), and the question agent will lean on it in the next game.

Why must course topic names match the question bank's topic names?

Weak topics are recorded from each question's topic. The dashboard keeps only weak topics that appear in COURSES, and lessons are found by topic. A mismatch would record weak topics that no course or lesson can ever point to.

A student signs up with email confirmation on, then logs in from a different browser. What happens to the profile they filled in?

It is lost. The pending profile is in the first browser's localStorage under pending_profile. The second browser has no profile, so the sidebar shows "Profile not set up" and the student fills it in again at /profile.

Which game asks long reading passages, and why only that one?

Squid Game. gamePace marks it deep because the player stops moving on red light and has time to read. Every other game is quick, and long questions are filtered out for them.

Chapter two

2Architecture

SATistics is three pieces: a Next.js 14 frontend that runs the pages and the games in the browser, a FastAPI backend that owns every decision touching data or an outside service, and a Supabase project that holds identity and every table. The browser never talks to Supabase. It talks to the backend with a bearer token, and the backend talks to Supabase with the service-role key. Everything else in this chapter follows from that one boundary.

This chapter is the map. It names the pieces and the outside services, lays out the repository, follows one request from a click to a database row and back, shows how the login token travels, lists where each kind of state lives, and marks the code in the tree that nothing runs, so you can ignore it. Where the code and this handbook disagree, the code is right.

2.1The three pieces

The frontend is frontend/: Next.js 14 with the App Router, React 18, TypeScript, Tailwind CSS, and Three.js for the 3D games. Almost every page is a client component ('use client'), and all data comes from the backend through one class, ApiClient in frontend/lib/api/client.ts, exported as the singleton apiClient. The only server-side code the frontend runs is frontend/middleware.ts, which checks for a cookie, plus metadata routes (app/robots.ts, app/sitemap.ts). There are no Next.js API routes.

The backend is backend/: FastAPI on Python, built in backend/src/main.py. It mounts eight routers, each in backend/src/api/, and most of them hand off to a service in backend/src/services/.

Supabase provides two things: Auth (email and password users in auth.users) and Postgres. The schema is plain SQL in backend/database/, pasted into the Supabase SQL editor by hand; there is no migration runner. schema.sql creates game_sessions, question_attempts and user_stats; add_profiles.sql adds profiles; add_materials.sql adds materials and custom_questions; reset.sql drops and recreates the first four. Every table has row level security enabled with owner-only policies, but the backend connects with the service-role key, which bypasses those policies. The backend enforces ownership itself, by filtering every query on the caller's user_id.

2.4A request, end to end

Follow one click: a signed-in student on /games/zombie/select presses play.

  1. The page. The select page has already written the student's choice of exam, section and question count with setExamPrefs. It navigates to /games/zombie. middleware.ts sees the auth_token cookie and lets it through.
  2. The game container. app/games/[gameId]/page.tsx renders GameContainer, which hands zombie to ZombieGameContainer. That component calls fetchAIQuestions(examPrefs.questionCount, undefined, gamePace(GAME_ID)).
  3. The client. fetchAIQuestions reads the prefs and calls apiClient.getAIQuestions, which builds GET /api/questions/?use_agent=true&limit=10&use_web_search=true&exam=sat&section=quant&pace=quick. The private request method prefixes NEXT_PUBLIC_API_URL, adds Authorization: Bearer <token>, and turns any non-2xx into an Error carrying the response's detail.
  4. The router. get_questions in src/api/questions.py resolves the caller with get_current_user_optional, so the route also works signed out (as a guest with an all-zero user id). It loads up to half the set from the student's approved material with load_custom_questions, then asks an ExamLearningAgent for the rest.
  5. The service. generate_questions reads the student's weak topics from user_stats and question_attempts through SupabaseAgentOps. For the SAT it calls CollegeBoardSource.fetch; any shortfall, and all GRE, goes to _questions_from_llm, which may first search the web for practice pages. Every question carries a source of official, web or ai.
  6. The response. The router validates each question against the Question model, shuffles, and returns { questions, total }. If the agent throws, the router returns just the custom questions.
  7. The fallback. Back in the browser, an error or an empty list makes fetchAIQuestions return getBankQuestions(exam, section, pace) from the offline bank. The game always starts.

When the game ends, the reverse trip is shorter. The container builds a GameAnalytics object and calls apiClient.saveScore. POST /api/games/save-score requires a user (get_current_user), and GameService.save_game_session inserts one game_sessions row, one question_attempts row per question, and updates user_stats.

Two requests skip request. uploadMaterial calls fetch directly so the browser can set the multipart boundary, adding the bearer header itself. And the backend's /api/auth/signup and /api/auth/login have explicit OPTIONS handlers in addition to the CORS middleware, which allows the origins in ALLOWED_ORIGINS plus localhost on ports 3000 and 3001.

2.5How the login token travels

There is one credential: the Supabase access token, a JWT. It is issued by Supabase, passed through the backend to the browser, kept in two places there, and sent back on every call.

  1. Issued. AuthService.login calls sign_in_with_password on the backend's Supabase client and returns session.access_token. AuthService.signup returns one only when email confirmation is off. The refresh token is returned by the service but dropped by TokenResponse; nothing refreshes a session.
  2. Stored. ApiClient.setToken writes the token to localStorage under auth_token and to a cookie of the same name with path=/, max-age=604800 (seven days) and SameSite=Lax. On construction the client reads localStorage first and falls back to the cookie, syncing it back.
  3. Checked by Next.js. middleware.ts only checks that the cookie exists. It does not decode or validate it. Its matcher skips _next assets, images and api paths.
  4. Sent to the backend. Every call carries Authorization: Bearer. FastAPI's HTTPBearer(auto_error=False) extracts it, and get_current_user answers 401 with "Missing authorization token" or "Invalid or expired token".
  5. Decoded. AuthService.get_user decodes the JWT with jwt.decode(token, options={"verify_signature": False}), rejects it if exp has passed, and returns { id: sub, email }.
  6. Cleared. logout posts to /api/auth/logout, which only acknowledges, and then always calls setToken(null), removing the key and expiring the cookie. DashboardLayout also calls clearAccountCache.
The signature is not checked get_user trusts the payload of any well-formed, unexpired JWT. Because the backend then queries with the service-role key, a forged token with another user's sub would read and write that user's rows. Verifying the token (with the project's JWT secret, or by calling Supabase Auth) is the fix; see Appendix B.

Expiry shows up as a 401 on the next call. The middleware cannot see it, because the cookie outlives the token. useAccount turns a failed /api/auth/me into a signed-out account, but no code sends the student back to /login on a 401.

2.8Code that nothing runs

The repo grew out of a hackathon project and still carries pieces of earlier designs. None of the following is reached from a page or a route. Do not extend them, and do not be misled by them when reading.

  • TypeScript under backend/src/, such as index.ts, api/games.ts, config/supabase.ts and services/gameScoreService.ts. They describe a Node backend that was never built; there is no package.json in backend/ to compile them. The live equivalents are the .py files beside them.
  • Other hosts' configs: backend/Dockerfile, fly.toml, railway.json, render.yaml. Production is Vercel.
  • The rewrite in frontend/vercel.json to a placeholder Railway URL. The client calls the backend by absolute URL, so /api/* on the frontend is never requested.
  • frontend/games/GameRenderer.ts and frontend/games/mario/. GameContainer only uses the renderer for games without their own container, and the only such game, mario, is not in lib/games.ts.
  • Unused components: components/AuthButton.tsx and components/GameCard.tsx are imported nowhere.

Check yourself

The RLS policies say users can only see their own rows. Why does that not protect the backend's queries?

Database.get_client prefers SUPABASE_SERVICE_ROLE_KEY, and the service role bypasses RLS. The backend's own .eq("user_id", ...) filters are what keep users apart, so a new query that forgets the filter leaks data.

A token expires while the student is on the dashboard. What do they see?

The middleware still passes them, since the cookie lasts seven days. Backend calls return 401; getUserStats and getRecentSessions swallow the error and return empty values, so the dashboard looks empty rather than signed out.

OpenRouter is down. Does a GRE game still start?

Yes. _questions_from_llm returns an empty list, the router returns only custom questions (possibly none), and fetchAIQuestions falls back to getBankQuestions, which has nine GRE questions per section.

Why does uploadMaterial not use the shared request method?

request always sets Content-Type: application/json. A multipart upload needs the browser to set the content type with its boundary, so it calls fetch directly with only the bearer header.

3Running it locally

SATistics runs on a laptop as two processes and one hosted database: the Next.js dev server on port 3000, the FastAPI server on port 8000, and a Supabase project you create for yourself. Supabase is the only integration you must set up. Everything else (AI questions, lesson video search) has a keyless fallback, so you can play every game and read every lesson before you sign up for anything else.

This chapter walks from an empty machine to a working sign-up. It covers the tool versions the code actually needs, the SQL that builds the database, every environment variable either app reads, where to get each key, what still works when a key is missing, and the failures people hit most often on the way. Two files are the short form of this chapter: backend/.env.example and frontend/.env.example. Copy them, fill them in, and come back here when something does not start.

3.1What runs where

The browser only ever talks to the FastAPI server. The frontend does not hold any Supabase key and never calls Supabase directly: sign-up, login, scores, profiles and uploaded material all go through frontend/lib/api/client.ts to the backend, which talks to Supabase with the service-role key. That is why the frontend needs exactly one variable and the backend needs the rest.

reset.sql deletes all users The file starts with DROP TABLE IF EXISTS ... CASCADE for every core table and then runs DELETE FROM auth.users;. Unlike reset.sql, add_materials.sql and add_review_and_pool.sql are additive and safe to run again: it uses CREATE TABLE IF NOT EXISTS and CREATE INDEX IF NOT EXISTS, and drops each policy before creating it.

One Auth setting matters for local work. Supabase enables "Confirm email" by default. With it on, POST /api/auth/signup creates the user but returns no session, and the backend answers "Please check your email to verify your account". For a development project, turn it off under Authentication, Sign In / Providers, Email, so a sign-up logs you straight in.

3.5Getting each key

Supabase. In the dashboard, open Project Settings, then the API keys page. Copy the project URL into SUPABASE_URL, the service_role key into SUPABASE_SERVICE_ROLE_KEY, and the anon key into NEXT_PUBLIC_SUPABASE_ANON_KEY. Newer dashboards list these JWT-style keys under a "legacy" tab beside the newer publishable and secret keys; the backend was written and tested against the anon and service_role pair. The service-role key is a root credential for your project. It goes in backend/.env and nowhere else.

OpenRouter. Create an account at openrouter.ai, add a small amount of credit, and create a key under Settings, Keys. Put it in OPENROUTER_API_KEY. The backend talks to https://openrouter.ai/api/v1 through the openai Python package, so any model id OpenRouter lists can go in OPENROUTER_MODEL. A cheap fast model is the right default; each question request is one model call of up to 25 questions (MAX_LLM_QUESTIONS in src/services/agent.py).

YouTube Data API. In Google Cloud Console, create a project, enable "YouTube Data API v3", and create an API key. Put it in YOUTUBE_API_KEY.

Serper. Sign up at serper.dev and copy the API key into SERPER_API_KEY.

Video search tries the providers in a fixed order and the first one that returns results wins: YouTube if its key is set, then Serper if its key is set, then DuckDuckGo through the ddgs package, which needs no key. Results are cached in memory for 24 hours per exam, section and topic (CACHE_TTL_SECONDS in src/services/videos.py), and only non-empty results are cached. Chapter 10 covers the ranking.

CORS. Locally you can leave ALLOWED_ORIGINS unset, because http://localhost:3000, http://localhost:3001 and the 127.0.0.1 forms of both are hard-coded in src/main.py. Set it only if you serve the frontend from another origin, such as a LAN address to test on a phone.

3.6What works with no optional keys

With only the Supabase variables set, the app is complete enough to develop almost anything:

  • Accounts, profiles, scores and stats work. They need Supabase and nothing else.
  • SAT questions still come from the real College Board question bank. ExamLearningAgent.generate_questions calls CollegeBoardSource.fetch for SAT before it considers the model, and that public API needs no key. Only the shortfall goes to _questions_from_llm, which logs "OPENROUTER_API_KEY not set" and returns nothing.
  • GRE questions come from the offline bank. When the API returns no questions, fetchAIQuestions in frontend/lib/api/questions.ts falls back to getBankQuestions from frontend/lib/questionBank.ts.
  • Games run entirely in the browser from frontend/games/ and only need questions and a place to save the score.
  • Lessons are static content in frontend/lib/lessons.ts and frontend/lib/courses.ts.
  • Lesson videos use DuckDuckGo, which rate limits after a burst of searches. An empty video list during development is usually that, not a bug.
  • Material uploads still parse PDFs and text with the rule-based parser in src/services/material_parser.py; the AI pass that finds more questions is skipped.

Without Supabase you can load the landing page and the backend health check, and nothing more. frontend/middleware.ts redirects /dashboard, /games, /learn, /materials, /mock, /profile and /stats to /login unless an auth_token cookie is present, and only the backend can issue one.

The public College Board question bank, through CollegeBoardSource.fetch. Only GRE falls back to the offline bank in frontend/lib/questionBank.ts.

You changed NEXT_PUBLIC_API_URL and the browser still calls the old URL. Why?

NEXT_PUBLIC_ values are inlined when Next.js compiles. Restart the dev server (or rebuild and redeploy in production).

Chapter four

4The design system

SATistics looks like a filled-in answer sheet that learned to play games: thick ink outlines, hard offset shadows, flat blocks of cobalt and lime, and the occasional frosted glass panel floating over soft paper. The whole system is small. It is seven color tokens and four shadows in the Tailwind config, a dozen component classes in one stylesheet, two fonts, a handful of SVG brand pieces and one app shell. This chapter walks through each of them and ends with the rules for building a screen that fits.

There is no component library and no design token package. Pages are client components that compose Tailwind utilities with the classes in frontend/app/globals.css. That keeps the system easy to read and easy to break, so most of this chapter is about the conventions the existing screens follow rather than about APIs.

4.1Two ideas: brutal and glass

The comment above the component layer in globals.css names the identity in one line: "brutalist outlines with frosted glass panels". The two halves do different jobs.

Neo-brutalism carries anything you can press or anything that holds content. It is a 2 px ink border, a solid offset shadow with no blur, generous radii (16 to 32 px), and flat fills from the palette. Buttons move toward their shadow when hovered and sink into it when pressed, which makes the shadow read as physical depth. Cards, form fields, chips, the shell's outer frame and the game covers all use the same outline.

Glass is for decoration and for secondary panels that sit over something busy: the landing page's section nav, the "how it works" steps, the key idea cards on a lesson, the caption on the developer page and the "Today's focus" card on the auth screens. It is a translucent white fill, a thin white border, a soft blurred shadow and backdrop-blur-xl. Glass only works over something with texture, which is why the app's background is the .paper-blobs gradient rather than a flat color.

The brand motif is the exam answer sheet. The logo mark is four answer bubbles laid out like a gamepad's face buttons, a decorative BubbleRow shows A to D with one bubble filled, and a Pencil draws a No. 2 test pencil in coral, paper and lime.

4.9Words

The copy is part of the system and follows a few rules you can check by reading any screen.

  • Sentence case everywhere. "Mark as learned", "Set up your profile", "Recent sessions", "Haven't tried yet". Never Title Case on buttons or headings. The arcade attract screen is the one place that shouts in capitals, on purpose.
  • No emoji in the interface. Icons come from Icons.tsx. The arcade top bar's menu and music glyphs are text symbols inside labelled buttons. The name fields in frontend/lib/games.ts still carry older titles with emoji; show titles through gameTitle from frontend/lib/gameMeta.ts instead.
  • Plain verbs on buttons. "Log in", "Continue", "Create profile", "Open lesson", "Practice in a game", "Play Whack-A-Mole". Say what will happen.
  • Talk to one person, briefly. "Your account is ready. Finish your profile to start." Empty states say what will fill them: "Finish a game and your score, accuracy and streak show up here."
  • Errors say what to do. "Usernames are 3 to 24 lowercase letters, numbers or underscores." "The username @shivvyas is taken. Try another one." End sentences with a period.
  • Loading text ends in an ellipsis character: "Logging in…", "Finding a video lesson…".

4.11Accessibility rules

The codebase already follows these; keep doing so.

  • Never remove the focus ring. :focus-visible draws a cobalt outline on everything. .field sets outline-none but replaces it with a cobalt shadow; if you suppress an outline, replace it.
  • Respect reduced motion. The global rule already zeroes transitions and animations. Do not drive essential state changes with animation alone, and add a prefers-reduced-motion override for any keyframe animation you add, as .arcade-blink does.
  • Label icon-only buttons. The menu toggle, the pause button, the back arrow on signup, the play overlay on a video thumbnail and each avatar swatch all carry an aria-label.
  • Expose state. Toggles use aria-pressed (exam choice, daily minutes, avatar color, "Mark as learned"), nav uses aria-current="page", the signup steps use aria-current="step".
  • Announce results. Errors render in FormError with role="alert"; quick check feedback and "Profile saved" sit in aria-live="polite" regions.
  • Decorative SVG is hidden. Logo marks, bubbles, the pencil, covers and icons are all aria-hidden. Do not put meaning only in a cover; put the game's title in text beside it.
  • Keep contrast. Ink on paper, mist, white, lime and every soft tint is high contrast. White text goes on ink, cobalt and coral only. Muted text uses text-ink/55 to text-ink/70; do not go lighter for anything a person needs to read. avatarTextColor switches to ink on the lime swatch for the same reason.
  • Label every field. Use Field with a matching htmlFor and id, and group choice buttons in a fieldset with a legend.

Why can a page write btn btn-ink py-3.5 and get the larger padding?

Because .btn is declared in @layer components, which Tailwind emits before the utilities layer. The py-3.5 utility comes later in the cascade with the same specificity, so it wins.

Where does font-serif get its typeface, and what happens if the font fails to load?

You add a seventh game and its card shows a lime circle on black. Why?

A page passes a helpful panel as aside. A tester on an iPad says it is missing. What is going on?

Glass panels blur what is behind them. Over a flat color the blur has nothing to work on and the panel looks like a grey box; the .paper-blobs gradients give it soft texture to frost.

5Accounts and profiles

An account in SATistics is two things: a Supabase Auth user, which owns the email and password, and a row in profiles, which holds the name, the exam and the goal that every other screen reads. The browser never talks to Supabase directly. It talks to the FastAPI backend, which signs people up and in through Supabase, hands back the access token, and later reads the user id out of that token on every request. This chapter follows that path end to end and is candid about where it is thinner than it looks.

5.1Intent

Signup should feel like setting up a game, not filling in a form. So it is three short steps (account, profile, goal) and the profile is created in the same flow, which means the dashboard can greet someone by name and aim their first game at their exam the moment they arrive.

The second intent is that a broken step never loses work. If the account is created but the profile save fails, signup does not fail; it sends the person to the profile page with a notice. If Supabase requires email confirmation, there is no session yet to save the profile with, so the profile waits in localStorage and is saved on the first login.

The third is that validation is the same on both sides. The form checks the profile before it sends it, using rules that mirror the backend's Pydantic model, so most errors show inline without a round trip, and the backend still enforces them.

5.4The server side

Routes. backend/src/api/auth.py is mounted at /api/auth and defines POST /signup, POST /login, POST /logout and GET /me, plus explicit OPTIONS handlers for signup and login. backend/src/api/profile.py is mounted at /api/profile with GET and PUT on the empty path.

Signup. The body is UserSignup (an EmailStr and a password string). AuthService.signup calls db.auth.sign_up. If Supabase returns a user, the result has success, the user's id and email, and, only when Supabase also returned a session (email confirmation off), an access_token. Known Supabase errors are rewritten into friendlier text ("An account with this email already exists", "Too many signup attempts. Please try again later.") and the route turns an unsuccessful result into a 400. Any other exception becomes a 500 whose detail includes the exception text.

Login. AuthService.login calls sign_in_with_password and returns the access token, a refresh token and the user. The route wraps this in TokenResponse, which has access_token, token_type and user, so the refresh token is dropped. Failures are 401 with "Invalid email or password" or the raw message.

Logout. AuthService.logout does nothing but return success. Its comments are explicit: the token is not revoked, it simply expires, and the client is trusted to forget it.

Who is calling. Every protected route depends on get_current_user. It reads the bearer token through HTTPBearer(auto_error=False), returns 401 "Missing authorization token" if there is none, and otherwise calls AuthService.get_user. That method decodes the JWT with jwt.decode(token, options={"verify_signature": False}), rejects it if exp is in the past, and returns {"id": sub, "email": email}. A None result becomes 401 "Invalid or expired token". GET /me returns exactly that dictionary.

Security caveat: tokens are not verified. Because the signature is never checked, anyone can construct a JWT with any sub and a future exp, and the backend will treat them as that user. Every route that uses get_current_user (profiles, sessions, stats, materials, videos) inherits this. The fix is to verify the token, either with the project's JWT secret (jwt.decode with the key, algorithms=["HS256"] and audience="authenticated") or by calling db.auth.get_user(token), which asks Supabase. Note that PyJWT, which provides the jwt module here, is not listed in backend/requirements.txt; it arrives as a dependency of the Supabase package. python-jose is listed but not used by this code.

The database client. get_db returns one process-wide client from Database.get_client(), built with SUPABASE_SERVICE_ROLE_KEY if set, then SUPABASE_SERVICE_KEY, then NEXT_PUBLIC_SUPABASE_ANON_KEY. The same client is used for auth.sign_up and auth.sign_in_with_password. The supabase-py 2.x client listens for its own auth events, and on SIGNED_IN it replaces its Authorization header with the new session's access token. On a shared server-side client that means table queries after a login run as the last person who logged in, not with the service key, until the process restarts. If you see RLS errors or empty results on a long-lived backend process, look here first; the safe pattern is a separate client for auth calls. Database.get_auth_client(), which builds a separate client with the anon key, exists but nothing calls it.

Profiles. GET /api/profile selects the seven profile fields for the caller and returns {"profile": ...} or {"profile": null}. PUT takes a Profile body, which Pydantic validates: the field constraints in the table above plus check_target_score, a model validator that applies the per-exam score range. The handler first looks for another user with the same username and returns 409 "The username @name is taken. Try another one." if there is one. Then it adds user_id and updated_at and upserts on user_id, returning the saved row.

5.5The client

Token storage. ApiClient in frontend/lib/api/client.ts is a singleton, apiClient. On construction in the browser it reads auth_token from localStorage, or, failing that, from document.cookie and copies it back. setToken(token) writes both: localStorage, and a cookie auth_token=...; path=/; max-age=604800; SameSite=Lax, which is seven days. setToken(null) removes both. The cookie exists only so the Next.js middleware can see it; API calls send the token as an Authorization: Bearer header from memory. signup and login call setToken when a token comes back, and logout clears it in a finally so a failed request still logs you out locally.

Errors from request become Error(detail), using the JSON detail field from FastAPI. That is why the 409 username message can be shown verbatim in the form.

Route protection. frontend/middleware.ts runs on every path except static assets, image files and anything under api. If the path starts with one of /dashboard, /games, /learn, /materials, /mock, /profile or /stats and there is no auth_token cookie (or Authorization header), it redirects to /login?redirect=<path>. If the path is /login or /signup and there is a token, it redirects to /dashboard. It checks only that a token is present, not that it is valid.

The account cache. frontend/lib/useAccount.ts keeps one module-level cached account, one inflight promise and a set of listeners. useAccount() subscribes the component, starts loadAccount() if nothing is cached (sharing the in-flight promise if one exists), and returns { account, loading, updateProfile }. loadAccount calls getCurrentUser() and, if that succeeds, getProfile(); either failing yields null rather than an error. setCachedProfile (exposed as updateProfile) patches the cached profile and notifies every listener, so the sidebar updates the moment the profile page saves. clearAccountCache() is called on signup, login and logout so the next page loads fresh.

Shared fields. frontend/components/profile/ProfileFields.tsx is used by both signup and the profile page. IdentityFields renders the Avatar preview, five color swatches, the name and the username. While the username still equals slugifyUsername of the current name, typing a name keeps suggesting a matching username; once the person edits the username themselves, it stops following. The username input lowercases as you type. GoalFields renders the exam choice (switching exam clears the target score, since the ranges differ), a number input whose min, max and step come from SCORE_RANGES, an optional date, and the daily minutes chips. validateProfile returns the first problem as a sentence, or null.

5.6How it works

Signup. frontend/app/signup/page.tsx holds step (0, 1 or 2 over STEPS = ['Account', 'Profile', 'Goal']), the email, two passwords and a Profile draft seeded from EMPTY_PROFILE, with the exam taken from ?exam=gre if present. A progress bar of three segments marks the current one with aria-current="step". Each submit runs checkStep: step 0 needs a password of at least 6 characters and a matching confirmation; steps 1 and 2 run validateProfile on the whole draft. Browser validation applies on step 0 (so the email must look like one) and is turned off with noValidate after that. The back button clears the error and steps back.

On the last step, createAccount calls apiClient.signup, clears the account cache and stores the chosen exam in the practice preferences with setExamPrefs. Then it branches:

  • No access token (confirmation is on): savePendingProfile(email, profile) and switch to the "Check your inbox" screen, which links to login.
  • Token, profile saves: push to /dashboard.
  • Token, profile fails (for example a taken username): push to /profile?setup=1&notice=<message>. The account exists; only the profile is left to do.

The pending profile. savePendingProfile writes { email, profile } to localStorage under pending_profile, with the email lowercased. takePendingProfile(email) returns it only if the emails match, deletes it as it reads, and merges it over EMPTY_PROFILE so a profile saved by an older version still has every field. Both swallow storage errors. Because the data lives in one browser, someone who confirms on their phone and logs in on a laptop starts without it and is sent to set up a profile.

Login. frontend/app/login/page.tsx calls apiClient.login, throws if no token came back, clears the cache, and then calls takePendingProfile. If a pending profile exists it is saved; a failure there goes to the setup page with a notice, as signup does. Finally it pushes to ?redirect if it is a same-site path (it must start with one / and not // or /\), else /dashboard, and refreshes the router so server components and middleware see the new cookie.

The profile page. frontend/app/profile/page.tsx renders inside DashboardLayout. When the account arrives it seeds a draft from the saved profile or, if there is none, from the email's local part (as the name and, slugified, the username). A cobalt header card previews the avatar, name, exam, target and test-day countdown live as you edit. Saving validates locally, calls saveProfile, pushes the result into the account cache with updateProfile, and syncs the exam preference. In setup mode (?setup=1) the page shows a lime banner with any notice, the button reads "Save and start", and success goes to the dashboard; otherwise "Profile saved" appears in a polite live region. Below the form, the strongest and weakest topics from getUserStats() are listed as chips.

Logout. The sidebar's "Log out" in DashboardLayout calls apiClient.logout(), then clears the cache and pushes to /login in a finally.

5.7Edge cases and tests

There are no automated tests for this area, in either the frontend or the backend. These are the behaviors worth knowing before you change anything.

  • Expired sessions. Supabase access tokens are short-lived, but the cookie lasts seven days and no refresh token is kept. After expiry the middleware still lets the person in, every API call returns 401, and nothing in the client redirects on 401. useAccount resolves to no user, so the sidebar shows an empty name; pages that read stats show empty states. Logging out and in again fixes it.
  • Validation drift. The backend accepts a display_name of a single space (only min_length=1), any daily_minutes from 5 to 240 and any hex color. The client is stricter: it trims the name and offers only the listed values. If you add a client option, check the server range.
  • Pydantic errors read badly. A 422 from FastAPI has a list in detail, and request passes it to new Error, which stringifies it. The client-side checks catch the common cases first, which is why this is rarely seen.
  • Username race. The 409 check and the upsert are two queries. Two people claiming the same name at once both pass the check; the unique constraint rejects the second, which surfaces as a 500 with the database message.
  • Redirect parameter. Login follows ?redirect only when it is a same-site path, so a crafted link cannot send someone to another site after they sign in.
  • Token exposure. The token is in localStorage and in a cookie set from JavaScript, so it is not HttpOnly; any script running on the page can read it.
  • Preflight handlers. The explicit OPTIONS routes for signup and login echo back whatever Origin they receive with credentials allowed, which is looser than the ALLOWED_ORIGINS list given to CORSMiddleware in backend/src/main.py.

To test by hand, run Supabase with email confirmation both on and off. With it off, signup should land on the dashboard with the name in the sidebar. With it on, signup should show "Check your inbox", pending_profile should appear in localStorage, and the first login should remove it and land on the dashboard with the profile in place. Try a taken username in both modes; you should arrive at /profile?setup=1 with the 409 message in the banner.

Why does the token live in both localStorage and a cookie?

The API client sends it as a bearer header, which needs it in JavaScript, and the middleware runs on the edge before any JavaScript, where only cookies are visible. The cookie is there purely so middleware.ts can decide whether to redirect.

Signup succeeds but no token comes back. What happens to the profile the person just filled in?

It is written to localStorage under pending_profile with the lowercased email. On the next login with the same email, takePendingProfile returns and deletes it, and the login page saves it with PUT /api/profile.

How does the backend know who is calling, and what does it not check?

get_current_user decodes the bearer JWT and takes sub as the user id after checking exp. It does not verify the signature, so a forged token is accepted.

Why does the sidebar show the new name immediately after saving the profile?

The profile page calls updateProfile, which is setCachedProfile: it replaces the profile in the module-level cache and calls every subscribed useAccount listener, including the one in DashboardLayout.

Why does changing the exam clear the target score?

The ranges do not overlap: 400 to 1600 for the SAT and 260 to 340 for the GRE. Keeping the old number would make the draft invalid on both sides.

Signup with a taken username: does the account get created?

Yes. The auth user is created first; the profile save then fails with 409, and signup routes to /profile?setup=1 with the message as the notice instead of failing.

Chapter six

6Exams, courses and practice settings

Every question in SATistics belongs to one exam and one section. That pair, plus a question count, is the only setting a player chooses before a game. This chapter covers where the pair is defined, how it is stored, how it reaches the games and the backend, and what a question looks like once it arrives. It ends with a checklist for adding an exam or a section.

6.1Intent

The product trains for two tests, the Digital SAT and the GRE, and each has a quantitative and a verbal section. Rather than build a separate game per test, the app keeps one small model of "what am I practising" and threads it through everything: the game setup screen, the question loader, the timer, the offline bank, the learning hub's courses and the mock exam. A game never knows which exam it is running; it receives questions and a number of seconds per question.

The model is deliberately thin. It is a pair of string ids, a question count and a table of real-exam pacing. There is no database row for it: the choice lives in the browser's localStorage, under one key, and the backend is told the exam and section as query parameters on every question request. The profile's exam field, covered with profiles, is a separate thing: it sets the target score scale and is not read by the question loader.

6.6How it works

  1. The player opens /games/squid-game/select. The effect calls getExamPrefs(); say it returns GRE, verbal, 10.
  2. The screen shows "Real exam pace: 12 questions in 18 min" and the chips Text Completion, Sentence Equivalence, Reading Comprehension.
  3. The player taps 20. setExamPrefs writes {"exam":"gre","section":"verbal","questionCount":20} to exam_prefs.
  4. "Start game" navigates to /games/squid-game. SquidGameContainer reads the preferences again and calls fetchAIQuestions(40, undefined, 'deep').
  5. fetchAIQuestions reads the preferences a third time and requests /api/questions/?use_agent=true&limit=40&use_web_search=true&exam=gre&section=verbal&pace=deep.
  6. The questions come back (chapter 7). The container builds the game with questionCount: 20 and secondsPerQuestion: 90, from EXAMS.gre.sections.verbal.

  5. frontend/lib/profile.ts: SCORE_RANGES, and the copy in frontend/components/profile/ProfileFields.tsx.
  6. backend/src/services/question_sources.py: add the entry to EXAMS with names suitable for search and an option_count.

  8. SQL: the CHECK constraints in add_materials.sql, add_profiles.sql and reset.sql need a new migration that drops and recreates them.

6.8Edge cases and tests

  • Private windows. If localStorage throws, the getter returns defaults and the setter is a no-op, so the setup screen works but forgets every change.
  • Stale values. A stored count of 15 from an older version falls back to 10 without touching the stored exam or section.
  • Two tabs. There is no storage event listener. A tab that is already open keeps the preferences it read on mount.
  • Name drift. The frontend says "Reading & Writing" and "Quantitative"; the backend says "Reading and Writing" and "Quantitative Reasoning". This is harmless but it means a label from one side should never be compared to the other.
  • Profile versus practice. A user whose profile says GRE can practise SAT. Nothing reconciles the two.

There are no automated tests for this code. The frontend package.json has no test script and the backend has no test directory. The validation in getExamPrefs and the hand-kept parity between SATQuestion and Question are the first things worth pinning.

Chapter seven

7The question engine

One endpoint builds every question set the games play. It mixes in the user's own approved questions, pulls official SAT questions from the College Board, asks an LLM to copy questions from web pages or write new ones for whatever is still missing, and tags each question with where it came from. When any of that fails, the browser falls back to a small built-in bank, so a game always starts.

7.1Intent

The project's promise is real exam questions inside arcade games. "Real" is the hard part. The College Board publishes its Educator Question Bank behind an open JSON API, so SAT questions can be official. ETS does not publish GRE questions for reuse, so for the GRE the engine searches the web for practice pages and asks a model to copy out questions that are actually on them, writing original ones only to fill the gap. Every question carries a source so the game can say honestly where it came from.

The engine is also personal. Before it picks anything it reads the user's weak topics from Supabase and leans the selection toward them. And it is game-aware: a fast arcade game asks for pace=quick and gets short questions; the slow game asks for pace=deep and gets passages and multi-step problems. The exam, section and pace model is chapter 6.

get_questions in backend/src/api/questions.py does four things when use_agent is true. If the caller is signed in and include_custom is set, it loads up to limit // 2 custom questions on a worker thread. It builds an ExamLearningAgent and asks it for limit - len(custom) more. It validates the combined list through the Question model and shuffles it. If the agent raises, it logs and returns the custom questions alone. Any other error becomes a 500.

use_agent=false returns nothing. The docstring and the fallback comment mention static questions, but there is no static bank on the server any more. Without use_agent=true the route returns an empty list. The offline bank lives only in the frontend.

The same router serves GET /api/questions/topics, which requires auth and returns the distinct topic values in question_attempts. It does not filter by user, so it lists topics from everyone's attempts. Nothing in the frontend calls it.

The agent

ExamLearningAgent.generate_questions runs analyze_performance on a thread. That reads the user_stats row through SupabaseAgentOps.get_user_performance (total answered, accuracy, weak and strong topics) and aggregates question_attempts per topic through get_topic_performance. It sets recommended_difficulty to easy below 50 percent accuracy, hard above 75, medium otherwise. Both reads catch their own exceptions and return empty data, so a missing database degrades to "new user".

For the SAT it then calls CollegeBoardSource.fetch. Whatever is still missing, for any exam, goes to _questions_from_llm. The agent appends a summary to context_memory, a plain list on the instance; a new agent is built per request, so that memory never outlives the request.

CollegeBoardSource

The source talks to BASE_URL, the College Board's qbank-api host, in two steps. _get_index posts to /get-questions with asmtEventId: 99, the test number and the domain codes from SECTIONS (Math is test 2, domains H,P,Q,S; Reading and Writing is test 1, domains INI,CAS,EOI,SEC). It keeps only entries with an external_id and caches the index per section for INDEX_TTL_SECONDS, six hours, in a class attribute.

  1. _fits_pace pre-filters on index metadata. Quick drops hard questions and, in verbal, keeps only the QUICK_SKILLS (Words in Context, Boundaries, Form, Structure, and Sense, Transitions). Deep drops easy quant questions and, in verbal, the quick skills.
  2. _pick_candidates oversamples: five times the limit for quick, four otherwise, because many items are later dropped. It splits the target evenly across the three difficulty codes and fills about half of each band with items whose domain or skill matches a weak topic (_matches_topic is a case-insensitive substring test either way round).
  3. Each candidate is fetched from /get-question, at most MAX_CONCURRENT_REQUESTS (8) at once, on one httpx.AsyncClient with a 20 second timeout. Failures are logged and skipped.
  4. _normalize rejects anything that is not type == "mcq", has fewer than two options, or contains a figure (has_figure). It finds the correct index from keys, or from the letter in correct_answer, and builds both the plain text and the sanitized HTML forms.
  5. For quick pace, is_quick_question drops anything whose full text exceeds QUICK_MAX_CHARS (220 for quant, 420 for verbal) or that has an option over QUICK_MAX_OPTION_CHARS (60).
  6. _balance_difficulty takes questions round-robin from the easy, medium and hard bands until it reaches the limit.

The LLM step

get_llm_client returns an OpenAI SDK client pointed at https://openrouter.ai/api/v1, or None when OPENROUTER_API_KEY is not set. With no client, _questions_from_llm logs and returns an empty list; it does not even search, because a page is useless without a model to read it. The model is LLM_MODEL, taken from OPENROUTER_MODEL with the default anthropic/claude-haiku-4.5. The count is capped at MAX_LLM_QUESTIONS, 25, because one call cannot reliably return more.

With use_web_search, WebQuestionSource.find_pages runs one or two DuckDuckGo text searches through the ddgs package: "{label} practice questions with answers and explanations", plus one for the first weak topic. search retries up to three times, sleeping 2 and then 4 seconds. Non-PDF result URLs are de-duplicated and the first eight are fetched with browser headers and a 12 second timeout. _read_page keeps a page only if its text has a line that starts like a lettered choice (A. or (B)); it keeps 9,000 characters starting 1,500 before that line. At most MAX_PAGES, four, are used.

_extract_from_pages sends the student context from build_agent_context and the numbered pages, and asks only for questions copied exactly from them, where the source gives the answer. It runs at temperature 0.2 with max_tokens=12000; extract_json parses from the first [ to the last ]. _normalize_llm_question tags a question web only if sourceIndex points at a real page and the first 50 normalized characters of its stem or passage appear in that page's normalized text; the sourceName is then the page's host. Anything else the model returns is dropped here, because new questions come from the question writer.

backend/src/services/question_writer.py writes the rest. BLUEPRINT lists every skill of each exam section with its domain, a weight close to the official mix, and its format rules: option count, the official stem wording, passage length, whether the text has a blank, and for GRE Quantitative Comparison the four fixed choices. plan picks up to MAX_WRITE_CALLS skills, weak topics three times as likely, gives each one difficulty from the pace, and makes one call per skill. For SAT, CollegeBoardSource.examples puts three real questions of the same skill and difficulty in the prompt as models. Every wrong option needs a distractorRationales entry naming the student mistake behind it. A question is dropped if it fails skill_problem (format rules, repeated options, "all of the above", a correct option that stands out as the longest) or copies_example (40% or more of its five-word runs taken from one example). arrange_options then sorts numeric options ascending and shuffles the rest, so the key's position gives nothing away.

backend/src/services/answer_check.py checks every key, web and written. For math the model also states answerValue; answer_value_matches evaluates it and the options with a small arithmetic parser, and drops the question unless exactly the keyed option has that value. verify_answer_keys then has VERIFIER_MODEL solve the set three times with no key or explanation and the options shuffled. A question stays if at least two solves pick the key and at most one picks or defends another option. A failed call counts as disagreement. Solves run only while they can change the outcome: two run together, and the third only for questions they split on, which gives the same decisions as always running three. The writer asks for 40% more questions than needed to cover what these checks drop. Quick pace applies is_quick_question again.

Writing and checking a question costs several LLM calls, so backend/src/services/question_pool.py keeps every AI-written question that passes in the question_pool table, including extras a set didn't need. Before writing anything, generate_questions takes pooled questions the student has no attempt for, about half on weak topics, and writes only what is still missing. Web questions are not pooled.

The writer puts math in LaTeX between single dollar signs. backend/src/utils/math_text.py turns each field into the pair official questions arrive with: sanitized MathML HTML through latex2mathml for screens that render it, and plain text through html_to_text for canvas labels and the answer checks. Explanations are numbered steps, and each wrong option keeps the writer's note on the mistake behind it as optionExplanations, which arrange_options reorders with the options.

Sanitizing HTML

Official questions arrive as HTML with MathML. backend/src/utils/html_utils.py parses it into a small tree with the standard library's HTMLParser and renders it two ways. sanitize_html keeps tags in HTML_TAGS and MATH_TAGS, keeps only the attributes in KEPT_ATTRS, removes DROPPED_TAGS (script, style, svg, img, iframe and others) with their content, removes sr-only elements, unwraps unknown tags, turns underline spans into <u>, and expands <mfenced>, which browsers no longer draw, into explicit <mo> brackets. html_to_text writes MathML out linearly, so a fraction becomes (12x + 28)/4 and a square root becomes √(...), for canvas games and for the LLM. has_figure reports any svg, img or figure element.

Custom questions

load_custom_questions selects the user's custom_questions rows for the exam and section with status = 'approved', looks up material names, converts each with to_game_question (topic defaults to "My material", source is custom, sourceName is the material's name), applies the quick filter for quick pace, shuffles and returns up to the limit. Errors return an empty list. How rows get there is chapter 12.

7.5The client

Fetching

fetchAIQuestions(limit, fallbackQuestions, pace) reads the exam and section from getExamPrefs() and calls apiClient.getAIQuestions, which always sends use_agent=true and use_web_search=true and adds the bearer token if the client has one. A non-empty list is returned as is. An empty list is turned into an error, and any error leads to getBankQuestions(exam, section, pace), or to fallbackQuestions if the bank had nothing.

fetchQuestionsWithCache(gameId, limit, fallbackQuestions) wraps it with a five-minute cache in sessionStorage under ai_questions_${gameId}_${exam}_${section}, and derives the pace from gamePace(gameId). Only Carnival and Whack-a-Mole use it; the other games call fetchAIQuestions directly and get a fresh set every run.

The offline bank

frontend/lib/questionBank.ts holds 36 hand-written questions: nine per exam and section, three of each difficulty, ids 9001 to 9309. GRE quant uses the four standard Quantitative Comparison choices from QC_OPTIONS; GRE verbal has five-choice items. getBankQuestions drops hard questions for quick pace and easy ones for deep pace (PACE_EXCLUDES), so a game gets six, prepends any passage to question, and tags each one source: 'practice'. The landing page's HeroQuestion also shows the first three SAT quant items.

Rendering

QuestionContent takes an optional html and a required text. With HTML it runs a second sanitizer in the browser: it parses with DOMParser, removes any element whose tag is not in ALLOWED_TAGS (the same list as the backend), strips attributes not in ALLOWED_ATTRS, and renders the result with dangerouslySetInnerHTML. Without HTML it renders the text with whitespace-pre-line. Note the difference: the backend unwraps an unknown tag and keeps its text, the frontend removes it and its text.

QuestionCard is the overlay panel the React-rendered games share. It shows "Question n of m", the skill or topic and the difficulty, then the passage, the stem and the choices, each through QuestionContent. A choice is a button when the game passes onPick and plain text when the player answers inside the game world. After a wrong answer it shows either an "insight" (the player will see the question again, so the right answer stays hidden) or the explanation under "Why X is correct". sourceLabel turns source into a caption such as "Official College Board question", or "From" followed by the page host or material name; Zombie, Subway Surfers and Squid Game print it.

Hints

useQuestionHints(question) resets when the question changes. The first request shows strategyHint: a tip chosen by matching the question's own wording against PROMPT_TIPS, then its skill and topic against STRATEGY_TIPS, then DEFAULT_TIP. Each later request calls eliminationHint, which rules out one wrong choice, preferring one the explanation addresses, and stops when only the right answer and one other remain. whyNot extracts the "Choice B is incorrect ..." sentence that College Board rationales contain, and rejects it if it is too short, uninformative, or names the correct letter. insightFor uses the same function after a wrong answer. HintButton is just the button, labelled "Hint" then "Another hint". Zombie, Subway Surfers, Squid Game and Pac-Man use the hook.

7.6How it works

A signed-in player starts Subway Surfers on SAT Math with ten questions.

  1. SubwaySurfersGameContainer calls fetchAIQuestions(20, undefined, 'quick').
  2. The browser sends GET /api/questions/?use_agent=true&limit=20&use_web_search=true&exam=sat&section=quant&pace=quick with the bearer token.
  3. The route resolves the user and loads up to 10 approved custom SAT Math questions. Say it finds 3.
  4. The agent reads performance, finds weak topic "Advanced Math", and asks the College Board source for 17.
  5. The source filters the cached index to non-hard items, picks 85 candidates (17 times 5) spread over easy and medium with half on Advanced Math, fetches them eight at a time, normalizes, drops long ones and balances. Say 17 survive.
  6. Nothing is missing, so no LLM call is made. The route validates 20 questions, shuffles and returns them.
  7. The game renders each with QuestionCard; the player can ask for hints.

7.7Performance and cost

The College Board path makes one request per candidate. A 50-question quick request from Carnival is up to 250 detail calls, eight at a time. The index cache is per process, so on serverless hosting each cold instance pays for its own index fetch. The LLM path costs one model call of up to 12,000 output tokens per request, plus up to two searches and eight page reads; the search retries use time.sleep, but they run in a worker thread through asyncio.to_thread, so they do not block the event loop. The only client cache is the five-minute one in fetchQuestionsWithCache.

7.8Edge cases and tests

  • Short sets are not topped up. If the backend returns three questions, the game gets three. The bank is used only when the list is empty.
  • The mock exam uses no pace, so it gets the whole index and no length filter (chapter 12).
  • GRE requests over 25 get at most 25 from the model, plus custom questions.
  • Agent failure hides official questions. Any exception inside generate_questions returns only the custom questions, even if some official ones were already loaded.
  • Unused parameters. topic and difficulty are accepted and ignored. recommended_difficulty reaches the prompt but not the College Board picker, which always spreads evenly.
  • Random elimination. When no wrong choice has a usable explanation, eliminationHint picks one at random on every render; only the one picked at click time is shown.
  • Comments. hints.ts has two stacked comments above PROMPT_TIPS, the first left over from an earlier version.

There are no automated tests. html_to_text, _normalize_llm_question, _balance_difficulty, whyNot and getBankQuestions are pure functions and the cheapest place to start.

Chapter eight

8The game framework

SATistics teaches through games, and every game is the same machine wearing a different costume: questions go in, a player answers them by doing something in a 3D scene, and an analytics object comes out. This chapter describes that machine. It covers how a game is registered, the three routes a player passes through, the container component that owns each game, the shared exam UI that every container borrows from, and how questions arrive and results leave. The one idea that shaped it is that the engine never touches React and React never touches the scene: they talk through a handful of callbacks and imperative methods.

This chapter describes the code on main at commit 9b9abf0. There is no plugin system and no game interface file. A "framework" here is a set of conventions that six games happen to follow, plus a few shared components in frontend/components/exam/ and frontend/components/arcade/. Where the games disagree with each other, this chapter says so, because the disagreements are where new contributors get caught.

8.1Intent

The first intent is that a game is practice, not a reward for practice. Answering is the gameplay: the player shoots the zombie wearing the answer, runs through the gate of the answer, stands on the pad of the answer. A question is never a modal that interrupts the game; it is the reason the game is moving.

The second intent is that every game uses the same questions and reports the same numbers. All of them fetch from one backend endpoint through lib/api/questions.ts, all of them fall back to the same offline bank, and all of them hand a GameAnalytics object to apiClient.saveScore. That is what lets the statistics pages and the "Your games" panel treat a Pac-Man round and a Squid Game round as rows in one table.

The third intent is that the exam stays visible. The newer games render the full question, passage and choices in a shared QuestionCard beside the action, pace themselves from the real exam's seconds per question, offer hints that rule out choices, and refuse to show the answer after a first miss so the question can come back later.

8.5How it works

Dispatch

GameContainer holds a constant OWN_CONTAINER_GAMES listing all six ids, then a chain of if (game.id === ...) early returns that render each game's own container. The early returns come after a useEffect, because React requires hooks to run in the same order on every render; the comment in the file says so. Only when the id matches none of them does the component render a bare full-screen <canvas>, and the effect constructs a GameRenderer on it.

GameRenderer and BaseGame are the original design: an abstract class with init, update(deltaTime), render(ctx) and handleInput(key), driven by a generic loop that also forwards keyboard events and draws on a 2D overlay canvas. Its init() switch knows exactly one id, 'mario', and 'mario' is not in games, so the play page returns 404 before GameContainer ever sees it. In practice the canvas branch is unreachable. Every live game takes the container path.

The container pattern

ZombieGameContainer is the cleanest example, and the newer containers follow it closely. In order:

  1. A mount effect calls getExamPrefs(), reads the local high score with getHighScore, and calls fetchAIQuestions(count, undefined, gamePace(GAME_ID)). A cancelled flag guards the setQuestions in case the page unmounts first.
  2. A second effect waits for both the canvas ref and the questions, then dynamically imports the engine module with await import('@/games/zombie/ZombieGame'). The type import at the top of the file is import type, so Three.js and the engine stay out of the page's initial bundle.
  3. It constructs the engine with the window size, the canvas, the questions and a config of { questionCount, secondsPerQuestion }, stores it in a ref, and assigns the callbacks: onHudChange, onQuestionChange, onFeedback and onGameOver. Most are passed React state setters directly.
  4. It adds resize and keydown listeners and starts a requestAnimationFrame loop that computes deltaTime, caps it at 50 ms so a background tab does not cause a jump, and calls game.update(deltaTime) then game.render().
  5. The effect's cleanup sets cancelled, cancels the frame, removes the listeners and calls game.cleanup(), which disposes geometries, materials and the renderer.

Everything the player reads is DOM, not canvas: the score bar, the question card, the hint button, the calculator, the pause menu and the results modal. The engine pushes a snapshot of its state through onHudChange, throttled to one call per HUD_UPDATE_INTERVAL_MS (100 ms) in Zombie, Subway Surfers and Squid Game, and the container renders from that snapshot. Controls flow the other way through public methods on the engine held in gameRef: start(), setPaused(), setMuted(), skipFeedback(), and per-game verbs such as shootAt, moveLane or lockIn.

A constructor that reports too early. The newer engines call emitHud(true) from their constructor, before the container has assigned onHudChange. ZombieGameContainer works around it by calling game.setMuted(false) straight after wiring the callbacks, which re-emits the HUD. The engines that load assets asynchronously (Subway Surfers, Squid Game) emit again when loading finishes, so they do not need the trick.

Getting questions

fetchAIQuestions(limit, fallbackQuestions, pace) reads the exam and section from getExamPrefs() and calls apiClient.getAIQuestions, which issues GET /api/questions/ with use_agent=true, limit, use_web_search=true, exam, section and, when given, pace. If the call throws or returns no questions, it falls back to getBankQuestions(exam, section, pace) from lib/questionBank.ts, then to fallbackQuestions. A game therefore always gets a list, though it may be short.

fetchQuestionsWithCache(gameId, limit, fallback) wraps that with a five-minute sessionStorage cache keyed ai_questions_${gameId}_${exam}_${section}. Only Whack-A-Mole and Balloon Pop use it, and both ask for 50 questions regardless of the chosen question count. The other four call fetchAIQuestions directly with a count derived from the preference: Zombie asks for questionCount, Subway Surfers and Squid Game ask for twice that so difficulty can adapt, and Pac-Man asks for a fixed 20.

Timing and pacing

Every engine that has a clock receives it from the container. Zombie and Subway Surfers get QUICK_SECONDS_PER_QUESTION; Pac-Man gets it through setQuestions(questions, QUICK_SECONDS_PER_QUESTION); Whack-A-Mole imports the same constant inside the engine for its popDuration. Squid Game, the one deep game, gets EXAMS[exam].sections[section].secondsPerQuestion, the real exam's pace. Balloon Pop has no clock at all. Engines measure time from the deltaTime the loop gives them, so a paused game's clock stops; the exception is the 2-second setTimeout that Whack-A-Mole and Balloon Pop use between questions.

Saving results

When an engine calls onGameOver, the container stores the result in state, which renders GameOverModal, and records the local high score with recordHighScore(gameId, score) (Zombie, Whack-A-Mole, Balloon Pop and Pac-Man do; Subway Surfers and Squid Game do not). It then imports apiClient lazily and calls apiClient.saveScore(gameId, analytics), which posts { gameId, analytics } to /api/games/save-score. The endpoint depends on get_current_user, so a signed-out player's save fails; every container catches the error and logs it, and the modal is unaffected.

8.7Input and assets

Keyboard and touch

Input is wired by the container, not by a shared layer. Keyboard listeners go on window and ignore e.repeat; Space and the arrow keys call preventDefault() so the page does not scroll. P and Escape pause in the four games that listen for keys; Whack-A-Mole and Balloon Pop have no keyboard input and pause only from the menu button. Number keys 1 to 5 pick an answer in Zombie and Subway Surfers. Touch uses pointer events, never touch events: Zombie aims on onPointerMove and fires on onPointerDown; Subway Surfers and Pac-Man treat a pointer drag longer than SWIPE_MIN_DISTANCE (30 and 24 px) as a swipe; Squid Game and Pac-Man draw on-screen buttons, and Squid's holdKey helper maps pointer down and up to handleInput and handleKeyRelease, so a held button behaves like a held key. Whack-A-Mole and Balloon Pop listen for click on the canvas inside the engine and raycast against their meshes, which works for taps too. Canvases that take gestures carry touch-none.

Assets

Whack-A-Mole, Balloon Pop, Zombie and Pac-Man build their scenes entirely from Three.js primitives and CanvasTexture labels; they load no files. Subway Surfers loads a glTF map from /games/subway-surfers/assets/subway_surfers_maps/scene.gltf, the FBX character from /Flying.fbx with /Falling.fbx and /Falling Flat Impact.fbx, and three MP3s from the public/ root. Squid Game loads three FBX animations and three glTF models from /games/squid-game/assets, two textures from its squid-textures folder, and audio from /games/squid-game/audio. Anything under frontend/public/ is served from the site root; anything elsewhere is not.

8.8Performance

The heavy cost is download, not frame time. frontend/public/games is about 129 MB, of which Squid Game is 124 MB: the red_guy guard model alone is 43 MB, and the squid-textures folder is 72 MB although the engine reads only two images from it. Engines are imported dynamically so none of this, nor Three.js, lands in the catalogue's bundle.

On the frame side, the newer engines are frame-rate independent: they scale motion by dt and smooth with an exponential damp(rate, dt). Zombie, Subway Surfers and Squid Game cap the renderer's pixel ratio at 2; Pac-Man passes window.devicePixelRatio uncapped. HUD callbacks are throttled to 10 per second, because each one is a React state update. The older code does not follow these rules: Pac-Man moves Pac-Man and the ghosts by a fixed step per frame and calls onHudChange on every frame; Balloon Pop moves balloons per frame and runs its pop and particle animations in their own requestAnimationFrame chains, outside the game loop and outside pause.

8.9Edge cases

  • No backend. fetchAIQuestions falls back to the offline bank, so every game still starts. Saving then fails and is logged.
  • Signed out. The game plays normally; save-score requires a user, so the session is not stored and does not appear in "Your games". The local high score still updates.
  • Restart. Every restart is window.location.reload(). For the two cached games, a reload within five minutes reuses the same questions from sessionStorage.
  • Background tab. The capped deltaTime stops a returning tab from skipping time, except in Whack-A-Mole, whose loop does not cap it, so one long frame can expire the question.
  • Five choices. LANE_COLORS and LANE_LETTERS have five entries and the newer engines build one target per option. Whack-A-Mole and Balloon Pop always build four, so a fifth choice cannot be picked.
  • Fractional averages. The backend's GameAnalytics.averageResponseTime is an int under Pydantic 2. Whack-A-Mole and Balloon Pop send an unrounded mean, which can fail validation; the other four round it.

There are no automated tests for the games or the shared exam components.

Why does the "Start game" link carry no query string?

To keep Three.js and the engine out of the page bundle and off the server. The top of the file uses import type, which is erased at compile time.

A flying runner over an endless subway map. Each question spawns one gate per choice across the lanes. The run is shaped like the digital SAT. The constructor shuffles the pool and splits questionCount into two modules. Module 1 is an even mix of difficulties. Each module has a section clock of secondsPerQuestion times its length; a single gate waits at most QUESTION_TIME_CAP (1.5) times the per-question budget. When the section clock runs out, the questions left are recorded as unanswered. A first miss is appended to the module and adds 35 seconds to its clock. 10Learn: lessons and videos

The games test what you know; Learn teaches it. Every course topic on both exams has a short lesson: a summary, the key ideas, a worked example revealed one step at a time, the traps that cost points, and one quick check question. Beside it sits a column of YouTube lessons that the backend finds and ranks on demand. The lesson text is static TypeScript shipped with the frontend; the videos are the only part that touches the server.

10.1Intent

A student who misses three Advanced Math questions in a game should be one click from the idea they are missing. Learn is built for that. The hub opens on the exam from the student's profile, puts their weakest topic first, and marks each card "Needs work" or "Strong" from the same user_stats lists the dashboard uses. A lesson ends with "Practice in a game", which sets the exam and section and drops the student into the games list.

Lessons are written content, not data. Keeping them in frontend/lib/lessons.ts means they are reviewed like code, typed, versioned and rendered without a request. Videos are the opposite: they change, there are thousands, and a good one for "Standard English Conventions" is a search away. So the backend searches, ranks toward lesson-length videos from established prep channels, and caches the result for a day.

  exam: ExamId
  section: SectionId
  topic: string
  summary: string
  ideas: { title: string; body: string }[]
  example: { prompt: string; steps: string[]; answer: string }
  traps: string[]

Content is written as LessonContent, which is Lesson without exam and section, in four arrays: SAT_MATH, SAT_RW, GRE_QUANT and GRE_VERBAL. BY_COURSE maps 'sat:quant' and so on to those arrays, and LESSONS is built by walking COURSES in order and stamping each piece of content with its course's exam and section. The result is 15 lessons, one per topic, in course order. Each has three or four key ideas, two to four example steps, two or three traps, and a check with four options on the SAT and five on the GRE, matching each exam's option_count in the backend. correctAnswer is a zero-based index.

Slugs. topicSlug lowercases a topic and turns every run of non-alphanumerics into one hyphen, so "Problem-Solving and Data Analysis" becomes problem-solving-and-data-analysis. lessonHref(exam, topic) builds /learn/<exam>/<slug>, and findLesson(exam, slug) reverses it by slugging every lesson's topic and comparing. "Algebra" exists on both exams; the exam segment keeps them apart.

Progress. frontend/lib/learnProgress.ts stores the set of learned lessons as a JSON array under the localStorage key learned_lessons. Ids come from lessonId(exam, topic), which is "exam:topic", for example "sat:Algebra". This progress is per browser, not per account; nothing is sent to the backend.

Videos. The Video shape is the same in schemas.py and client.ts: id, title, channel, duration (a clock string such as "12:04"), url, thumbnail, published (a date) and trusted. Nothing about videos is stored in the database.

10.4The server side

backend/src/api/learn.py is mounted at /api/learn and has one route, GET /videos. It requires a signed-in user through get_current_user and validates its query: exam must match ^(sat|gre)$, section must match ^(quant|verbal)$, topic is 2 to 80 characters and limit is 1 to 12 (default 6). It awaits find_topic_videos and returns VideoResponse; any exception becomes a 502 "Video search failed: ...".

backend/src/services/videos.py does the work in four stages.

1. Cache. The key is exam:section:topic with the topic lowercased. _cache is a module-level dict of (timestamp, ranked list); a hit younger than CACHE_TTL_SECONDS (24 hours) is sliced to limit and returned. The limit is not part of the key, so the dashboard's request for three and the lesson page's request for six share one search.

2. Queries. The exam and section display names come from EXAMS in question_sources.py. First comes a dedicated GregMat search, "GregMat GRE <topic>" for the GRE or "GregMat <topic>" for the SAT; only results whose channel is GregMat and whose title mentions the topic are kept. Then up to three general queries run in order: "<exam> <topic> lesson"; for the SAT "Khan Academy SAT <topic>", for the GRE "GRE <topic> strategy"; and "<exam> <section> <topic> explained". The loop stops early once 15 non-GregMat videos are collected. Queries run one at a time on purpose, because parallel queries get rate limited. Results are deduplicated by video id.

3. Providers. _search builds a chain and returns the first provider's non-empty result:

OrderProviderEnabled byNotes
1YouTube Data APIYOUTUBE_API_KEYsearch with videoEmbeddable=true, 15 results, then one videos call for durations and view counts. ISO durations become clock strings with _iso_to_clock.
2SerperSERPER_API_KEYPOST https://google.serper.dev/videos, 15 results. No view counts, so views are 0.
3DuckDuckGoalwaysDDGS().videos through the ddgs package, run in a thread with asyncio.to_thread. Up to 2 attempts with a 2 second backoff, since rate limiting shows up as an error rather than a status.

An httpx.HTTPError from YouTube or Serper is logged and the chain moves on. Every result passes through _video, which keeps only URLs that match the YouTube id pattern (so every result can be embedded), builds the canonical watch URL and the hqdefault.jpg thumbnail, parses the duration into minutes and marks the video trusted if its channel matches TRUSTED_CHANNELS: Khan Academy, College Board, ETS, Official GRE, GregMat, Magoosh, Scalar Learning, Princeton Review, Kaplan, PrepScholar, Supertutor, 1600.io and Target Test Prep. Single-word names must match a whole word of the channel; multi-word names match as substrings.

4. Ranking. _score adds:

  • 3 for a trusted channel;
  • 2 for a length of 3 to 25 minutes (fits in a study session), 0.5 for anything else up to 60 minutes, and minus 2 for longer (multi-hour livestreams); no change if the duration is unknown;
  • log10(views) / 3, so a million views is worth 2.

The list is sorted by score, then up to GREGMAT_SLOTS (3) GregMat videos that mention the topic are moved to the front. Only a non-empty result is cached, so a rate-limited search is retried on the next request rather than remembered as "nothing found".

10.7How to add or edit a lesson

  1. Editing text is a change to the right array in frontend/lib/lessons.ts. Aim for four ideas and three short traps, keep the SAT at four options and the GRE at five, and make sure check.correctAnswer is the zero-based index of the right option. Use real typographic characters (the file already uses −, ×, ² and curly quotes) rather than markup; the fields render as plain text.
  2. Adding a topic to an existing course takes two edits. Add the topic name to that course's topics in frontend/lib/courses.ts, spelled exactly as the question bank spells it, so weak-topic matching and the dashboard's focus topics work. Then add a LessonContent object with the same topic to the course's array in lessons.ts. Its position in the array is its position in the course and decides what "Next" points to.
  3. Check the slug. Run the topic through topicSlug in your head: it must be unique within the exam. Two topics that differ only in punctuation would collide.
  4. Adding a course means a new COURSES entry, a new content array and a new BY_COURSE key of the form exam:section. A course with no BY_COURSE entry produces no lessons but still shows its heading on the hub with an empty grid. A new section also needs the backend's section pattern in learn.py and an entry in EXAMS in question_sources.py.
  5. Check the videos. Open the lesson and look at what the search returns. If the results are poor, the levers are the query templates and TRUSTED_CHANNELS in videos.py, not the lesson. Restart the backend to clear its cache.
  6. Run npm run type-check in frontend/. The Lesson type catches missing fields; it does not catch a wrong correctAnswer, so read the check once more.

10.8Edge cases and tests

  • No keys configured. With neither YOUTUBE_API_KEY nor SERPER_API_KEY, every search goes to DuckDuckGo, which rate limits. A cold lesson can then take several seconds (up to four searches, each with a possible 2 second backoff) and may return nothing; the panel says no videos were found and offers the YouTube search link. Nothing is cached, so the next visit tries again.
  • Serverless cache. _cache lives in process memory with no size bound. On a serverless deployment each instance has its own and loses it on a cold start, so the one-day TTL is a ceiling, not a promise.
  • Learned is per browser. Clearing site data or switching devices resets it, and two people on one browser share it.
  • Hub counts. Each course heading shows course.topics.length while the grid shows the lessons that exist for that section. They agree today because every topic has a lesson; if they ever diverge, the count will be wrong.
  • Weak topics across exams. Status badges match by topic name only. A weak "Algebra" from GRE games will also mark the SAT Algebra lesson as "Needs work".
  • Answer position. Nine of the 15 quick checks have option A as the answer. A student who notices will stop reading the options. When you write or edit a check, vary the position.
  • Unknown slug. /learn/sat/nope renders the not-found card inside the shell; it does not return a 404 status.

There are no automated tests. topicSlug, findLesson, _score, _iso_to_clock, _duration_minutes and _mentions are pure functions and the obvious first candidates.

Check yourself

Why is the video cache key on the server free of limit while the client's includes it?

The server caches the whole ranked list and slices it per request, so every limit can share one search. The client caches request promises, and a promise for one video cannot answer a request for six.

Why are the general queries run one after another instead of with asyncio.gather?

The free providers rate limit bursts. The comment in find_topic_videos says so, and serial queries also let the loop stop early once it has 15 non-GregMat videos.

What must be true of a new topic name for the dashboard to recommend its lesson?

It must appear in the course's topics and match, character for character, the topic the games report in question_attempts, since weak_topics comes from those reports.

A DuckDuckGo search hits a rate limit. What does the student see, and when is the search tried again?

The provider returns an empty list, the endpoint returns no videos, and the panel shows "No lesson videos found for this topic yet." with a YouTube search link. The empty result is not cached, so the next request searches again.

Where is "Mark as learned" stored, and what is its id for GRE Geometry?

In localStorage under learned_lessons, as "gre:Geometry".

Chapter eleven

11Dashboard, statistics and sessions

Every game and every mock exam ends the same way: the client posts one analytics object, the backend writes a session row, one row per question attempted, and an updated running total for the player. The dashboard and the statistics page are two views over those rows. This chapter follows a finished game into the database and back out onto the screen, including how the weak and strong topic lists are worked out and the places where the numbers are rougher than they look.

11.1Intent

The dashboard answers one question when you sign in: what should I do next? It names a focus topic, offers a game to practice it and a lesson to study it, and shows videos on it. Everything else on the page (the numbers, the recent sessions, the courses, the games you have not tried) supports that one suggestion.

The statistics page answers a different question: how am I doing? It shows totals, a right and wrong bar for every answer so far, an accuracy trend, the weak and strong topics, and a record per game.

The storage design behind both is deliberately simple. Raw history lives in game_sessions and question_attempts; a single user_stats row per player holds running totals so neither page has to aggregate history on every load.

11.3Model

The analytics object. Every game builds the same shape, checked on the server by GameAnalytics in schemas.py:

FieldTypeMeaning

SaveScoreRequest wraps it as { gameId, analytics }. The outer gameId is the one stored.

Tables. backend/database/schema.sql creates three tables, all with row level security and all cascading from auth.users.

  • game_sessions: a uuid id, user_id, game_id, score, accuracy as DECIMAL(5, 4) (a fraction from 0 to 1), correct_answers, wrong_answers, max_streak, average_response_time and created_at. Indexed on user_id and on created_at DESC.
  • question_attempts: a uuid id, session_id (cascading from the session), question_id as an integer, topic, difficulty, is_correct, time_spent and created_at. add_user_id_to_attempts.sql adds a denormalized, not-null user_id, two indexes (user_id, and user_id, topic) and rewrites the policies to use it, so per-user topic queries skip the join.
  • user_stats: one row per user (user_id is unique) with total_games_played, total_score, total_questions_answered, total_correct, total_wrong, overall_accuracy (a fraction), favorite_game, weak_topics and strong_topics as TEXT[], and updated_at.

On the client, frontend/lib/sessions.ts declares GameSession with the same fields as GameSessionResponse, and GameRecord (gameId, plays, bestScore, lastPlayed) for the per-game rollup.

11.4The server side

Saving. POST /api/games/save-score in backend/src/api/games.py takes a SaveScoreRequest, resolves the user with get_current_user and calls GameService(db).save_game_session(user_id, game_id, analytics). A failure is a 500 with the error text; success returns { success: true, sessionId }.

save_game_session in backend/src/services/game_service.py does three things in order, each its own request to Supabase:

  1. Insert the game_sessions row. accuracy is recomputed by _accuracy as correct / (correct + wrong), or 0 when there were no answers, so the game's own percentage is never trusted. max_streak is streakInfo.get("maxStreak", 0).
  2. If there are attempts, insert all of them in one call with the new session_id and the user_id.
  3. Call _update_user_stats.

Any exception is caught and returned as { success: False, error }.

Weak and strong topics. _update_user_stats first classifies this round's topics from topicPerformance, working from the counts rather than the game's percentage (the comment notes that games report it as a percent). A topic with at least one question is weak if fewer than half were right, strong if at least 80 percent were, and neither in between.

If the player has no user_stats row yet, it inserts one with this round's totals and lists. Otherwise it adds this round to each total, recomputes overall_accuracy as total_correct / total_questions_answered, and merges the lists: 

merged_weak   = (existing_weak   - this_round_strong) | this_round_weak
merged_strong = (existing_strong - this_round_weak)   | this_round_strong

So a topic moves from weak to strong (or back) as soon as one round says so, and a topic that lands in the middle band keeps whatever label it had. The lists are sets converted to Python lists, so their order is arbitrary.

Favorite game is never computed. favorite_game exists in the table, the response model and the dashboard's types, but no code writes it, so it is always null. The dashboard falls back to the most recently played game (section 11.6). To make it real, compute the most-played game_id from game_sessions in _update_user_stats and write it with the other totals.

Reading. backend/src/api/stats.py has two routes. GET /api/stats/user returns the caller's user_stats row as UserStatsResponse, or an all-zero response with empty lists and an empty updated_at if there is no row. GET /api/stats/sessions?limit= returns the newest limit sessions (default 10), newest first, as a list of GameSessionResponse. Neither reads question_attempts.

The agent's view. SupabaseAgentOps in backend/src/services/supabase_agent_ops.py is a set of static methods over the same tables for the AI question agent in agent.py. Two are in use: get_user_performance reads user_stats and reports accuracy as a percent; get_topic_performance reads every question_attempts row for the user and aggregates total, correct, accuracy and avg_time per topic. That is the only place per-attempt history is read. The class also has save_game_session, save_question_attempts and update_user_stats, a second write path that expects a different, snake_case game_data dictionary and never updates topic lists. Their only caller, ExamLearningAgent.update_performance, is never called, so these three methods are dead code. Games save through GameService only.

11.5The client

Saving. Each game container (ZombieGameContainer, WhackAMoleGameContainer, CarnivalGameContainer, SubwaySurfersGameContainer, SquidGameContainer, PacManGameContainer) registers an onGameOver handler that shows the results screen (the four arcade-style games also record a local high score) and then calls apiClient.saveScore(gameId, analytics), logging any error to the console. recordsByGame(sessions) walks the sessions, which arrive newest first, and builds one GameRecord per game in a Map: plays counted, best score kept, and lastPlayed taken from the first (newest) session seen. 11.6How it works

The dashboard, frontend/app/dashboard/page.tsx, loads the account, the stats and the last 20 sessions, and derives everything else.

  • Greeting. "Morning" before noon, "Afternoon" before 6 pm, else "Evening", plus the first word of the display name (or the email's local part). Under it, a test-day countdown if the profile has a future date, and the daily goal in minutes. An account without a profile gets a lime "Finish your profile" card.
  • The exam and its courses. The exam comes from the profile, defaulting to SAT; courses are the two COURSES for that exam.
  • Focus topics. weak_topics filtered to topics that belong to this exam's courses. focusTopic is the first of them, or the first topic of the first course (SAT Algebra, GRE Arithmetic) when there are none.
  • Next game. favorite_game if it is a known game, else the game of the most recent session, else 'whackamole'. Since favorite_game is always null today, this is in practice "the last thing you played".
  • Up next. A cobalt-soft card names the focus topic, says whether it is your weakest topic or a good place to start, and offers "Play game" and "Study the lesson". Playing calls practice(course), which stores the course's exam and section with setExamPrefs and pushes to /games/<nextGameId>/select. The game's cover fills the right side.
  • Numbers. Games played, accuracy (the stored fraction times 100) and questions answered, each with a skeleton until stats arrive.
  • Watch. RecommendedVideos asks for three videos on the focus topic through useTopicVideos and hides itself if none come back.
  • Recent sessions. Up to eight SessionCards, tinted lime-soft at 80 percent accuracy or more, white at 50 or more, coral-soft below, with right and wrong counts, best streak, an accuracy bar and the score. With no sessions, a dashed empty state links to the games.
  • The aside. The exam's courses as tiles (each starts practice), up to four focus topics with a "Practice" button, and "Haven't tried yet": up to four games whose id is not among the last 20 sessions, drawn with GameCover.

The statistics page, frontend/app/stats/page.tsx, loads stats and the last 50 sessions. Until both arrive it shows four skeleton tiles; if total_games_played is 0 (or stats failed) it shows "Nothing to show yet". Otherwise:

  • Four tiles: games played, accuracy, questions answered, and best streak, which is the maximum max_streak over the 50 loaded sessions.
  • "Every answer so far": a lime segment over a coral bar, sized by overall_accuracy, labelled with the totals.
  • AccuracyTrend, when there are at least two sessions: up to TREND_LENGTH (12) bars, oldest on the left, colored lime, cobalt or coral by the same 80 and 50 percent thresholds, each with a title naming the game.
  • Two TopicLists, "Work on these" and "Going well". Their empty hints state the rules in plain words: under half right, and at least four in five.
  • "By game" from recordsByGame, each linking to that game's select page, and the newest 15 sessions as a list.

11.7Edge cases and tests

There are no automated tests for this area. These are the behaviors to know.

  • Mock exams are sessions too. A mock exam is stored with game_id 'mock-exam'. When picking "Up next", the dashboard skips any session whose id is not in games, so a mock exam never becomes the suggested game. The stats page's "By game" card still links mock exams to /games/mock-exam/select, which renders "That game doesn't exist"; it should link to /mock instead.
  • Topic labels are jumpy. Labels come from single rounds, so one wrong answer in a topic marks it weak until a later round scores 80 percent or better on it. They are not computed from the attempt history, even though get_topic_performance could.
  • No transaction. If the attempts insert or the stats update fails after the session insert, the route returns 500 but the session row stays, and the totals miss that round. The client does not retry, so nothing is duplicated, but nothing is repaired either.
  • Lost updates. _update_user_stats reads the row, adds in Python and writes it back. Two games finishing at the same moment for one player (two tabs) can overwrite each other. A Postgres function doing the increment in one statement would fix it.
  • Silent failures. getUserStats returns null on error. The stats page then shows "Nothing to show yet"; the dashboard's number tiles keep their skeletons, because they treat null as "still loading".
  • Windows, not history. "Haven't tried yet" looks at the last 20 sessions and "Best streak" at the last 50, so a game played long ago can reappear as untried and an old streak can drop off.
  • Unbounded limit. /api/stats/sessions accepts any limit; the clients ask for 20 and 50. Add an upper bound with Query(..., le=...) if you expose it further.
  • Question ids are integers. question_attempts.question_id and QuestionAttempt.questionId are both integers; a question source with string ids must map them first or the whole save fails validation.
  • Leftovers. games.py declares an unused security = HTTPBearer(), and backend/src/api/games.ts, backend/src/services/gameScoreService.ts and backend/src/types/database.ts are TypeScript from an earlier design that the FastAPI app never loads.

To check the path by hand, finish a short game, then compare the new game_sessions row, its question_attempts and the user_stats row in the Supabase table editor against the results screen. A good unit test would call _update_user_stats with a stub client and assert the merged lists for a topic that moves from weak to strong.

A round has 3 Geometry questions and the player gets 2 right. Geometry was weak before. What is it after?

Nothing is written. The request fails with 401, the container logs the error, and the round exists only on the results screen and in the local arcade high score.

Two features sit beside the games. The mock exam is a timed section in test-day format: one clock, no feedback until the end, a score report after. "My material" lets a student upload a practice test or notes, review the questions found in it, and approve the ones that should appear in their games and mock exams. Both reuse the question engine of chapter 7 rather than adding their own.

12.1Intent

Games are good for repetition, but a student also needs to feel the real exam's pace and to see an honest score afterwards. The mock exam gives them that with the same questions the games use. It lives entirely in the browser: one page, three screens (setup, exam, results), and a single call to save the result alongside game sessions so it feeds statistics and weak topics.

Students also have their own material: a teacher's handout, a practice test PDF, class notes. The materials feature turns that into questions in the standard game format. The design rule is that nothing from an upload reaches a game until the student has looked at it. Every question starts as pending, and a question cannot be approved without a correct answer.

A material is a name, an owner, an exam and a section. It holds no text and no file: the upload is read once, turned into rows in custom_questions, and discarded. There is no storage bucket. If the parser misses a question, the only way to get it is to upload again.

Three indexes support the reads: by materials.user_id, by custom_questions.material_id, and a compound one on (user_id, exam, section, status), which is exactly the filter load_custom_questions uses. Both tables have RLS enabled with an owner-only policy for all operations.

Ownership is enforced in Python. The backend's Database.get_client prefers SUPABASE_SERVICE_ROLE_KEY, which bypasses RLS. Every query in materials.py therefore filters by user_id itself, and _own_material returns 404 for a material that is not the caller's. The RLS policies are a backstop. If the backend ever ran with only the anon key, the inserts would fail, because auth.uid() would be null.

Upload

upload_material takes form fields exam and section (both Literal), name, text, generate and an optional file. If a file is present it reads all of it, checks the size, and replaces text with extract_text(filename, content); pasted text is ignored in that case. An empty name falls back to the file name, and later to "Untitled material". Then:

  1. Text shorter than 40 characters after trimming is a 400 that suggests the PDF is scanned.
  2. parse_questions(text) runs the rule-based parser.
  3. If generate is set or the parser found nothing, questions_from_llm runs too.
  4. merge_questions keeps every parsed question and adds model questions whose first 60 normalized characters are new.
  5. No questions at all is a 422 that explains the numbered format.
  6. One materials row is inserted, then all questions in one insert, each with the material's exam and section, topic defaulting to "My material" and difficulty to medium. The response is the material and the saved rows.

Reading files

extract_text treats a file as PDF if its name ends in .pdf or its first five bytes are %PDF-, and reads it with pypdf's PdfReader, joining each page's extract_text(). There is no OCR, so a scanned PDF yields little or no text. Anything else is decoded as UTF-8 with errors="replace". The file input in the browser accepts .pdf, .txt, .md, application/pdf and text/plain, but the server does not check the type: a Word document would be decoded as noise and most likely fail with "No questions found".

The parser

parse_questions reads line by line with five regular expressions.

PatternMatches
QUESTION_START1., 12), 3: or Question 4. followed by text; up to three digits
OPTION_STARTA), b., (C) followed by text; letters A to E
ANSWER_LINEAnswer: C, Correct answer is (B)
EXPLANATION_LINEExplanation:, Solution:, Rationale:
ANSWER_KEY_HEADINGA line that is just Answer Key or Answers

An answer key heading ends the questions: everything after it is scanned with ANSWER_KEY_ENTRY for pairs like 1. C or 2-D. Options must arrive in order (A, then B, then C), so a line that happens to start with a later letter, such as "C. Smith wrote", is not taken as a choice. A new numbered line starts a new question only once the current one has options, so a numbered list inside a stem stays part of it. Continuation lines join the stem, the last option or the explanation, depending on what came last. A question survives with two to five options. Its answer comes from its own answer line, else the key, else it is None. Parsed questions are origin: "extracted" and have no topic or difficulty.

The model

questions_from_llm imports the agent's get_llm_client lazily, so the parser still works where the agent's dependencies are missing, and returns an empty list when OPENROUTER_API_KEY is not set. It splits the text into 12,000-character chunks, keeps the first four, and sends them in parallel with temperature 0.3. The prompt asks the model to extract every multiple-choice question exactly, to give correctAnswer only when the material states it, and, with generate, to write up to eight original questions per chunk with fromMaterial: false.

_normalize_llm_question applies the same honesty test as the question engine: a question counts as extracted only if the model said so and the first 50 normalized characters of its stem appear in the chunk. A generated question without a valid answer is dropped, because it cannot be reviewed into shape. An extracted one without an answer is kept with correctAnswer: None.

Review

QuestionUpdate accepts question, options, correct_answer, explanation and status. update_question merges the change over the stored row and rejects an answer outside the options (400) and an approval without an answer (400). approve_all approves the rows with an answer and returns approved and needs_answer counts. delete_material deletes the questions and then the material; the foreign key cascade would do the first step anyway.

12.6How it works

  1. A student pastes a ten-question worksheet with an "Answer Key" at the end and leaves the checkbox off.
  2. parse_questions finds ten questions and takes their answers from the key. The model is not called.
  3. Ten pending rows are saved. The page opens them; the student clicks "Approve all with answers".
  4. The next time a signed-in game or mock exam for that exam and section asks for questions, load_custom_questions returns up to half the requested limit from these rows, each with source: 'custom' and sourceName set to the material's name, so the question panel shows "From" and the material name.

With no OPENROUTER_API_KEY, step 2 is all there is: the checkbox does nothing and unnumbered notes produce a 422. Custom questions still appear in the GRE when no other source is available, which makes them the main way to get real GRE questions into a keyless setup.

12.7Edge cases and tests

  • Pasted text is not capped. MAX_TEXT_CHARS applies only inside extract_text; a large paste goes to the parser in full.
  • The whole file is read before the size check. On Vercel the platform limit stops oversized bodies first; elsewhere the server holds the bytes in memory.
  • Only the first 48,000 characters reach the model. The parser sees up to 400,000.
  • Unhandled rejections. On the materials page, delete question, approve all and delete material have no try; a failure shows nothing to the user.
  • The file input is not cleared. After an upload setFile(null) resets state, but the uncontrolled input still shows the old file name.
  • Unreachable mock error. The mock page shows an error when no questions load, but fetchAIQuestions always falls back to the bank, which is never empty. With the backend down, a 54-question full section silently becomes a 9-question exam, with the clock scaled to match.
  • The SAT blurb overstates. Setup says SAT questions are official ones. Custom questions and, when the College Board falls short, model questions can be mixed in.
  • Mock exams change game settings. Starting one writes its exam and section to exam_prefs.
  • No resume. Exam state is React state; a reload loses the attempt.
  • Delete is idempotent. DELETE /api/materials/questions/{question_id} returns success for an id that does not exist.

There are no automated tests. parse_questions is the obvious first target: it is a pure function with many formats to pin, including answer keys, out-of-order letters and multi-line options.

Check yourself

Where is the uploaded PDF stored?

Nowhere. It is read in memory, turned into custom_questions rows and discarded. The materials row holds only a name, owner, exam and section.

When is the model called during an upload?

When generate is true, or when the parser found no questions, and only if OPENROUTER_API_KEY is set.

Why can a generated question never be saved without an answer, while an extracted one can?

An extracted question's answer may be in the student's head or answer sheet, so review can supply it. A generated question with no answer has nothing to check against, so _normalize_llm_question drops it.

How does the mock exam's clock length follow from the exam?

It is the number of questions actually loaded times the section's secondsPerQuestion, so a shorter set gets a shorter clock.

The backend uses the service role key. What stops one user reading another's material?

The routes filter every query by the caller's user_id and _own_material 404s on foreign ids. RLS would only apply to a client using a user's own token or the anon key.

13Data model and security

Six tables in Supabase Postgres, every one keyed to auth.users and every one with Row Level Security switched on. None of that RLS is what protects the data in practice: the browser never talks to Supabase, and the FastAPI backend reaches the database with the service-role key, which bypasses every policy. What protects a user's rows is the backend's own user_id filters and the way it checks the bearer token. This chapter reads both honestly.

The first half is the schema: which SQL file is current, every column, index, trigger and policy, and how the tables relate. The second half is the security model: who writes each table, how a JWT becomes a user id in auth_service.py, what the browser keeps in storage, CORS, input validation, HTML sanitizing, and a checklist for contributors. Several weaknesses turn up along the way. They are stated plainly, because a contributor who does not know about them will build on them.

"Own" is auth.uid() = user_id in every case. An UPDATE policy without WITH CHECK reuses its USING expression for the new row, so a user could not move their stats or profile to another user id even through it.

Now the part that matters. Database.get_client() in backend/src/utils/database.py builds one process-wide client from SUPABASE_URL (or NEXT_PUBLIC_SUPABASE_URL) and the first key it finds among SUPABASE_SERVICE_ROLE_KEY, SUPABASE_SERVICE_KEY and NEXT_PUBLIC_SUPABASE_ANON_KEY. With a service-role key, Postgres sees the service_role role, which bypasses RLS entirely. Every route uses this client through get_db(). The frontend has @supabase/supabase-js and @supabase/ssr in package.json but never imports them; no browser code talks to Supabase. So in normal operation no policy is ever evaluated. The policies are a second line that only comes into play if someone reaches the database with the anon key and a user JWT, which this codebase never does.

Authorization therefore lives in Python. Every query on user data must carry .eq("user_id", current_user["id"]) or check ownership first, as _own_material() in materials.py does. A route that forgets is a cross-user leak, and RLS will not catch it. One already exists: GET /api/questions/topics selects topic from all of question_attempts with no user filter and returns every topic any user has practised. It is low sensitivity, but it is the pattern to avoid.

If the service-role key is missing, the backend silently runs as anon get_client() falls back to NEXT_PUBLIC_SUPABASE_ANON_KEY. With the anon key and no user session, auth.uid() is null, every policy fails, reads return empty lists and writes are rejected. The symptom is "stats are always zero" and "save-score returns 500", not a startup error.
Signing in on the shared client may change who the client is AuthService.signup and login call auth.sign_up and auth.sign_in_with_password on the same singleton client every route uses for data. In supabase-py 2.x the client listens for its own auth events, and on SIGNED_IN it replaces the Authorization header it sends to PostgREST with the new session's access token. If that is the behaviour of the installed version, then after the first login in a process every later query runs as that user, under RLS, instead of as the service role. A single developer testing with one account would never notice, because their own rows pass their own policies. A second user would see empty reads and failed writes, and everyone would fail once the first user's token expires. Database.get_auth_client() creates a separate client for auth and looks meant for this, but nothing calls it, and it too prefers the anon key and falls back to the service-role key. Doing auth calls on a fresh, separate client is the fix to make and test.

13.7How a token becomes a user

Login goes through the backend. POST /api/auth/login calls Supabase's sign_in_with_password and returns the session's access_token, a Supabase JWT. The frontend sends it back as Authorization: Bearer .... Protected routes depend on get_current_user in api/auth.py, which uses HTTPBearer(auto_error=False), returns 401 Missing authorization token when there is no header, and otherwise calls AuthService.get_user(token): 

# backend/src/services/auth_service.py, get_user (abridged)
decoded = jwt.decode(token, options={"verify_signature": False})
if decoded and "sub" in decoded:
    user_id = decoded["sub"]
    user_email = decoded.get("email", "")
    exp = decoded.get("exp", 0)
    if exp and exp < time.time():
        return None
    # For now, we'll trust the JWT payload since it's from Supabase
    return {"id": user_id, "email": user_email}
The signature is never verified get_user decodes the token with verify_signature: False and checks only that sub exists and that exp, if present, is in the future. Anyone can build a token by hand with another user's id in sub and no exp, send it, and be treated as that user. Because every query then runs with the service-role key (13.5), that is full read and write access to the victim's profile, stats, sessions and materials. User ids are UUIDs and are not shown in the UI, which raises the bar but is not a control. The fix is to verify the token: either decode with the project's JWT secret or JWKS (HS256 or the project's asymmetric key, with audience="authenticated"), or call Supabase's auth.get_user(token) on a separate client. No JWT secret variable exists in the backend today, so this needs a new environment variable or a network call per request. python-jose is in requirements.txt but unused; get_user imports jwt (PyJWT), which requirements.txt does not list and which only arrives as a dependency of another package.

The other auth routes are thin. POST /api/auth/logout does nothing on the server; its comment says the token "will expire naturally". Login returns no refresh token to the browser (TokenResponse has no field for it, although AuthService.login reads one), so a session ends when the access token expires, which is the Supabase project's JWT expiry setting. GET /api/questions/ uses get_current_user_optional, which returns None on a missing or bad token instead of raising.

13.9CORS

backend/src/main.py adds Starlette's CORSMiddleware before any router. The allowed origins are the comma-separated ALLOWED_ORIGINS variable plus four fixed development origins: http://localhost:3000, http://localhost:3001, http://127.0.0.1:3000 and http://127.0.0.1:3001. The rest of the configuration is permissive: allow_credentials=True, methods GET POST PUT DELETE OPTIONS PATCH HEAD, allow_headers=["*"], expose_headers=["*"], max_age=3600.

Since auth is a bearer header and not a cookie the backend reads, credentials mode adds nothing; the client sets credentials: 'include' anyway. auth.py also defines explicit OPTIONS handlers for /signup and /login that echo back any Origin with credentials allowed. The middleware answers real preflights before they reach a route, so these handlers only run for a bare OPTIONS request, but they reflect any origin and should be deleted rather than copied.

The global @app.exception_handler(Exception) returns {"detail": "Internal server error"} with status 500. In Starlette that handler runs in the outermost middleware, outside CORS, so the 500 has no Access-Control-Allow-Origin header and the browser reports a network failure rather than the error. Routes that raise HTTPException are not affected.

13.11HTML sanitizing

Official SAT questions arrive as HTML with MathML. CollegeBoardSource._normalize in question_sources.py stores two forms: plain text from html_to_text for games that draw text themselves, and questionHtml, passageHtml, optionsHtml and explanationHtml from sanitize_html for rich display. No other source produces HTML; web, AI, custom and built-in questions are text only.

sanitize_html in backend/src/utils/html_utils.py parses with the standard library's HTMLParser into its own tree and re-renders it from allowlists:

  • DROPPED_TAGS (script, style, svg, img, iframe, object, embed, form, button and others) are removed with everything inside them, as is any element whose class contains sr-only.
  • HTML_TAGS (paragraphs, inline formatting, lists, tables) and MATH_TAGS (the MathML presentation elements) are kept.
  • Any other tag is unwrapped: the tag goes, its children stay.
  • Only attributes in KEPT_ATTRS survive: alttext, display, mathvariant, colspan, rowspan, columnalign, linethickness, all HTML-escaped. No href, src, style or event handler can pass.
  • Text is escaped. mfenced becomes an mrow with explicit mo brackets; a span with underline in its style becomes u.

The frontend does not trust this alone. QuestionContent in frontend/components/QuestionContent.tsx runs a second allowlist, with the same tags and attributes, through DOMParser before dangerouslySetInnerHTML. It removes disallowed elements outright, contents included. That component and the two JSON-LD script tags in app/layout.tsx and app/developer/page.tsx are the only uses of dangerouslySetInnerHTML in the app.

13.12A security checklist for contributors

  1. Every new route that touches user data depends on get_current_user and filters by current_user["id"]. RLS will not save you; the backend is the service role.
  2. When you take an id from the path, prove ownership before acting on it, the way _own_material and the .eq("user_id", ...) on question updates do.
  3. Never trust a JWT you have not verified. Until get_user verifies signatures, treat every user id as attacker-chosen when you judge the impact of a change.
  4. Keep auth calls off the shared data client. Do not add another db.auth.* call to it.
  5. New tables go in a new SQL file and in reset.sql, with RLS enabled and owner policies, even though the backend bypasses them. Update the README's setup step.
  6. Constrain new inputs in the Pydantic model or with Query(...): lengths, ranges, literals. Do not rely on the frontend.
  7. Any HTML that reaches the DOM goes through sanitize_html on the server and QuestionContent on the client. Do not add a new dangerouslySetInnerHTML.
  8. Do not return str(e) in a detail. Several routes do today (signup, profile, stats, questions, /api/health/supabase), which leaks database and library messages.
  9. Never add a secret to a NEXT_PUBLIC_ variable or to frontend code. The service-role key belongs only in the backend's environment as SUPABASE_SERVICE_ROLE_KEY.
  10. Add a production origin to ALLOWED_ORIGINS; never widen CORS to * with credentials.

You run reset.sql on a fresh project and uploads return 500. Why?

reset.sql does not create materials or custom_questions; add_materials.sql does, and the documented setup runs it second.

What does an attacker need to act as another user today?

That user's id. get_user does not verify the JWT signature, so a hand-made token with that id in sub and no exp is accepted.

The dashboard loads (no redirect to login) but every stat is empty and the console shows 401s. What happened?

The access token expired. The auth_token cookie lasts 7 days and the middleware only checks that it exists; the backend rejects the expired token and there is no refresh token to renew it.

So the agent's per-user queries and the owner policy are one indexed comparison instead of a join. add_user_id_to_attempts.sql added it; reset.sql builds it in.

user_stats.favorite_game.

14.1Conventions

  • Auth. "Required" means the route depends on get_current_user from api/auth.py: an Authorization: Bearer <token> header carrying the Supabase access token from login. No header gives 401 Missing authorization token; a token that cannot be decoded, has no sub or has expired gives 401 Invalid or expired token. The signature is not checked (13.7).
  • Errors. Every error body is {"detail": ...}. For an HTTPException, detail is a string. For a request that fails validation, it is FastAPI's 422 list of {loc, msg, type} objects. An unhandled exception becomes 500 {"detail": "Internal server error"} from the global handler in main.py, without CORS headers.
  • Trailing slashes. Two routes are declared as "/", so their canonical paths end in a slash: /api/health/, /api/questions/. A request without the slash gets a 307 redirect. /api/profile and /api/materials are declared as "" and have no slash.
  • Naming. Request bodies for games use camelCase (gameId, correctAnswers); rows read from the database come back snake_case (game_id, correct_answer). Both styles are in use; follow the neighbouring route.

Examples use two placeholders: $API for the base URL and $TOKEN for an access token.

14.9The frontend client

frontend/lib/api/client.ts exports one instance, apiClient, of the class ApiClient. Its base URL is NEXT_PUBLIC_API_URL, defaulting to http://localhost:8000; next.config.js repeats the same default. The browser calls the backend directly on that origin. frontend/vercel.json has an /api/:path* rewrite to a placeholder Railway URL, but the client never uses relative /api paths, so that rewrite does nothing.

Tokens

The constructor reads auth_token from localStorage, or from the auth_token cookie if storage is empty, copying it back to storage. setToken(token) writes both, the cookie with max-age=604800 and SameSite=Lax; setToken(null) clears both. login and signup call setToken when the response has an access_token; logout calls setToken(null) in a finally, so the token is cleared even if the request fails. There is no refresh: when the token expires, calls return 401 until the user signs in again.

Requests and errors

The private request<T>(endpoint, options) sets Content-Type: application/json, adds Authorization: Bearer when a token is held, and fetches with mode: 'cors' and credentials: 'include'. On a non-2xx response it parses the body (falling back to {detail: statusText}) and throws new Error(error.detail || 'HTTP error! status: N'). On success it returns parsed JSON when the content type is JSON, else {}. Every failure is logged with console.error('API request failed:', ...) and rethrown.

Three consequences follow. The status code is lost: callers see only a message, so a 401 and a 500 look alike, and nothing signs the user out on 401. A 422 has a list in detail, and new Error(list) produces the message [object Object]; pages that show err.message will show that. And a CORS-less 500 surfaces as a TypeError from fetch, not as the server's message.

uploadMaterial is the one method that bypasses request: it builds a FormData and calls fetch itself so the browser sets the multipart boundary, adds the bearer header by hand, and throws body.detail the same way. getUserStats and getRecentSessions catch everything and return null and []. getQuestions and getTopics have no callers.

14.10Adding a route

  1. Put the handler in the router file for its area under backend/src/api/, or a new file registered in main.py with a prefix and tag.
  2. Depend on get_current_user and get_db; filter every query by current_user["id"].
  3. Define request and response models in backend/src/models/schemas.py with real constraints, and set response_model.
  4. Raise HTTPException with a sentence a user can read; do not put str(e) in it.
  5. Add a typed method to ApiClient and call it from the page, not fetch.
  6. Add the route to this chapter.

15.2The backend on Vercel

The backend is one Python serverless function. Vercel's Python runtime installs backend/requirements.txt, finds backend/api/index.py, and serves the ASGI object named app that the file exposes. The file is four lines of real code: 

# backend/api/index.py
backend_dir = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
if backend_dir not in sys.path:
    sys.path.insert(0, backend_dir)

from src.main import app  # noqa: E402,F401

It puts backend/ on the import path so from src.api import ... resolves exactly as it does locally, then re-exports the FastAPI app. There is no adapter such as Mangum; the runtime speaks ASGI directly. backend/vercel.json sends every path to that one function: 

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/api/index" }
  ]
}

The rewrite changes which function runs, not the path FastAPI sees, so /api/health/ still matches the health router. The file sets no maxDuration or memory, so the platform defaults apply. Question generation that calls the College Board bank, a web search and a model in sequence is the slowest request; if it starts timing out, a functions block in this file is the place to raise the limit.

backend/.vercelignore keeps the upload small and secret-free. It excludes .env and .env.*, venv/, caches, the alternative deploy files (Dockerfile, fly.toml, railway.json, render.yaml), every *.sh script, and the whole database/ folder. The SQL never ships, because nothing at runtime reads it.

Serverless has two consequences worth knowing. The in-memory caches (the 24-hour video cache in src/services/videos.py and the College Board index cache in src/services/question_sources.py) live per warm instance and vanish on a cold start. And Database.get_client() keeps one Supabase client per instance, shared by every request that instance serves.

15.3The frontend on Vercel

frontend/vercel.json declares the Next.js framework with npm install, npm run build and an output directory of .next. It also contains a rewrite that is left over from an earlier hosting plan: 

"rewrites": [
  {
    "source": "/api/:path*",
    "destination": "https://your-backend-url.railway.app/api/:path*"
  }
]

The destination is a placeholder that does not resolve. Nothing depends on it, because the browser calls the API by its full URL from NEXT_PUBLIC_API_URL, never through a relative /api path, and frontend/middleware.ts skips /api paths. A request to www.satistic.tech/api/... fails. Removing the block, or pointing it at https://api.satistic.tech, is a safe cleanup.

frontend/next.config.js sets reactStrictMode, allows remote images from one host for the developer page, sets output: 'standalone' (which Vercel ignores; it matters only for self-hosting in a container), and copies NEXT_PUBLIC_API_URL into the build's env with a default of http://localhost:8000.

The API URL is baked into the build NEXT_PUBLIC_API_URL is inlined into the JavaScript bundle at build time. Changing it in the Vercel dashboard does nothing until the frontend is redeployed. If it is missing from the project, the build succeeds and production quietly calls http://localhost:8000, which shows up as every API call failing in users' browsers.

frontend/.vercelignore excludes .env.local, .env.*.local, node_modules/, .next/, .vercel/ and log files. frontend/deploy.sh builds and runs npx vercel --prod by hand; with the Git integration you do not need it, and its reminder to set Supabase variables on the frontend is out of date (see 15.4).

15.5Domains, CORS and deployment protection

Both domains are added in each project's Settings, Domains, with DNS records at the registrar pointing at Vercel. The site's canonical host is www.satistic.tech; it is SITE_URL in frontend/lib/site.ts.

Why the API has its own domain. Vercel's deployment protection puts a Vercel login in front of generated deployment URLs (the *.vercel.app hosts). A browser fetch from the site to such a URL gets a 401 and a login page instead of JSON, and the CORS preflight fails with it, so the site looks broken while the API is fine. A custom production domain is not covered by standard protection, so api.satistic.tech is reachable by every browser while the generated URLs stay private. Point NEXT_PUBLIC_API_URL at the custom domain, never at a vercel.app URL.

CORS. backend/src/main.py builds the allow list once, at import: 

allowed_origins = os.getenv("ALLOWED_ORIGINS", "").split(",") if os.getenv("ALLOWED_ORIGINS") else []
default_origins = [
    "http://localhost:3000",
    "http://localhost:3001",
    "http://127.0.0.1:3000",
    "http://127.0.0.1:3001",
]
allowed_origins = [origin for origin in allowed_origins + default_origins if origin]

The middleware allows credentials, the methods GET, POST, PUT, DELETE, OPTIONS, PATCH and HEAD, any header, and caches a preflight for 3600 seconds. Matching is exact: https://satistic.tech and https://www.satistic.tech are different origins, and the split does not trim spaces, so write the list with commas only. A frontend preview deployment has its own origin, which is not on the list, so previews can load pages but their API calls to production are blocked. Test API changes locally, not on previews.

15.6Changing the database

There is no migration runner. Schema lives in SQL files under backend/database/, and a change reaches production when someone pastes it into the Supabase SQL Editor for the production project. CONTRIBUTING.md sets the rule: a schema change is a new SQL file, and the same change is folded into reset.sql so a fresh project gets the whole schema in one run. Every new table gets RLS enabled and policies, even though the backend uses the service-role key.

Order matters because the two sides deploy separately:

  1. Write the change additively: CREATE TABLE IF NOT EXISTS, ADD COLUMN with a default, and DROP POLICY IF EXISTS before CREATE POLICY, so the file can be rerun.
  2. Run it on a development project and exercise the code against it.
  3. Run it on production before merging code that reads the new column or table.
  4. Merge. The new backend deploys against a schema that already fits it.
  5. Remove old columns only in a later change, after no deployed code reads them.

A new project gets the schema from two files, run in order: reset.sql, then add_materials.sql, which creates materials and custom_questions. Never run reset.sql on production. It drops the core tables and deletes every user in auth.users. Chapter 13 lists the tables and policies.

15.7Search engines

Three files in the frontend describe the site to crawlers, and all of them build URLs from SITE_URL in frontend/lib/site.ts:

  • frontend/app/sitemap.ts lists four public URLs: the home page, /developer, /signup and /login, with lastModified set to build time.
  • frontend/app/robots.ts allows /, disallows /dashboard, /games, /learn, /materials, /mock, /profile and /stats, and points at /sitemap.xml.
  • frontend/app/layout.tsx sets metadataBase, the title template %s | SATistics, the description and application name from lib/site.ts, and renders JSON-LD through the jsonLd helper, which escapes < so the data cannot close the script tag.

The robots disallow list matches protectedPrefixes in frontend/middleware.ts route for route. Keep the two lists in step when you add a signed-in route. If you run your own copy on another domain, SITE_URL is the one value to change.

15.8Rolling back

Every deployment Vercel has built stays available. To undo a bad release, open the project's Deployments tab, find the last good production deployment, and use Instant Rollback (or "Promote to Production"). The CLI does the same with vercel rollback from a directory linked to the project. The switch is immediate because nothing is rebuilt.

Three things to keep in mind:

  • The projects roll back separately. If a change touched both the API and the client, decide whether the old frontend works with the new backend before rolling back only one.
  • An instant rollback keeps the old build's inlined values. A frontend deployment carries the NEXT_PUBLIC_API_URL it was built with.
  • The database does not roll back. Nothing reverses a SQL change. This is why schema changes are additive and run first.

After a rollback, fix forward on a branch: git revert the bad commit in a pull request, so main matches what is serving again and the next push does not reintroduce the bug.

16.2Branches and commits

Branch from main for every change and open a pull request. Never push to main directly: both Vercel projects deploy it to production on every push (15.1), and nothing makes the deploy wait for CI. 

git switch main
git pull
git switch -c add-pac-man-hint-button
# ...edit, check, commit...
git push -u origin add-pac-man-hint-button

Commits follow the history that is already there:

  • Small and focused. One logical change per commit. A refactor and a feature are separate commits, and usually separate pull requests.
  • Imperative subject lines that say what changed for the user: "Add hints, material uploads, arcade skin and touch support to the games", "Fix backend Vercel deployment". Not "updated files". A scope prefix such as fix(learn): or feat(games): is welcome but not required.

  • No AI co-author trailers. If a tool helped, you are still the author and the one responsible for the change.
  • No secrets, ever. Not in code, docs, fixtures or screenshots. CI runs a gitleaks scan on every pull request, but it is a net, not a plan.

Adding a game

16.7Code style

There is no formatter configuration in the repository, so match the file you are editing. These are the conventions the code follows.

TypeScript and React

  • Strict mode. frontend/tsconfig.json sets "strict": true. Write real types; a handful of files still use any (for example the auth responses in lib/api/client.ts), and replacing them is welcome, adding more is not.
  • Path aliases. Import with @/lib/..., @/components/..., @/games/... and @/types/..., as configured in tsconfig.json, not with long relative paths.
  • App Router. Each page is frontend/app/<route>/page.tsx. Interactive pages and components start with 'use client'; keep the directive as low in the tree as you can. A new signed-in route also goes into protectedPrefixes in frontend/middleware.ts and the disallow list in frontend/app/robots.ts.
  • Components. Named function components with a Props interface above them, one main component per file, grouped by feature under components/ (exam/, learn/, brand/, arcade/). Shared data and helpers live in lib/, one concern per file.
  • Network. All API calls go through the single apiClient in lib/api/client.ts. Do not call fetch against the backend from a component.
  • Lint. ESLint extends next/core-web-vitals (frontend/.eslintrc.json).

Styling

  • Theme tokens. Use the colours in frontend/tailwind.config.js: paper, ink, mist, and cobalt, lime and coral with their soft variants. Use the shadows shadow-brutal, shadow-brutal-sm, shadow-brutal-lg and shadow-glass, and the font-display and font-serif families. Do not add raw hex values to components.
  • Component classes. Reuse the classes in frontend/app/globals.css: .btn with .btn-cobalt, .btn-ink, .btn-lime or .btn-paper, plus .brutal, .glass, .field and .chip.
  • Copy. Sentence case, plain verbs, no emoji in the interface. Chapter 4 has the full rules.

Python

  • Layers. Routers in src/api/ stay thin: validate, authorise, call a service, shape the response. Services in src/services/ hold the logic. Pydantic models live in src/models/schemas.py, and their field names are camelCase (gameId) because they mirror the TypeScript types.
  • Imports are absolute from the src package: from src.services.videos import find_topic_videos.
  • Type hints use typing (List, Dict, Optional, Literal). Keep code runnable on Python 3.9: no X | None unions and no match statements.
  • Docstrings open every module and route, in one plain sentence.
  • Blocking work such as a Supabase query or a DuckDuckGo search inside an async route runs through asyncio.to_thread, as questions.py and videos.py do.
  • Configuration comes from os.getenv with a documented default, and every new name goes into backend/.env.example.

CI is green on your backend pull request. What has it not checked?

Any route's behaviour. The backend job only imports src.main, so it proves modules load and routers register, nothing more. You have to start the server and call the route.

Why must a new backend query filter by current_user["id"] when every table has RLS?

The backend's client uses the service-role key, which bypasses RLS. The filter in the handler is the only boundary between users.

You add a signed-in page at /review. Which two lists change besides the page itself?

Your chapter edit builds in the browser but stops build.py. What is the usual cause?

It is not well-formed XML: an unclosed tag, an unescaped & or <, or a void element that is not self-closed.

Appendix B

BDecisions

This is a log of the design and engineering decisions that can be read off the code. Each entry gives the decision, the reason (from a comment in the code where there is one), and the consequence a contributor lives with. None of them is sacred. If you change one, change the entry too.

B.1A separate FastAPI backend

Decision. All data access and every outside call runs in a Python FastAPI app in backend/, deployed as its own Vercel project. The Next.js app has no API routes.

Reason. The question pipeline is Python: the openai client for OpenRouter, ddgs for DuckDuckGo, pypdf for uploads, and httpx for the College Board and YouTube. Keeping secrets and slow work off the browser and out of the page server keeps the frontend a static-ish client.

Consequence. Two deploys, two sets of environment variables, and CORS: ALLOWED_ORIGINS must name the frontend's origin. The frontend must be built with NEXT_PUBLIC_API_URL pointing at the backend. A change that spans both needs both deployed.

B.2Supabase for auth and data, behind the backend

Decision. Supabase provides Auth and Postgres. Only the backend talks to it, through one client built by Database.get_client, which prefers SUPABASE_SERVICE_ROLE_KEY.

Reason. One client with full rights is simple: no per-request client, no RLS to reason about in each query. The comment in utils/database.py says it plainly: the "service role key bypasses RLS".

Consequence. The RLS policies in backend/database/*.sql are defence in depth only. Isolation between users depends on every query filtering on user_id. The frontend's @supabase/ssr and @supabase/supabase-js dependencies are unused.

B.3A bearer token in localStorage and a cookie

Decision. The Supabase access token is returned by /api/auth/login, stored by ApiClient.setToken under auth_token in localStorage and a seven-day cookie, and sent as Authorization: Bearer. middleware.ts checks only that the cookie exists. AuthService.get_user decodes the JWT without verifying its signature and checks exp.

Reason. The cookie exists so the edge middleware can redirect signed-out visitors before a page renders; the comment in setToken says "Also set cookie for middleware auth check". Decoding without a network call keeps every request fast.

Consequence. No refresh: when the token expires, calls fail with 401 until the student logs in again. And because the signature is not checked while the backend holds the service-role key, a forged token is trusted. Verifying the JWT is the most important open fix in the codebase.

B.4Official questions first, then the LLM, then an offline bank

Decision. ExamLearningAgent.generate_questions takes SAT questions from the College Board Educator Question Bank (CollegeBoardSource). Any shortfall, and every GRE question, comes from one LLM call that is given up to four web pages of practice questions (WebQuestionSource.find_pages) and told to extract real questions first and write the rest. If the backend returns nothing, fetchAIQuestions falls back to getBankQuestions in frontend/lib/questionBank.ts.

Reason. The landing page promises questions "Drafted in the real format" and "Checked against the web". An LLM alone invents plausible but wrong questions; real sources fix that where they exist. The offline bank means a game always starts, even with no API key.

Consequence. A question is labelled web only if the first 50 normalized characters of its stem or passage appear on the cited page (_normalize_llm_question); otherwise it is ai. Every question carries source, sourceName and sourceUrl so the UI can say where it came from. One LLM call is capped at MAX_LLM_QUESTIONS (25). The offline bank is small: nine questions per section, 36 in all.

B.5Question length matched to the game

Decision. Games have a pace. gamePace marks squid-game as deep and every other game as quick, and the backend filters with is_quick_question and _fits_pace.

Reason. The comment in question_sources.py: "Fast games need questions that can be read and answered in seconds; slow games take the long passages and multi-step problems."

Consequence. Quick games never see reading passages, so verbal practice in them is limited to short skills (QUICK_SKILLS). The College Board fetch oversamples five times for quick games because so many candidates are dropped.

B.6Weak topics decided per game, by fixed thresholds

Decision. GameService._update_user_stats marks a topic weak below 50 percent accuracy in the game just played and strong at 80 percent or more, and moves topics between the two lists.

Reason. The comment: "A topic moves between the lists as the player improves or slips."

Consequence. One bad game makes a topic weak, and one good game clears it. Topics in neither range keep whatever label they had. The dashboard and the agent both read these lists.

B.7Lessons as static content

Decision. The fifteen lessons are TypeScript constants in frontend/lib/lessons.ts, one per topic in COURSES, each with ideas, a worked example, traps and a quick check.

Reason. Lessons must be right, and they change rarely. Static content is reviewed in a pull request, costs nothing to serve, and needs no backend.

Consequence. Editing a lesson is a code change and a deploy. A new topic in COURSES needs a lesson in the matching array, or it has none.

B.8A video provider chain with a one-day cache

Decision. videos.py tries the YouTube Data API (YOUTUBE_API_KEY), then Serper (SERPER_API_KEY), then DuckDuckGo; the first provider with results wins. Results are cached in memory for CACHE_TTL_SECONDS (24 hours), ranked toward trusted channels and 3 to 25 minute lengths, with up to GREGMAT_SLOTS (3) GregMat videos first.

Reason. DuckDuckGo needs no key but rate limits; the paid providers are reliable but optional. The module docstring explains the ranking: lesson-length videos from established test-prep channels.

Consequence. With no keys set, videos still work, slowly and sometimes not at all. Only non-empty results are cached, "so a rate-limited search is retried next time". The cache is per process, so each Vercel instance warms its own.

B.9Profiles in a table, with a pending-profile flow

Decision. Profiles live in profiles, keyed by user_id, saved by an upsert in PUT /api/profile. When signup returns no session (email confirmation on), the profile is parked in localStorage as pending_profile and saved on first login.

Reason. The comment in frontend/lib/profile.ts: "When Supabase requires email confirmation, signup returns no session, so the profile can't be saved yet."

Consequence. A student who confirms and logs in on another device has no profile and is asked again. Usernames are unique; a clash is a 409, and signup or login sends the student to /profile?setup=1 rather than failing.

B.10Lesson progress in localStorage

Decision. "Mark as learned" writes to the learned_lessons key in frontend/lib/learnProgress.ts. So do exam preferences (exam_prefs) and high scores (arcade_hi_<gameId>).

Reason. The file's comment: "Kept in this browser only." It needs no table, no endpoint and no sign-in.

Consequence. Progress does not follow the student between browsers. Moving it to a table is a small, self-contained change.

B.11Mock exams saved as game sessions

Decision. app/mock/page.tsx saves results with saveScore('mock-exam', ...), in the same GameAnalytics shape as a game.

Reason. The comment: "Save it alongside game sessions so it feeds statistics and weak topics." No new table or endpoint.

Consequence. gameTitle special-cases mock-exam. Statistics mix mock exams with games.

B.12Uploaded questions need approval

Decision. Questions from uploads go into custom_questions as pending. Only approved ones are served, and they make up at most half of a game's set (limit // 2 in get_questions).

Reason. Parsed and LLM-extracted questions can have the wrong or missing answer (correct_answer is nullable). The student is the only one who can confirm them.

Consequence. Uploading has a review step. The rest of every set still comes from the agent, so the student's own material never crowds out real exam questions.

B.13A neo-brutalist and glass design system

Decision. The site's look is thick ink outlines with hard offset shadows (brutal, brutal-sm, brutal-lg in tailwind.config.js) combined with frosted glass panels, over a paper background, in a five-colour palette: paper, ink, cobalt, lime, coral.

Reason. The comment in app/globals.css: "SATistics theme: brutalist outlines with frosted glass panels". It reads as a game, not a textbook.

Consequence. Use the component classes in globals.css (.brutal, .glass, .btn) and the Tailwind tokens rather than raw colours. The in-game screens use a separate arcade skin with the Press Start 2P font from lib/arcade.ts.

B.14Game covers drawn as inline SVG

Decision. components/brand/GameCover.tsx draws each game's cover as SVG in the site palette, with a FALLBACK for unknown ids.

Reason. The file's comment: "Illustrated cover art for each game, drawn as SVG in the site palette." No image assets to license, load or keep in sync with the palette.

Consequence. A new game needs a cover entry in COVERS, written as SVG.

B.15Schema as hand-run SQL files

Decision. The schema lives in backend/database/*.sql, run by hand in the Supabase SQL editor. There is no migration tool.

Reason. Few tables, one environment, one maintainer.

Consequence. Order matters and nothing records what has been applied. reset.sql recreates the four core tables but not materials or custom_questions, so after a reset run add_materials.sql again.

B.16The backend as one Vercel Python function

Consequence. In-memory caches are per instance and lost on cold starts. Long question builds (web search plus an LLM call) run inside a single function invocation. The Docker, Fly, Railway and Render configs in backend/ are left over and not used.
